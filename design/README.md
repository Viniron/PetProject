# design/ — макеты интерфейса

Здесь проектируется интерфейс JARVIS: экран за экраном, до того как
появится `apps/web/`. Это **входные данные** для будущего фронтенда,
а не сам фронтенд.

**Где мы сейчас — `PROGRESS.md`.** Начинать всегда с него.

---

## Как посмотреть макет

Двойной клик по файлу в `mockups/`. Откроется в браузере.

Ни `npm install`, ни сборки, ни интернета не нужно: макеты — чистый
HTML и CSS, все стили лежат локально в `tokens.css`. Это сделано
намеренно, чтобы посмотреть макет можно было в любой момент с любой
машины, не поднимая окружение.

---

## Как Claude смотрит макет сам

Playwright установлен и работает, но **протокол `file://` он блокирует**.
Поэтому перед проверкой поднимается локальный сервер из папки `design/`:

```bash
python -m http.server 8777 --bind 127.0.0.1
```

и макет открывается как `http://127.0.0.1:8777/mockups/00-themes.html`.

Смотреть макет глазами обязательно. Структурная проверка (баланс тегов,
отсутствие внешних ссылок) пропускает ровно те дефекты, ради которых
макеты и делаются: на этапе 0 подпись «Календарь» не помещалась в круглую
подложку вкладки — разметка при этом была полностью валидна.

Скриншоты Playwright складывает в `tmp/` в корне репозитория; папка
в `.gitignore`, после проверки её можно удалять.

## Что здесь лежит

```
design/
  PROGRESS.md    ← текущий этап, что утверждено, решения по ходу
  README.md      ← этот файл
  tokens.css     ← палитра (светлая + тёмная), типографика, радиусы, отступы
  mockups/
    00-styles.html   три варианта стиля — история выбора
    00-themes.html   утверждённый результат: две темы рядом
    ...              дальше по файлу на экран
```

`tokens.css` подключается каждым макетом. Все цвета и размеры —
CSS-переменные в одном месте, поэтому правка палитры перекрашивает
все макеты сразу. Если какой-то цвет прописан прямо в макете мимо
переменных — это ошибка, стиль перестал быть системным.

**Тем две.** Светлая — база на `:root`, тёмная переопределяет только цвета.
Переключение: `data-theme="light"` или `data-theme="dark"` на любом
элементе; без атрибута тема берётся из настройки системы.

## Что значит «утверждён»

Этап закрывается **только после явного «ок» от owner**. Не «выглядит
неплохо», не молчание — именно подтверждение. До этого статус в
`PROGRESS.md` остаётся «🔄 на рассмотрении», и следующий экран не
начинается.

Причина простая: каждый следующий макет опирается на предыдущий.
Незакрытый этап 1 означает, что этапы 2–9 придётся переделывать.

Всё, что owner поправил или выбрал, дописывается в раздел
«Решения по ходу» в `PROGRESS.md` — чтобы в новом чате это не
обсуждалось заново.

## Данные в макетах вымышлены

Реального API пока нет — по roadmap (`docs/SPEC.md` §1) движок курсов
делается позже, чем UI. Поэтому всё, что видно в макетах: расписание,
названия тем, оценки, минуты — **выдумано для показа вёрстки**.
Каждый макет несёт об этом видимую пометку.

Формы данных при этом не выдуманы: они взяты из `docs/SPEC.md` §8.2
(узел змейки) и §6 (контракт разбора работы). Макет показывает те поля,
которые реально будут, а не удобные для картинки.

## Отношение к будущему `apps/web/`

Макеты — не прототип на выброс, но и не код продукта.

По ADR-017 фронтенд будет **Next.js + Tailwind**. Здесь Tailwind не
используется: он требует сборки, а требование к макетам — открываться
файлом. При переезде разметка перепишется в компоненты и классы,
а `tokens.css` переедет как источник темы — значения переживут,
синтаксис нет.

Поэтому в макетах не стоит вылизывать структуру HTML: важны решения
про композицию, иерархию, состояния и цвет.
