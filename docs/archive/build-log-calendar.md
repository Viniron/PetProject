## Э0 · Скелет монорепо — техническое задание

Цель: `test` и `lint` существуют и зелёные **до** первой строки бизнес-логики.
Ничего предметного в этом этапе нет — ни календаря, ни ИТМО, ни моделей.

**Состав.**

```
apps/api/
  pyproject.toml            зависимости, ruff + black + mypy + pytest в одном файле
  jarvis_api/
    __init__.py             версия пакета
    config.py               Settings на pydantic-settings, всё из env
    main.py                 FastAPI app + GET /health
  tests/
    test_health.py          живость + tz-aware время
Makefile                    dev / test / lint / migrate / sync-itmo / plan-today / backup
make.ps1                    те же цели для Windows, пока make не установлен
.env.example                только заглушки
infra/docker-compose.yml    api + postgres, restart: unless-stopped
infra/Dockerfile.api        multi-arch: linux/amd64 + linux/arm64
.github/workflows/ci.yml    lint + mypy --strict + pytest на Linux
.pre-commit-config.yaml     gitleaks (публичный репозиторий, ADR-019)
```

**Что уже выяснено и не нужно переоткрывать:**

- `fastapi` ставится версии 0.141; `TestClient` тянет `httpx` и предупреждает
  `StarletteDeprecationWarning: install httpx2 instead` — предупреждение
  безвредное, но `httpx2` в dev-зависимостях снимет шум.
- Набор правил ruff, который стоит взять: `E, F, W, I, UP, B, DTZ, ASYNC, T20`.
  **`DTZ` здесь не украшение** — он превращает инвариант 7 (нет наивных
  `datetime`) из пункта ревью в ошибку линтера. `T20` ловит `print` в сервисе.
- `/health` **не должен трогать базу**: он обязан отвечать и до того, как
  `DATABASE_URL` заполнен, иначе нечем проверять поднятие стека на Э1.
- Тесты пишутся по-русски в именах — так же, как комментарии в `tokens.css`.

**Решения, которые нужно принять на Э0 (спросить owner, не выбирать молча):**

1. **`make`.** Либо owner ставит его (`winget install GnuWin32.Make` или
   Git Bash + `choco install make`), либо в репозитории живёт `make.ps1`
   с теми же целями. `CLAUDE.md` требует `Makefile` — он будет в любом случае,
   вопрос только в том, чем owner запускает цели у себя.
2. **Docker.** На Pi обязателен — там весь стек. На машине owner нужен раньше,
   чем предполагалось: dev-база больше не берётся у managed-провайдера
   (ADR-020). Два варианта, выбирает owner: **(а)** Docker Desktop на Windows
   и Postgres контейнером локально — работает без домашней сети и физически
   не может задеть prod; **(б)** второй инстанс `jarvis_dev` на Pi, доступный
   по локальной сети, — Docker Desktop тогда не нужен вовсе и 3–4 ГБ RAM
   на ноутбуке остаются свободными, но разработка вне дома требует туннеля,
   а prod рядом. Вариант (а) безопаснее, (б) дешевле.
3. **`apps/web`.** Скелет Next.js создаётся `create-next-app` и приносит
   сотни файлов. Предложение: в Э0 фронта нет вообще, он целиком в Э7 —
   иначе Э0 перестаёт быть проверяемым за один взгляд.
4. **`mypy`** — см. поломку выше: в CI обязательно, локально по возможности.

**Критерий закрытия Э0:**

- `pytest` зелёный (2 теста: живость, tz-aware);
- `ruff check` и `black --check` чисты;
- `mypy --strict` чист в CI;
- `docker compose config` валиден (без запуска);
- `gitleaks` в pre-commit срабатывает на подложенном тестовом секрете;
- `.env.example` содержит **только** заглушки, ни одного настоящего значения.

**Э1 · блок снят, решения owner, 2026-09-03.** Owner дал тот самый отдельный

- **Ночной бэкап планирует systemd timer на хосте,** а не cron внутри
  контейнера. Юниты лежат в `infra/systemd/` и ставятся симлинком; таймер

  непривилегированным пользователем. Цена решения названа: часть настройки
  живёт на хосте, а не целиком в compose.
- **На Э1 в prod-базе живёт таблица-проба `restore_probe`** — несколько строк
  с tz-aware временем, создаётся скриптом. Без неё восстановление проверяет

  месте, а это и есть смысл бэкапа. Удаляется на Э2 первой миграцией.
  Инвариант «схема только через Alembic» не затронут: это проба бэкапа,

- **SSH-доступ к Pi даётся Claude.** Owner ставит ОС, дальше Docker, клон,

  на Э0 ставились make и Docker. Секреты в `.env` вписывает owner сам:

- **ОС переустановлена, и это был блокер, а не гигиена.** На карте стояло

  заметно старее, поэтому не брался.

Находки, каждая из которых стоила бы отдельного разбирательства в новом чате:

- **Raspberry Pi Imager 2.x провижионит через cloud-init,** а не через
  `custom.toml` или `firstrun.sh`: в командной строке ядра появляется
  `ds=nocloud;i=rpi-imager-<id>`, на bootfs лежат `user-data`, `meta-data`,
  `network-config`. Положенный руками `custom.toml` не читается вовсе — он так
  и остался на разделе нетронутым, вместе с паролем Wi-Fi открытым текстом
  (удалён). Проверять, применились ли настройки, надо по cloud-init файлам.
- **memory cgroup отключён прошивкой платы,** и в `cmdline.txt` этого не видно:
  `cgroup_disable=memory` добавляет firmware. Без него Docker не ограничивает
  память контейнеров. Дописано `cgroup_enable=memory cgroup_memory=1`; проверено
  фактом, а не файлом — контейнер с `--memory 64m` получил ровно 67108864 байт.
- **`docker compose` ищет `.env` в каталоге compose-файла,** то есть в `infra/`,
  а не в корне репозитория, где живёт `.env.example`. Сейчас стек поднимается
  с `--env-file .env`; в `Makefile` это надо внести на Э1a, иначе `make` на Pi
  свалится на отсутствии `POSTGRES_PASSWORD` — причём не сразу, а на первой
  цели, которая дойдёт до compose.
- **Беспарольного `sudo` cloud-init не выдаёт,** в отличие от старых образов с
  пользователем `pi`. Настроен `/etc/sudoers.d/010_jarvis-nopasswd`.
- **Локальная сеть с ноутбука была недоступна из-за kill-switch в AmneziaWG:**
  клиент блокирует всё, что не идёт в туннель, включая домашние адреса. Симптом,
  по которому это узнаётся сразу: `ping` до собственного роутера отвечает
  `General failure`, при живом интернете через VPN. Лечится снятием галочки
  «Block untunneled traffic» — выключать VPN целиком не требуется.

**Э1 · решения по ходу, 2026-09-03.**

- **`sudo` без пароля для `jarvis`.** Обоснование: вход на плату только по
  ключу (аутентификация по паролю в SSH отключена при провижининге), наружу
  плата не выставлена, и беспарольный `sudo` — штатное поведение Raspberry Pi OS
  для первого пользователя. Альтернатива — передавать пароль в каждой команде,
  оставляя его в списке процессов, что хуже. Файл ставил owner руками: пароль
  знает только он, и в чат он не попадал.
- **Пароль базы сгенерирован на плате** (28 символов) и лежит в `~/jarvis/.env`
  с правами 600. В репозиторий и в чат не попадает; `DATABASE_URL` собирается
  из `POSTGRES_*` внутри compose, второй копии пароля не существует.
- **Доступ Claude к плате** — ключ `~/.ssh/jarvis_pi` на машине owner,
  пользователь `jarvis`. **Обращаться по имени `jarvis.local`, а не по адресу:**
  адрес выдаёт DHCP, и он меняется при смене сети — за один день 2026-09-03
  сменился с `192.168.0.111` на `192.168.0.109` после переезда платы. Имя
  отвечает по mDNS в любой сети. Если mDNS молчит, плата ищется сканированием
  подсети по MAC-префиксу `dc:a6:32`.

**Э2 · найдено проверкой.** Семь вещей, каждая из которых стоила бы времени
на Pi, где отладка дороже.

1. **`alembic.ini` читается в кодировке локали.** Alembic открывает ini
   с `encoding="locale"`; на Windows это cp1251, и русский комментарий в UTF-8
   роняет CLI ещё до запуска команды. Файл теперь ASCII-only, пояснения по-русски
   живут в `alembic/env.py`, который Python читает как UTF-8. На Linux с локалью
   `C` было бы то же самое.
2. **Пути внутри ini заданы через `%(here)s`.** Иначе `script_location = alembic`
   разрешается от текущего каталога, и `make migrate` работал бы только из
   `apps/api`, но не из корня репозитория.
3. **Внешний ключ сам по себе не задаёт порядок вставки.** SQLAlchemy строит
   порядок по `relationship`, а не по FK: без связи сырьё захвата уходило
   в базу раньше черновика и падало на внешнем ключе. Связь добавлена
   с `passive_deletes=True` - удаляет по-прежнему база каскадом, ORM не читает
   `bytea` ради удаления.
4. **Строке-одиночке нужен `autoincrement=False`.** Единственному целочисленному
   первичному ключу SQLAlchemy заводит последовательность; `settings.id`
   получал `nextval`, и `alembic check` справедливо находил расхождение.
5. **Сессия тестов работает в savepoint** (`join_transaction_mode="create_savepoint"`).
   Тесты намеренно ловят `IntegrityError` и делают rollback; без вложенной
   транзакции этот rollback откатывал внешнюю - ту, которой фикстура убирает
   за тестом.
6. **Проверка доступности тестовой базы кэшируется.** Без кэша каждый
   пропущенный тест заново ждал таймаут соединения: прогон без базы занимал
   132 секунды вместо пяти.
7. **Git Bash подменяет аргументы, похожие на пути Linux.** Команда
   `docker run ... alembic -c /app/apps/api/alembic.ini` приходит в контейнер
   как `C:/Program Files/Git/app/...`, и alembic отвечает «No script_location
   key found» - выглядит как ошибка образа, а является особенностью MSYS.
   Контейнерные команды с Windows проверять обёрткой `sh -c '...'`; на Pi
   этого нет.

Мелочи тем же прогоном: `mypy` не видел `jarvis_api` из `alembic/env.py`, пока
в конфиг не добавлен `mypy_path = "$MYPY_CONFIG_FILE_DIR"` (относительный путь
там разрешается от текущего каталога, а не от файла конфигурации); ruff принимал
библиотеку `alembic` за локальный пакет из-за одноимённого каталога в репозитории -
поправлено `known-third-party`.

**Э1 · у платы нет часов, и это влияет на бэкап.** Найдено по расхождению:
`docker ps` показывал контейнеры «Up 2 hours» при uptime системы 8 минут.
Разгадка - у Raspberry Pi нет батарейки RTC: при включении время берётся из
последнего сохранённого systemd и уточняется по NTP только после появления
сети. Docker записал время старта по неверным часам, потом они прыгнули на
2,5 часа вперёд.

Для бэкапа это не косметика: **имена дампов строятся из времени, а ретеншн
сортирует копии по имени.** Дамп, снятый до синхронизации, получил бы имя
«из прошлого» и был бы удалён первым - при том, что он самый свежий.
Лечение - две строки в `infra/systemd/jarvis-backup.service`:

```
Wants=time-sync.target
After=time-sync.target
```

Теперь джоб не стартует раньше, чем часы выверены. Проверено:
`systemctl show jarvis-backup.service -p After` содержит `time-sync.target`.

Сортировку по имени менять на сортировку по времени файла не стали намеренно:
`mtime` зависит от тех же часов, и проблему это не решило бы, а порядок
перестал бы читаться глазами.

  `UnicodeDecodeError: 'utf-8' codec can't decode byte 0xd0`. `readline`
  декодирует приглашение по локали, и хотя `print` тем же текстом работает,
  `input` падает. Из-за этого ответ `y` не дошёл до кода удаления, и старый
  ключ остался жив. Все приглашения ко вводу переведены на латиницу, причина
  записана в шапке скрипта - чтобы это не «починили» обратно.
- **Справка о длинах ключей была неверной.** У мастер-ключа `keyID` - это
  идентификатор аккаунта, около 12 символов, а сам ключ около 42; числа
  25/31 относятся к обычным ключам. Первый `401` owner получил именно из-за
  этой путаницы.

**Э1 · раскладка копий по префиксам, 2026-09-03.** Требование ADR-020 про
глубину 7 ежедневных / 4 недельных / 6 месячных не выполнялось: джоб кладёт
дамп в один префикс, а правила жизненного цикла B2 различают копии
**только по префиксу имени**. Значит раскладывать обязан джоб - иначе все
копии попадают под одно правило и живут одинаково недолго.

Сделано: `target_prefixes()` возвращает `daily` всегда, добавляет `weekly`
в воскресенье (конец недели по ISO - недельной копией становится последняя
за неделю, а не первая) и `monthly` первого числа. `upload_dump()` грузит
файл под каждым префиксом, авторизуясь в B2 один раз: токен живёт сутки.

Тестов стало 24 (было 18). Добавлены четыре случая раскладки, включая тот,
который ломается тихо: **первое число, выпавшее на воскресенье** - копия
обязана лечь трижды, а не дважды (проверено на 2026-11-01). Плюс проверка,
что авторизация одна на все префиксы.

Проверено на живой плате:

| Что | Как |
|---|---|
| три префикса | прогон с датой 2026-11-01 на подставном B2: `daily/`, `weekly/`, `monthly/` - три выгрузки, ping после всех |
| обычный день | живой прогон 2026-09-03 (четверг): только `daily/`, как и должно |
| ретеншн | впервые сработал на живых данных: восьмая локальная копия удалена, осталось семь |
| содержимое бакета | спрошено у облака (право `listFiles` появилось вместе с новым ключом): три копии, у каждой сходится sha1 |

**Числа для правил жизненного цикла B2**, которые остаётся выставить owner

| Префикс | Скрыть через | Удалить через | Смысл |
|---|---|---|---|
| `daily/` | 8 дней | 1 день | 7 ежедневных копий плюс запас на сутки |
| `weekly/` | 29 дней | 1 день | 4 недельных |

**Э1 · восстановление проделано owner руками, 2026-09-03.** Критерий закрытия
этапа по ADR-020 выполнен: дамп **скачан из B2 через веб-интерфейс**,
доставлен на плату, развёрнут в отдельную базу `jarvis_restore` и проверен
запросом - `SELECT * FROM restore_probe` вернул три строки с временем в UTC.

Существенно, что проверялся именно скачанный из облака файл, а не локальная
копия: перед восстановлением сверены контрольные суммы, и sha1 совпал
с тем, что хранит B2 (`3802b015...`, 2007 байт). То есть проверен весь тракт
целиком - `pg_dump`, выгрузка, хранение, скачивание, `pg_restore`, - а не
только его начало.

Мелочи, найденные при этом и стоящие строки в RUNBOOK:

- **Backblaze меняет `/` на `_` в имени при скачивании:** файл приходит как
  `daily_jarvis-...dump`, а не `daily/jarvis-...dump`.
- **PowerShell не раскрывает `*` для внешних программ** - `scp` с маской
  ищет файл с буквальной звёздочкой в имени. Имя нужно указывать целиком.
- **`docker cp /tmp/...`, выполненный на ноутбуке вместо платы,** Docker
  Desktop читает как `C:	mp\...` и отвечает `GetFileAttributesEx C:	mp`.
  Признак, по которому это опознаётся сразу: приглашение `PS C:\...`
  вместо `jarvis@jarvis:~ $`.

**Код Э1 зафиксирован:** коммит `948da34`, запушен в `main`, **CI зелёный**
(40 с). Незакоммиченного не осталось.

Отступление от конвенции, зафиксированное как факт: коммит сделан прямо
в `main`, без ветки и pull request, и сообщение не в стиле Conventional
Commits, которого требует `CLAUDE.md`. История уже опубликована,

**Одно решение по ходу, которого не было в плане.** `--dry-run` сохраняет
токены, добытые входом, — единственное исключение из «не пишет ничего».
Иначе каждый ручной прогон логинился бы паролем заново, то есть ровно то,
чего мы избегаем приоритетом refresh-токена. Исключение узкое и проверено
тестом: зеркало, аудит и `job_runs` после dry-run пусты, токены сохранены.

**Фикстуры синтетические, и это записано в них самих.** Настоящего ответа
портала не было и взять его было неоткуда: креды живут в `.env` на плате.
Имена полей и вложенность взяты из референса, значения выдуманы. После
первого живого забора фикстуры заменяются анонимизированным настоящим
ответом — это хвост этапа, а не отдельная работа: разбор, проверенный
только на выдуманном ответе, доказывает, что код читает наши собственные
представления о портале, и ничего больше.

- **Шифрование проверено на боевых данных:** три строки `integration_tokens`
  расшифровываются ключом из env, ни один секрет не встречается открытым
  текстом ни в своей строке, ни в чужой, чужим ключом не открывается ни одна.
  Пароль в базе совпал с `ISU_PASSWORD` — переезд из env в базу состоялся.
- **Деградация проверена на плате, а не только в тестах.** Прогон с заведомо
  недоступным адресом портала: три попытки с паузами 2 и 4 секунды, отказ
  громкий, **зеркало нетронуто — 80 пар и прежний `fetched_at`**, то есть
  пометка давности сохранена (инвариант 9). Строка в `audit_log` со статусом
  `error`, `job_runs` помечен `failed` с причиной. Следующий успешный прогон
  вернул `ok`.

**Четыре расхождения между настоящим порталом и референсом.** Все найдены
живым прогоном, все были бы не найдены иначе.

1. **У портала есть поле `format`** («Очный», «Очно - дистанционный » —
   с хвостовым пробелом). Референс его не читает. По выдуманной фикстуре мы
   выводили формат из наличия ссылки на Zoom и писали бы пусто у каждой
   очной пары — а дистанционных пар в семестре не оказалось ни одной.
2. **Рядом с `data` лежат `code` и `message`,** на успехе `code = 0`. Это
   самое дорогое из четырёх: отказ сервиса приходит с **HTTP 200** и пустым
   `data`, то есть без проверки неотличим от каникул. Окно зеркала
   заменяется целиком, поэтому такой ответ стёр бы все пары окна, а Э4
   следом удалил бы их из Google. Проверка добавлена, проверена от обратного.
3. **Поля `teacher_fio` нет вовсе,** есть только `teacher_name`.
4. **День без пар приходит пустым списком,** а не `null`: из 36 дней десять
   пришли `[]` и ни одного `null`.

**Фикстуры заменены настоящим ответом,** обезличенным на плате структурно
по именам полей; сырой ответ в репозиторий не попадал (ADR-019). Подробности
и правила обезличивания — `apps/api/tests/fixtures/itmo/README.md`.

**Вывод, который стоит унести на Э4 и дальше.** Фикстура, написанная по
чужому коду, проверяет наши представления об источнике, а не источник.
119 тестов были зелёными и при этом не знали ни про `format`, ни про `code`,
ни про то, что переменные не доходят до контейнера. Живой прогон — не
формальность в конце этапа, а единственная проверка, которой у нас
на источник вообще есть.

**Итог проверки:** `make lint` чист · **135 тестов** зелёных против настоящей
Postgres · `make compose-check` на трёх конфигурациях · образ собран под

**Три зависимости, которых не было** (ADR-026, решение owner): `google-api-python-client`,
`google-auth`, `google-auth-httplib2`. Следом приезжают `google-api-core`, `requests`,
`protobuf`, `proto-plus`, `googleapis-common-protos`, `opentelemetry-api` — три строки
в `pyproject.toml` превращаются в дюжину пакетов в образе, и это названо в ADR прямо.
Проверено, что колёса под `linux/arm64` публикуются для всех, включая `protobuf`:
компилятор на плате не нужен.

**Что найдено при реализации.**

1. **`session.rollback()` при отказе одного события откатывал чужую работу.**
   Найдено тестом «следующий прогон дописывает неудавшееся»: после отказа
   на первой паре из сессии исчезали строки, вставленные до джоба, и второй
   прогон падал с «календарь не создан». Заменено на вложенную транзакцию
   (`begin_nested`) вокруг каждого события: снимается ровно полуприменённое
   одно событие. В проде симптом был бы тем же классом беды, что и на Э3
   с проброской переменных, — код «работает», пока не встретит отказ.
2. **`static_discovery=True` обязателен.** Без него `discovery.build()` идёт
   за описанием API в сеть — то есть тесты ходили бы в Google (запрещено
   прямо), а на плате первый же прогон зависел бы от доступности ещё одного
   адреса, помимо самого API.
3. **Таймаут задаётся только в одном месте и легко теряется.** `httplib2.Http()`
   по умолчанию ждёт без ограничения; `CLAUDE.md` требует таймаута на каждом
   внешнем вызове. Джоб с зависшим сокетом не падает и не завершается — он
   просто не делает ничего до перезапуска платы, и в `job_runs` остаётся
   `running`. Явный `httplib2.Http(timeout=…)` внутри `AuthorizedHttp`.
4. **`update`, а не `patch`.** Тело события формируется из зеркала целиком,
   и поле, исчезнувшее в источнике (пропала аудитория), обязано исчезнуть
   в календаре. `patch` оставил бы прежнее значение — то есть врал бы
   ровно в том поле, ради которого событие и открывают.
5. **Типы чужих пакетов.** У `google-api-python-client` нет `py.typed` — взяты
   стабы `google-api-python-client-stubs` в dev. У `google-auth-httplib2` нет
   ни того, ни другого, и стабов не существует вовсе: заведён единственный
   узкий `ignore_missing_imports` на этот модуль. Один вызов `google-auth`
   подавлен точечным `type: ignore`. Глобального ослабления `--strict` нет.
6. **`alembic revision -m` с русским текстом даёт нечитаемое имя файла.**
   Имя строится из сообщения средствами консоли, и на Windows оно приезжает
   в cp1251: файл назывался `…_settings_id_календарей_google_э4.py`
   кракозябрами. Заголовок ревизии теперь латиницей, пояснение по-русски —
   в докстринге файла, который Python читает как UTF-8. Это продолжение
   находки Э2 про `alembic.ini` и локаль.
7. **Подставной Google — сервер с состоянием, а не список ответов.**
   `HttpMockSequence` из самого SDK не подошёл: половина проверок этапа
   («второй прогон не делает ничего», «событие, удалённое руками, создаётся
   заново», «журнал восстанавливается по ключам из выдачи») требует памяти
   между запросами. Написан транспорт `httplib2` на ~200 строк, который
   ведёт календарь в словаре и считает обращения.

## Э5 · Джобы и планировщик — сделано

**Решения owner, 2026-09-10.** Четыре развилки закрыты до первой строки кода,
записаны в ADR-027: APScheduler ветки 3.x; цепочка гоняется каждые три часа
с 06:30 до 21:30; рубильник `SCHEDULER_ENABLED` включён по умолчанию и выключен
на машине разработки; **расчёт времени напоминаний (`SPEC.md` §4) из этапа
исключён.**

**Почему §4 ушёл.** Всё, чем он считает время, — `offset_minutes`,
`fallback_time`, `latest_start` — приходит из манифеста курса. Курсов
установлено ноль, курсовых таблиц в схеме v1 нет, `calendar_events.source`
допускает только `itmo` и `capture`. Писать его сейчас значило бы выдумать
содержание курса, что запрещено прямо. §4 уезжает в дорожку курсов вместе
с заглушкой `make plan-today`, текст которой перестал ссылаться на Э5
и называет настоящую причину.

**Что появилось.**

| Файл | Роль |
|---|---|
| `jobs/common.py` | зона owner, окно расписания, отметка прогона — то, что было в трёх копиях |
| `jobs/runner.py` | цепочка `daily_calendar`, правило догона, `make daily` |
| `scheduler.py` | APScheduler: шесть слотов, зона owner, одноразовый подъём |
| `main.py` | lifespan, настройка логов процесса, рубильник |
| `config.py` | четыре `SCHEDULER_*` и разбор слотов с валидацией |
| `tests/test_runner.py` | 16 тестов цепочки и догона против настоящей Postgres |
| `tests/test_scheduler.py` | 9 тестов расписания: слоты, зона, уникальность id |
| `tests/test_lifespan.py` | 3 теста подъёма процесса, в том числе без базы |
| `docs/RUNBOOK.md` | раздел «Расписание джобов»: настройки, проверка, разбор отказов |

**Одна новая зависимость:** `apscheduler>=3.11,<4` (решение owner). Следом
приезжает `tzlocal` — чистый Python, колесо `py3-none-any`, компилятор на плате
не нужен. Стабов у APScheduler нет и не существует, взят точечный
`ignore_missing_imports` по прецеденту Э4.

**Что найдено при проектировании — четыре мины, из них три тихие.**

1. **`${SCHEDULER_ENABLED:-}` роняет процесс.** `test_compose_env.py` жёстко
   требует формат с пустым умолчанием, и для строк это безобидно. Но у
   планировщика есть `bool` и `int`, а на них пустая строка даёт
   `ValidationError` при построении `Settings` — то есть **на импорте
   `main.py`**, до всякого lifespan. `/health` не поднимается, healthcheck
   валится, `restart: unless-stopped` крутит контейнер по кругу; на плате это
   выглядело бы как «после `make build` API не встаёт». Заведён валидатор
   «пустая строка = умолчание», формат остался один на все переменные.
2. **`make dev` рубильником не выключался.** Цель поднимает uvicorn мимо
   compose, `infra/dev.env` до него не доезжает, `Settings` env-файл не читает.
   Каждое сохранение файла при `--reload` перезапускало бы процесс, а с ним
   и догоняющий запуск — в живой ИСУ и живой Google с машины разработки.
   Закрыто целевой переменной в `Makefile`.
3. **Логи джобов под uvicorn не видны вовсе.** uvicorn настраивает только свои
   логгеры и не трогает корневой, а `logging.basicConfig` наш код звал лишь
   в `main()` джобов. Из планировщика весь дифф и «75 создано» уходили бы
   в никуда, а `logger.error` выводился бы аварийным `lastResort` — без
   времени и имени. То есть «фоновые джобы падают громко» в единственном
   триггере, который на плате реально работает, держалось на честном слове.
4. **База в lifespan — цикл перезапуска.** Первая версия читала там зону owner.
   Недоступная база (в отличие от ненастроенной) не бросает исключение —
   она висит в таймауте сокета, а uvicorn не принимает соединений, пока
   startup не закончился. Теперь в lifespan нет ни одного обращения к базе:
   зона, слоты и решение о догоне живут в рабочем потоке.

**Правило догона переписано по ходу.** Задумывался порог «строка `running`
старше N минут — брошенная». Защищать оказалось нечего: решение принимается
при старте процесса, до первого прогона, и живому `running` взяться неоткуда —
процесс один, воркер один. Зато нашёлся сценарий, который тот порог не
покрывал: цикл перезапуска после неудачного прогона означал бы вход в ИСУ
на каждый рестарт, а за это портал банит. Порог заменён на **остывание**
последней попытки, и оно закрывает оба случая.

**Два дефекта Э4, найденные и починенные попутно.** Оба про неизвестную зону
в `settings`: `push_gcal.run_once` ловил `(PushError, GcalError)`, а
`owner_timezone` бросала `SyncError` из чужого модуля — сломанная зона давала
трассировку без строки в `audit_log` и без отметки в `job_runs`. Второе место
того же дефекта — сама запись следа об отказе читала зону голым вызовом и
падала второй раз, унося и причину. Тот же класс, что нашёл живой прогон Э4
на пропавшем календаре. Закрыто типом `OwnerZoneError`, страхующей
`зона_без_падения` и регрессионным тестом.

**Найден и попутный дефект `Makefile`:** в списке `.PHONY` вместо переносов
строк стояли литеральные `\n` — наследие правок Э3 и Э4. Цель с именем `\n`
ничего не ломала, но список читался как один длинный мусорный токен.

| Пункт | Как проверен |

## Э6 · API календаря

Первые предметные эндпоинты поверх схемы v1. Опора — `SPEC.md` §8.4 и §10.3,
развилки — ADR-031.

**Э6 закрыт 2026-09-13** после зелёной проверки (344 теста, `make lint` чист,
`alembic check` без новой ревизии) и живого прогона на плате.

**Работа начиналась дважды.** Шаги 1–6 были написаны в воркtree `site` и там
же остались незакоммиченными, пока main ушёл вперёд на два коммита (Ф1 и
дробление документов). Обнаружилось это вопросом owner «разве Э6 не был
сделан?» — а `BUILD-PROGRESS.md` на main показывал этап как не начатый,
потому что дробление шло от версии файла без правок Э6. Код перенесён на
`feat/e6-calendar-api` копированием файлов: все десять изменённых Э6 файлов
на main и в воркtree совпадали побайтно, конфликтовать было нечему.
**Вывод на будущее:** работа, лежащая в воркtree незакоммиченной, для
остального репозитория не существует.

**Состав этапа.**

| Что появилось | Где |
|---|---|
| подпакеты `api/` (граница HTTP) и `domain/` (арифметика без HTTP) | `jarvis_api/` |
| `GET /api/calendar` — сетка на день и неделю | `api/routes_calendar.py` |
| `GET` / `POST` / `DELETE` `/api/day-flags` | `api/routes_day_flags.py` |
| единое тело отказа и обработчики исключений | `api/errors.py` |
| контракт `packages/contracts/openapi.json` + `make contract` | `jarvis_api/contract.py` |
| три настройки живучести: порог давности, таймауты соединения и пула | `config.py`, `.env.example`, compose |

Итог прогона: **344 теста** (было 320 после Ф1), `make lint` чист,
`mypy --strict` на 64 файлах чист, миграции не потребовалось.

**Четыре мины, все тихие, все найдены тестами, а не ревью.**

1. **Обработчик `HTTPException` не доставал до отказов роутера.** Повешенный
   на `fastapi.HTTPException`, он молча не срабатывал: роутер Starlette при
   ненайденном пути бросает **базовый** `starlette.exceptions.HTTPException`,
   а подкласс в MRO базового не участвует. Неизвестный путь отдавал штатное
   `{"detail": "Not Found"}` — тело не из контракта, то есть клиент Э7,
   разбирающий ответ по схеме, получил бы поле, которого в ней нет.
2. **Имена моделей Pydantic попадают в контракт именами схем OpenAPI.**
   Первая версия называла тело отказа `Отказ` — в `openapi.json` появилась бы
   кириллическая схема, из которой генератор сделал бы кириллический тип
   TypeScript. Правило записано в докстрингах и закреплено тестом контракта:
   имена классов, полей и параметров — латиницей, остальной код русский.
3. **Кириллическое имя параметра пути ломает маршрут молча.** Starlette
   разбирает шаблон ASCII-регуляркой: `{id_периода}` не распознаётся как
   параметр вовсе, маршрут становится литералом, и любой `DELETE` отвечает
   404 «Not Found» — тем самым штатным телом, от которого избавлялись в п. 1.
4. **У движка не было таймаута соединения с Э2.** Джобам это не мешало — они
   падают громко и повторяются, — а для эндпоинта это прямое нарушение §10:
   недоступная база не отказывает, а висит до таймаута TCP операционной
   системы, то есть даёт «вечный спиннер». `pool_pre_ping` не спасает: сам
   ping зависает так же. Настроек стало три, а не две: без `pool_timeout`
   исчерпание пула во время прогона цепочки даёт тот же спиннер изнутри.

**Асимметрия переезда из `jobs/`.** Переехала только `границы_окна`;
`sync_window`, `owner_timezone`, `OwnerZoneError` и `FALLBACK_TIMEZONE`
остались в `jobs/common.py` и импортируются как есть. Причина не в чистоте
имени, а в зависимостях: `jobs/common.py` не тянет ничего тяжёлого и циклов
не создаёт, а импорт из `push_gcal` притащил бы в слой HTTP SDK Google.
Условие большого переезда — пятый потребитель (Ф6 или курсы) либо импорт
из `api/` в `jobs/`.

**`Пометка` живёт в `domain/day_flags.py`, а не в `calendar.py`,** хотя
показывает её день сетки: признак `manual` считается из константы
`АВТОПОМЕТКА`, и правило обязано лежать в одном месте с ней. Разъехавшись,
они дали бы период, который в сетке «системный», а в списке периодов
«ручной». Найдено при написании роутера: схема ответа потребовала признака,
которого у строки базы нет.

**Чего в этапе нет намеренно.**

| Что | Почему нет |
|---|---|
| «занятие курса», `calendar='study'` | считается по манифесту курса, §4 исключён из релиза (ADR-027 п. 11); курсов ноль, заполнять нечем. Запрет сделан исполняемым: тест контракта проверяет, что слова `study` нет ни среди имён свойств, ни среди значений enum |
| «сдвинуто ×N», `fallback` | §4 п. 3 и п. 5 |
| `late_classes` как значение, которое ставит API | ставит джоб §4, которого нет; API его читает, но создать и удалить отказывается |
| черновики захвата | их дата лежит в `capture_drafts.extracted` (JSONB), и схема этого объекта принадлежит Э8. Эндпоинт-список тоже не заводим: до Э8 черновики некому создавать, и он всегда возвращал бы `[]` |
| аутентификация, CORS | решение owner, ADR-031 п. 3, с условием «туннель не раньше аутентификации» |
| `PATCH /day-flags/{id}` | период правится удалением и вводом заново; экран периодов не нарисован |
| миграция | схема v1 покрывает всё: `reason` — свободный `String(64)` без CHECK |

**Э6 · живой прогон на плате, 2026-09-13.** Пятнадцать проверок по loopback
против настоящих пар и настоящей `settings.timezone`:

| Что проверялось | Результат |

**Что живой прогон нашёл:** ничего. Третий раз из четырёх — на Э3 и Э4

через `new Date()` превращается в зону браузера: у owner в поездке всё
расписание уехало бы на несколько часов — молча и правдоподобно. Часы
берутся разбором строки, зона для линии «сейчас» — из поля `timezone`
ответа, а не из браузера.

**`freshness.fetched_at` отдавался в UTC** — единственное время в ответе,
не приведённое к зоне owner. Полоса печатает его словами, и расписание
выглядело устаревшим на три часа раньше, чем на самом деле. Найдено
глазами на живом экране, а не тестом: тесты сравнивали моменты, а моменты
были равны. Исправлено в `domain/calendar.py`, проверка добавлена.

**Панель управления не должна переезжать между поддеревьями.** Пока
данных не было, тулбар жил в своей обёртке, а с приходом ответа переезжал
внутрь сетки — React пересоздавал его узлы, и нажатие, случившееся в этот
момент, пропадало вместе со старой кнопкой. Теперь обёртка `.cal` и шапка
на месте всегда, меняется только её содержимое. Первым это поймал тест
листания, а не браузер.

**Отказ без тела контракта всё равно даёт «Повторить».** ADR-034 велит
брать признак повтора у сервера, но 502 от прокси и 500 из-под упавшего
API сервером не написаны вовсе, и «нельзя» из молчания не следует.

*Чего в шаге нет намеренно:* экрана периодов `day_flags` (макет `09` ещё
не нарисован, дизайн на этапе 5) · занятий курсов, черновиков захвата
и пометок «сдвинуто»/`fallback` — их нет в контракте, а рисовать
правдоподобное вместо настоящего запрещает инвариант 9 · тёмной темы
отдельными правилами: она приходит из токенов · включения туннеля (шаг 4).

*Проверено глазами на живом стеке* (`make dev` + `make web-dev`, dev-база
с наполнением под проверку, удалённым после): неделя с конфликтами,
периодом и автопометкой; экран дня с тройным наложением; день вне окна
забора; полоса давности и пунктирные пары; упавший API — плашка с причиной
и повтором вместо пустого экрана.

**Шаг 4 · туннель: инструкция owner и проверка двери — 2026-09-13.** Опора —
ADR-031 п. 3 («туннель не включается раньше аутентификации»), ADR-033,
ADR-017. Развилки закрыты owner до начала работы: `/health` остаётся
открытым снаружи отдельной bypass-политикой (ADR-036), условие «дверь
раньше трубы» делается прогоном, а не абзацем.

*Состав:* раздел `docs/RUNBOOK.md` «Cloudflare» переписан с нуля — от
регистрации аккаунта и домена до проверки с телефона по мобильной сети ·
`jobs/tunnel_check.py` и цели `make tunnel-check` / `tunnel-check-pi` ·
ADR-036 · `redirect: "manual"` в клиенте фронта · четыре проверки overlay
платы в `test_compose_env.py` · 15 тестов проверки, 3 теста клиента.

*Дыра, найденная в собственной документации.* `.env.example` с шага 1
отправлял owner в «`docs/RUNBOOK.md`, раздел «Cloudflare»», а раздел там был
один — «Cloudflare Tunnel», написанный на Э1, и вёл он прямо к включению
туннеля: аккаунт, туннель, токен, `make up`. Ни слова про Access. То есть
единственная письменная инструкция этапа проводила ровно мимо той двери,
ради которой этап начинали с аутентификации. Тот же класс, что запоздавший
ADR шага 1: документ выглядит существующим и выполненным, пока его не
откроют.

*Находка на фронте: 302 от Access выглядел обрывом связи.* Протухшая сессия
приходит редиректом на страницу входа Cloudflare — на **чужой** источник.
`fetch` с умолчанием `redirect: "follow"` шёл туда сам, упирался в CORS
и отдавал `TypeError`, неотличимый от выключенной платы. Экран говорил
«Сервер не отвечает, нет связи с платой» и предлагал повтор, которым сессия
не чинится, — при живой плате и в одном клике от рабочего расписания.
Лечится `redirect: "manual"`: перехваченный редирект приходит ответом
`opaqueredirect`, и причина называется своим именем. Своих редиректов
у API нет, терять на этом нечего.

*Почему проверка смотрит на два адреса.* Наружу выходит `web`, а не `api`:
маршрут туннеля ведёт на Caddy, и дыра в прокси со стороны API не видна.
Проверяются оба, тем же путём, каким пойдёт запрос с улицы.

*Чего проверка не делает намеренно:* не трогает `CF_TUNNEL_TOKEN`
и `COMPOSE_PROFILES`. Ошибка в них громкая — `cloudflared` не поднимается,
и это видно в логах; проверять стоит тихие отказы. В контейнер `api` они
не проброшены по той же причине: токен двери незачем класть внутрь комнаты.

*Мелочь, стоившая прогона:* значение подставного заголовка было написано
кириллицей, и запрос падал на кодировании, не дойдя до двери. Заголовки
HTTP — ASCII.

*Чего в шаге нет и почему.* **Туннель не включён: у owner нет ни аккаунта
Cloudflare, ни домена** (2026-09-13). Домен платный — $10–12 в год за `.com`
из панели Cloudflare или несколько сотен рублей за `.ru` у российского
регистратора с делегированием NS (вопрос owner в тот же день), — и это
единственная постоянная трата проекта; бесплатного постоянного имени
у туннеля не бывает, а Access без своей зоны не работает. Инструкция и
проверка готовы и ждут. Живой прогон снаружи — вход по почте, отказ чужой
почте, открытый `/health`, `Registered tunnel connection` в логах — часть
закрытия этапа, а не этого шага. Экран периодов `day_flags` (макет `09`
не нарисован, дизайн на этапе 5), PWA-манифест и иконка — по-прежнему вне
Э7, как записано на шагах 2 и 3.

*Проверено на dev-стеке:* проверка против незапертого API (`ENV=dev`,
пустые `CF_ACCESS_*`) даёт шесть `FAIL`, включая «ДВЕРЬ ОТКРЫТА», и код
возврата 1; против запертого (`ENV=prod`, заполненные настройки) — один
`FAIL` на выдуманном домене команды и `OK` на всех пунктах запертости.
`docker compose config` проходит и с `COMPOSE_PROFILES=tunnel`.

**Шаг 4 продолжение · туннель включён — 2026-09-14.** Домен owner купил
в reg.ru (`viniron.ru`), зона подключена к Cloudflare, команда Zero Trust —
`viniron.cloudflareaccess.com`, два приложения Access заведены по RUNBOOK.
Дверь заработала сразу: снаружи `/` и `/api/calendar` отдают 302 на вход
с нашим `aud`, `/health` открыт (ADR-036), `make tunnel-check-pi` — тринадцать
`[OK]`. Труба не заработала, и разбор занял вечер.

*Пять правок по ходу, каждая из-за тихого отказа.*

**Плата отставала на два этапа.** `make tunnel-check-pi` не нашёлся вовсе:
на плате лежал код из `main` времён Э5, то есть API **без проверки токена
Access**. Включённый туннель поверх такого API — ровно то, что запрещает
ADR-031 п. 3. Ветка Э6–Э7 жила только на машине owner; выложена и забрана
платой перед всем остальным.

**`make build` собирал только `api`.** Комментарий над целью обещает, что
новый код приезжает на плату после неё, а фронт при этом оставался старым —
молча, потому что `up -d` поднимает уже собранный образ. Теперь `api web`.

**Токен туннеля утёк в переписку.** Owner выполнил показанную Cloudflare
команду `cloudflared service install <токен>` на **ноутбуке** — коннектор
встал службой Windows, а скриншот с токеном ушёл в чат. Две ошибки разного
рода: коннектор обязан жить на плате (адрес `web:8080` существует только
внутри её docker-сети, а ноутбук засыпает и уезжает), и секрет, попавший
в переписку, отзывается, а не забывается. Служба снята, туннель пересоздан,
старый токен умер вместе с ним.

**QUIC не проходит, HTTP/2 проходит.** Умолчание `cloudflared` — QUIC
по UDP 7844; precheck его хвалит, а дальше «failed to accept QUIC stream:
timeout». В команду добавлен `--protocol http2`.

**Энергосбережение Wi-Fi платы.** 10 % потерь до собственного роутера;
выключено глобально в `/etc/NetworkManager/conf.d/10-wifi-powersave.conf`,
а не в профиле соединения — профиль генерируется netplan и правку затирает.
Потери ушли, но туннель это не вылечило.

*Диагноз, ради которого и стоило мерить.* Коннектор изнутри рапортовал
`readyConnections: 4`, край Cloudflare в ту же секунду видел одно соединение
и `degraded`, а входящие запросы до коннектора не доходили вовсе — в логе
ни одной строки. Исключены проверками: конфигурация Access и маршрута,
origin (`web:8080` изнутри отдаёт 200), нагрузка платы (LA 0.07), Wi-Fi
(0 потерь на сотне пакетов, 5 МБ за 1,4 с, TLS к GitHub живёт 300 с), второй
коннектор, MTU (версия не подтвердилась при перепроверке), протокол и регион
(QUIC и HTTP/2, EU и US — одинаково). Осталось одно: сессии туннеля рвут
по пути. Решение — ADR-037: выход через AmneziaWG, в VPN уводится только
`198.41.192.0/20`.

*Ловушка, стоившая часа.* Панель Cloudflare отдаёт кэшированные ответы:
`status: down, connections: []` держался минутами при живом туннеле.
С обходом кэша — `degraded` и одно соединение. Статус туннеля в панели
не доказательство ни в одну сторону; доказательство — запрос снаружи.

*Ещё мелочь:* плата сменила адрес по DHCP (`.111` → `.113`) посреди работы,
отчего SSH стал отвечать `connection refused` — по старому адресу оказалось
чужое устройство. Постоянный адрес за платой не закреплён; задача отдельная.

**Э7 закрыт — 2026-09-14.** Живой вход с телефона по мобильной сети пройден
owner: страница Cloudflare, код на почту, экран календаря. Перед слиянием имя
переехало с `jarvis.viniron.ru` на апекс **`viniron.ru`** — правкой destination
у обоих приложений Access и публичного имени туннеля, в этом порядке (дверь
раньше трубы даже при переезде). `aud` основного приложения при правке
сохранился, поэтому `.env` на плате не трогали. Старая запись `jarvis` из DNS
ушла вместе с публичным именем; проверено снаружи: `viniron.ru/health` — 200,
`/api/calendar` и `/` — 302 на вход, `jarvis.viniron.ru` не резолвится.

*Цена выбора апекса, записанная здесь, чтобы не удивляться потом:* на этом
домене больше не повесить публичную страницу — он целиком за дверью Access.

*Хвосты, не блокирующие этап:* за платой не закреплён постоянный адрес в DHCP
(за вечер она переехала с `.111` на `.113`), и живёт она на Wi-Fi с сигналом
48 % — кабель Ethernet ей показан. Оба — в Э9, где живучесть.
