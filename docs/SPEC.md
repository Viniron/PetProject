# SPEC.md — спецификация платформы

Дополняет `CLAUDE.md`. Описывает **приложение**, а не учебные программы.

**Границы документа.** Здесь нет и не должно быть: содержания курсов, тем, уровней, пропорций занятия, лимитов повторений, названий конкретных моделей и их цен. Всё это приходит от owner — программы отдельными файлами курсов, выбор моделей отдельным решением. Задача платформы — исполнить **любую** программу и обратиться к **любой** назначенной модели. Пункты с **[?]** требуют подтверждения owner.

## 1. Roadmap

**Этап 1. Календарный фундамент.** Клиент my.itmo.ru → нормализованные занятия → Google Calendar через reconcile-джоб. Готово, когда: расписание на 2 недели в календаре, джоб запущен трижды без дублей, смена аудитории подхватывается.

**Этап 2. Захват событий.** Текст → фото → голос. Экран подтверждения с первой версии.

**Этап 3. Движок курсов на фикстуре.** Очередь, активности, состояния, rollover, таймер, отставание. Работает на `courses/_fixture/` — синтетический курс из десятка узлов. Без реального контента и без обращений к моделям. Самая важная и самая недооценённая часть: сломанный движок обесценивает любую программу поверх.

**Этап 4. Подсистема интервальных повторений.**

**Этап 5. Автонапоминания.** Расчёт времени, `latest_start`, `day_flags`, разрешение конфликтов.

**Этап 6. Слой моделей.** Маршрутизация по конфигу, учёт стоимости, кэш, фолбэк, структурированный вывод. На заглушках, пока owner не назначит модели.

**Этап 7. Проверка работ.** Контракт разбора, ошибки → карточки.

**Этап 8. Подбор материалов.** Поиск, валидация ссылок, кэш, антиповторы.

**Этап 9. Контрольные срезы.**

**Этап 10. UI.** Вкладки, змейка, экран занятия, календарь.

**Этап 11. Установка реальных программ.** Второй курс обязан встать **без изменений в ядре** — это приёмочный тест на модульность.

## 2. Движок курсов

### 2.1 Модель данных

```
Course → Unit → Node → Activity
```

`Node.kind`: `lesson` | `review` | `checkpoint` | `media` | `level_check`.

Единица планирования — **сессия**: один слот занятия. Длительность сессии, дни недели и состав блоков задаёт манифест курса; ядро значений не знает.

Манифест — структура, не содержание:

```yaml
id: <course-id>
title: <название>
schedule:
  days: [mon, tue, wed, thu, fri]     # рабочие дни курса
  minutes_per_session: <N>
  start_date: <YYYY-MM-DD>
  extra:                               # активности сверх сессии, свой счётчик
    weekday_watch: { minutes: <N>, counts_toward_session: false }
    sat: { kind: media, counts_toward_session: false }
session_template:                      # состав сессии, сумма = minutes_per_session
  - { activity: <тип>, minutes: <N> }
tutor:
  rubric: <имя рубрики>                # рубрика принадлежит курсу, не ядру
  explanation_language: <политика>
level_check:
  every: quarter                       # периодичность контрольного среза
  day: first_saturday
reminder:
  anchor: after_last_class
  offset_minutes: <N>
  fallback_time: "<HH:MM>"
  latest_start: "<HH:MM>"
```

Узел:

```yaml
- id: <node-id>
  kind: lesson
  unit: <unit-id>
  sessions: <N>                # сколько слотов занимает
  tags: [<...>]
  requires: [<node-id>]
  activities:
    - { type: <тип>, ... }
  done_when: { min_minutes: <N>, activities_passed: all }
```

### 2.2 Типы активностей

Ядро знает набор типов и умеет их исполнять; какие из них использует конкретный курс — дело манифеста.

| Тип | Что делает | Проверка |
|---|---|---|
| `theory` | показывает материал: внешняя ссылка либо объяснение от модели | — |
| `flashcards` | колода интервальных повторений на сегодня | детерминированная |
| `quiz` | закрытые задания | детерминированная |
| `reading` | текст + вопросы | смешанная |
| `listening` | аудио/видео + вопросы | смешанная |
| `writing` | свободный текст | модель по рубрике курса |
| `level_check` | контрольный срез | модель + детерминированная |

Новый тип активности — расширение ядра, а не курса. Курс может комбинировать существующие, но не изобретать свои.

### 2.3 Состояния и очередь

`locked` → `available` → `in_progress` → `done` | `partial`

**Только один узел `available`.** Прямое следствие требования «тему нельзя пролистнуть»: в UI узлы ниже заблокированы, перескочить нельзя.

**Прогресс — очередь, а не календарь.** Узел не привязан к дате; дата вычисляется из позиции в очереди и истории занятий. Планировщик каждое утро берёт голову очереди: `available`, `in_progress` или `partial`.

### 2.4 Rollover

- Узел не завершён к концу дня → остаётся головой очереди. Ничего не пролистывается.
- **Накопленные минуты сохраняются всегда**, независимо от длины перерыва. Сброса при долгом пропуске нет (решено owner). Риск принят: после долгого перерыва накопленные минуты могут не отражать удержанное знание.
- **Отставание** = рабочих дней курса с даты старта − завершённых сессий, минус дни с флагом. Показывается числом, не прячется.
- **Догон** по умолчанию выключен. Опция: дополнительная сессия в нерабочий день курса при отставании выше порога.

### 2.5 Календарь исключений `day_flags`

Owner вносит периоды вручную: диапазон дат + причина. Автоматического источника нет.

- Дни внутри периода **не входят в расчёт отставания** — иначе месяц каникул превращается в месяц фиктивного долга.
- В такие дни не выдаются темы и не ставятся напоминания.
- Период, внесённый **задним числом**, пересчитывает отставание, а не остаётся историческим шрамом.
- Причина `late_classes` проставляется автоматически — см. §4.

### 2.6 Учёт времени

`study_sessions`: `id, course_id, node_id, activity_id, started_at, ended_at, minutes_counted, status`.

Таймер `start / pause / resume / stop`; на паузе минуты не идут. Автопауза: приложение в фоне дольше 2 минут либо отсутствие взаимодействия 5 минут. При обрыве связи клиент буферизует тики и досылает; сервер принимает только монотонно растущие значения — защита и от двойного зачёта, и от накрутки.

**Прогресс курса считается по сессиям**, не по узлам: `сессий_завершено / сессий_всего`, где знаменатель — сумма `sessions` по узлам. Иначе узел на 3 сессии весит столько же, сколько на 1.

Счётчики в UI: минуты за сегодня из нормы сессии, прогресс курса, отдельно **время активностей вне сессии** (то, что в манифесте помечено `counts_toward_session: false`), и график контрольных срезов.

### 2.7 Контрольные срезы

Периодическая независимая проверка уровня — прогресс по узлам измеряет усердие, а не результат. Периодичность и день задаёт манифест.

- Срез **привязан к календарю**, а не к позиции в очереди: уехавший вместе с отставанием срез перестаёт быть периодическим и ломает сопоставимость измерений.
- Ставится на нерабочий день курса, чтобы не прерывать очередь и не увеличивать отставание. При такой постановке исключение из §2.3 не требуется.
- **Не входит ни в счётчик занятий, ни в счётчик внеурочного времени**: это измерение, а не занятие; попадание в любой счётчик искажает обе метрики.
- Дата сдвигается вперёд, если попадает на период `day_flags`.
- Пропущенный срез предлагается в следующий подходящий день, пока не выполнен.
- Результаты — в `level_checks`: дата, оценка по каждому навыку, сводная оценка. Навыки, которые приложение оценить не может, вносятся вручную; при незаполненном поле сводная оценка **не вычисляется**, иначе она систематически завышается.

## 3. Интервальные повторения

Библиотека `fsrs` (py-fsrs). Свой алгоритм не писать.

`vocab_cards`: `id, course_id, term, translation, context, source, fsrs_state (JSON), due_at`.

Три источника карточек:
1. Материал узла — при прохождении темы.
2. Отмеченное пользователем при чтении и просмотре.
3. **Собственные ошибки** из проверенных работ.

Третий источник — ключевой обучающий контур: ошибся → получил карточку → повторил. Не побочный эффект, а причина, по которой подсистема существует.

Лимиты дневной колоды (сколько новых, потолок всего) задаются курсом. Карточка двусторонняя. Контекст обязателен — единица без контекста бесполезна.

## 4. Расчёт времени напоминаний

Джоб, окно 14 дней, ежедневно и при каждом изменении расписания. На каждый рабочий день курса:

1. Взять занятия дня из локальной копии расписания.
2. Есть занятия → `start = конец последнего + offset_minutes`, округлить вверх до 5 минут.
3. Занятий нет → `fallback_time`.
4. **Расчётное начало позже `latest_start` → занятие в этот день не ставится вовсе.** День автоматически помечается `day_flags` причиной `late_classes` и **не входит в отставание**: это следствие расписания университета, а не пропуск по вине owner. Очередь не потребляется, тема выдаётся на следующий рабочий день.
5. Конфликт с существующим событием → сдвиг на длительность сессии, максимум 3 раза, затем `fallback_time` с пометкой конфликта. Упёрлись в `latest_start` → правило п.4.
6. Несколько курсов → сессии подряд без перекрытия, порядок из конфига; последняя не должна вылезти за `latest_start`.
7. Reconcile по `external_key = study:<course_id>:<date>`. Расписание изменилось → **переместить** событие, не создать новое.

Обязательно в тестах: занятий нет; одно занятие; последнее кончается перед самым `latest_start`; последнее кончается после него — напоминания нет, день помечен, отставание не выросло; расписание изменилось после срабатывания напоминания; период `day_flags` внесён задним числом; смена таймзоны.

## 5. Слой моделей

**Конкретные модели назначает owner.** Платформа обязана работать с любым назначением и уметь его сменить без правок кода.

### 5.1 Маршрутизация

`llm.routing` — конфиг вида «задача → провайдер + модель». Точки вызова, которые платформа обязана поддерживать:

| Задача | Профиль требований |
|---|---|
| Закрытые задания | **вызова нет** — детерминированная сверка. Не платить за сравнение строк |
| Генерация карточек, извлечение сущностей | механическая работа по фиксированной схеме, объём большой, требования к качеству низкие |
| Генерация упражнений, подбор материалов | нужно суждение; **не срочно** — кандидат на батч-режим |
| Оценка открытых ответов | нужно суждение, интерактивно |
| Проверка письменных работ по рубрике | качество вывода определяет ценность продукта; интерактивно |
| Контрольный срез | глубокий разбор, редко |
| Разбор фото и текста в событие | vision, короткие ответы |
| Ответы на вопросы пользователя | интерактивно, возможна эскалация на более сильную модель по запросу |

Разные задачи имеют **разные профили**, поэтому одна модель на всё — либо переплата, либо низкое качество там, где оно важно. Профили фиксированы, назначение моделей — нет.

### 5.2 Требования к реализации

- **Смена модели — правка конфига, не деплой.**
- **Каждый вызов в `audit_log`:** провайдер, модель, задача, токены, стоимость.
- **`max_tokens` на каждом типе вызова.** Выход дороже входа у всех провайдеров кратно; неограниченный ответ — самая дорогая покупка.
- **Месячный потолок расходов** с деградацией на дешёвую модель **и уведомлением** — не тихий отказ и не тихий перерасход.
- **Фолбэк:** провайдер недоступен → альтернатива из `llm.routing`, а не ошибка пользователю.
- **Структурированный вывод** через JSON Schema, с валидацией и ретраем при невалидном ответе. Доля ответов, прошедших схему с первого раза, — метрика пригодности модели.
- **Промпты в `prompts/*.md` с версией**, не в строковых литералах. Смена промпта → повторный прогон эталонного набора.
- **Кэш и батч.** Механики скидок у провайдеров различаются принципиально: где-то платно хранение кэша по времени, где-то нет; где-то есть батч-режим, где-то нет. Отсюда: **адаптеры тонкие, но провайдер-специфичные.** Общая абстракция поверх кэша течёт, и течёт молча — счёт вырастает без ошибок в логах. Попадание в кэш проверяется тестом.

### 5.3 Обязательный локальный замер

Публичных бенчмарков на «оценить работу по рубрике» не существует, а общие лидерборды измеряют другое. Поэтому выбор модели для проверки работ owner делает **замером**, а платформа обязана его поддерживать: режим прогона набора эталонных работ через несколько назначенных моделей с отчётом.

Метрики: совпадение с эталонной оценкой; **стабильность повторных прогонов одной и той же работы**; доля ответов, прошедших схему без ретрая. Стабильность важнее средней точности: оценщик, дающий разные результаты на одну работу, делает график срезов бессмысленным.

## 6. Проверка работ

Рубрика **принадлежит курсу**, а не ядру: `tutor.rubric` — поле манифеста, `domain/tutor/` загружает её по имени. Разные курсы проверяются по-разному.

Контракт разбора, единый для любой рубрики:

```json
{
  "verdict": "passed | failed | partial",
  "scores": { "<критерий>": "<оценка>" },
  "overall": "<сводная>",
  "errors": [
    { "span": "…", "type": "…", "correction": "…",
      "explanation": "…", "severity": "high|medium|low", "tag": "…" }
  ],
  "blockers": ["что держит на текущем уровне"],
  "strengths": ["…"],
  "next_focus": ["<node-id>"],
  "new_cards": [{ "term": "…", "context": "…" }]
}
```

Правила, не зависящие от предмета:

- **Строгость выше вежливости.** Спорное не засчитывается как верное, оценка не завышается.
- Объяснение конкретное: что не так, как правильно, почему. «Постарайся лучше» — брак.
- Каждая ошибка `severity: high` порождает карточку или упражнение.
- Повторение одного `tag` несколько раз за период → в очередь вставляется узел `review`.
- `blockers` — отдельное поле не для красоты: ответ на вопрос «что именно мешает вырасти». Без него разбор превращается в список запятых.
- Способ агрегации сводной оценки задаёт рубрика курса, не ядро.

## 7. Подбор материалов

Утренний джоб, до начала учебного дня:

1. Голова очереди → тема дня.
2. Найти материал по тегам узла: приоритет внешним источникам.
3. **Валидация ссылки:** доступность, тип, длительность в допустимом диапазоне, наличие требуемых курсом атрибутов.
4. Отдельно — материал для активностей вне сессии, если курс их объявляет.
5. Проверка по `content_history`: повторно не рекомендуем.
6. Генерация упражнений по теме.
7. Внешнего материала нет → объяснение от модели, **в UI помечено как объяснение ассистента**, а не выдаётся за внешний источник.

`content_items`: `url, kind, title, duration, tags[], attrs (JSON), source, http_status, checked_at`. Кэш переиспользуется между днями и курсами. Политику подбора (какие источники, какие атрибуты обязательны, что чередовать) задаёт манифест курса.

**Только легальные источники.** Ссылки на пиратские ресурсы не выдаём ни при каких настройках курса.

## 8. UI

### 8.1 Навигация

**Вкладки генерируются, а не прописаны в коде.** Первая всегда календарь, далее по одной на каждый установленный курс в порядке из конфига. Хардкод списка вкладок — баг: он ломает требование добавлять и удалять курсы.

**Телефон:** плавающая капсула внизу поверх контента. Иконка над подписью; активная вкладка — скруглённая подложка внутри капсулы и акцентный цвет. Справа отдельная круглая кнопка контекстного действия: на календаре «добавить событие», внутри курса «начать занятие».

**Компьютер:** та же капсула **вертикально, в левом верхнем углу**; подложка активной вкладки съезжает по вертикали. Контент справа.

Общее: переключение вкладки не теряет состояние (вернулся — тот же узел, таймер продолжается); подложка анимируется перемещением; **потолок капсулы — 5 вкладок**, дальше нужен другой паттерн; обе раскладки читают один контракт, различается ориентация.

### 8.2 Змейка

Backend отдаёт плоский массив, вёрстка на клиенте по фиксированной формуле, одинаковой на всех платформах:

```
offset_x(i) = A * sin(2π * i / P)      A ≈ 25% ширины, P = 6
```

```json
{
  "id": "<node-id>", "index": 12, "unit_id": "<unit-id>",
  "kind": "lesson", "title": "…", "state": "available",
  "minutes_accumulated": 15, "activities": ["…"], "icon": "…"
}
```

Разделы отделяются заголовком и цветом. Активный узел — единственный акцент на экране. Пройденные приглушены, заблокированные серые без деталей. Иконки активностей показывают состав. Узлы `level_check` выделены как вехи.

### 8.3 Экран занятия

Пошаговый: активность за активностью, полоса по блокам вверху, таймер. Внутри активности — только она.

После проверки — разбор: оценки по критериям, ошибки с исправлениями, `blockers` отдельным блоком, что уйдёт в карточки, кнопка «спросить репетитора».

### 8.4 Календарь

День и неделя; занятия из университета и сессии курсов визуально различимы; конфликты помечены. Кнопка контекстного действия открывает захват: текст, фото, голос. Отдельный экран — внесение периодов `day_flags`.

## 9. Модульность

**Минимум два курса одновременно** — это архитектурное требование, а не сценарий использования. Ядро не должно знать ни одного названия предмета.

**Установка:** папка `courses/<id>/` с манифестом и программой → `make course-install <id>`, валидация по JSON Schema, заливка в БД.
**Удаление:** `make course-remove <id>` → soft-delete, удаление событий календаря по префиксу `study:<id>:`, вкладка исчезает, история сохраняется.

Валидация обязательна: циклы в `requires`, ссылки на несуществующие узлы, дубли `id`, неизвестные типы активностей, сумма минут шаблона ≠ `minutes_per_session` → отказ с внятной ошибкой.

**Курс без программы допустим.** Есть манифест, программы нет. Обязано работать:
- валидация **пропускает курс с нулём узлов** — это не ошибка;
- вкладка открывается и показывает пустое состояние, а не пустой экран и не падение;
- джобы подбора и напоминаний такой курс пропускают;
- прогресс не делит на ноль.

Через это состояние проходит любой новый курс, поэтому случай тестируемый, а не временный.

**Один пользователь, без мультиарендности.** `user_id` в таблицах не заводим. Настройки owner — одна строка в `settings`, чтобы точка расширения была одна, если решение изменится.

Таблицы ядра, ни одна из которых не знает про конкретный предмет:
`courses`, `course_units`, `course_nodes`, `node_activities`, `node_state`, `study_sessions`, `vocab_cards`, `mistakes`, `submissions`, `level_checks`, `tutor_messages`, `content_items`, `content_history`, `extra_activity_log`, `calendar_events`, `day_flags`, `settings`, `audit_log`, `integration_tokens`.

## 10. Поведение при отказах

Инвариант «деградация вместо падения» запрещает **два** способа обработки отказа и требует третий.

Запрещено: **упасть** (пустой экран, 500, вечный спиннер) и **соврать** — подставить правдоподобное вместо недоступного. Второе опаснее: модель выдумывает охотно и убедительно — сгенерирует ссылку на несуществующее видео, вымышленное расписание, оценку наугад.

Требуется: **показать то, что есть, и явно подписать давность.** Критерий — пользователь в любой момент видит, свежие перед ним данные или нет.

| Отказ | Что делаем | Чего не делаем |
|---|---|---|
| Портал не отвечает, токен истёк | последнее сохранённое расписание + пометка давности | пустой календарь; догадки о занятиях |
| Материал не найден, квота кончилась | занятие с темой и упражнениями, честно «материал не найден» | сгенерированная ссылка: пользователь потеряет время, прежде чем поймёт, что её нет |
| Ссылка была в кэше, видео удалено | пометить статус, исключить, взять следующий вариант | отдать мёртвую ссылку |
| Модель недоступна | фолбэк из `llm.routing`; молчат все — «проверка недоступна, работа сохранена» | оценка наугад; потеря работы |
| Достигнут потолок расходов | деградация на дешёвую модель **с уведомлением** | тихий отказ; тихий перерасход |
| Ошибка записи в календарь | джоб падает громко, состояние помечено рассинхронизированным, следующий прогон делает reconcile | считать, что записалось |
| Формат ответа портала изменился | джоб падает громко | писать разобранный мусор в календарь |

**Фоновые джобы падают громко, интерфейс деградирует тихо.** Джоб некому смотреть в момент запуска, поэтому его отказ должен быть заметен позже; на экран смотрит человек прямо сейчас, ему нужен работающий экран с честной пометкой, а не трассировка стека.

Каждая деградация пишется в `audit_log` — иначе «почему у меня расписание трёхдневной давности» становится неотвечаемым вопросом.

## 11. Восстановление после сбоя

Сервер — домашний Raspberry Pi. Рассчитывать на стопроцентный аптайм нельзя: электричество, сеть, перезагрузка.

### 11.1 Инфраструктура

Настройка хоста, но от неё зависят гарантии приложения.

- **Автоподъём стека:** `docker compose` с `restart: unless-stopped` на каждом контейнере. Проверять после каждого изменения compose-файла.
- **Буфер питания:** UPS или пауэрбанк с passthrough. Гасит секундные моргания, снимает главную причину порчи носителя.
- **Носитель:** USB-SSD надёжнее SD-карты. На карте ночной `pg_dump` в офсайт обязателен.
- **Доступ извне:** Pi за домашним роутером с динамическим адресом, порты наружу не открываем. Фронтенд и телефон вне дома должны дотягиваться до API → **Cloudflare Tunnel**: стабильное HTTPS-имя без проброса портов, плюс валидный сертификат, без которого не работает OAuth-редирект Google.

### 11.2 Приложение

**Догоняющий запуск.** При старте планировщик сверяет `last_run_at` каждого ежедневного джоба с расписанием и догоняет пропущенное **в пределах текущего дня**. Часовое отключение утром → материалы и напоминание появятся позже сегодня, а не пропадут.

**Граница наверстывания.** Вчерашнее напоминание не воскрешаем — оно бессмысленно и мусорит в календаре. Пропуск отражается в отставании курса, а не задним числом в расписании.

**Идемпотентность ужесточается.** Catch-up означает штатный второй запуск джоба за день. Reconcile по `external_key` обязан это выдержать без задвоения. Это тот сценарий, ради которого reconcile, а не «добавить ещё раз».

**Транзакции.** Обрыв посреди записи не должен оставить полуприменённое состояние: логически цельная запись — одна транзакция.

**Heartbeat** во внешний healthcheck: нет сигнала за сутки → письмо owner. Иначе о тихо лежащем сервере узнаёшь, только не увидев напоминания.

## 14. Глоссарий

**Пара** — учебное занятие в университете. **ИСУ / ITMO ID** — аккаунт ИТМО, вход в my.itmo.ru. **Сессия** — один слот занятия внутри курса (не экзаменационная). **Активность** — блок внутри сессии. **Узел (node)** — элемент змейки. **SRS / FSRS** — интервальные повторения. **Rollover** — перенос незавершённого узла на следующий рабочий день курса. **external_key** — идентификатор события в Google Calendar. **day_flags** — периоды, исключённые из учёбы и из расчёта отставания.
