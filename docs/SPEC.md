# SPEC.md — спецификация платформы

Дополняет `CLAUDE.md`. Описывает **приложение**, а не учебные программы.

**Границы документа.** Здесь нет и не должно быть: содержания курсов, тем, уровней, пропорций занятия, лимитов повторений, названий конкретных моделей и их цен. Всё это приходит от owner — программы отдельными файлами курсов, выбор моделей отдельным решением. Задача платформы — исполнить **любую** программу и обратиться к **любой** назначенной модели. Пункты с **[?]** требуют подтверждения owner.

## 1. Roadmap

**Этап 1. Календарный фундамент.** Клиент my.itmo.ru → нормализованные занятия → Google Calendar через reconcile-джоб. Готово, когда: расписание на 2 недели в календаре, джоб запущен трижды без дублей, смена аудитории подхватывается.

**Этап 2. Захват событий.** Текст → фото → голос. Экран подтверждения с первой версии.

**Этап 3. Движок курсов на фикстуре.** Очередь, активности, состояния, rollover, таймер, отставание. Работает на `courses/_fixture/` — синтетический курс из десятка узлов. Без реального контента и без обращений к моделям. Самая важная и самая недооценённая часть: сломанный движок обесценивает любую программу поверх.

**Этап 4. Подсистема интервальных повторений.**

**Этап 5. Автонапоминания.** Расчёт времени, `latest_start`, `day_flags`, разрешение конфликтов.

**Этап 6. Слой моделей.** Маршрутизация по конфигу, учёт стоимости, кэш, фолбэк, структурированный вывод. На заглушках, пока owner не назначит модели.

**Этап 7. Проверка работ.** Контракт разбора, ошибки → карточки.

**Этап 8. Подбор материалов.** Поиск, валидация ссылок, кэш, антиповторы.

**Этап 9. Контрольные срезы.**

**Этап 10. UI.** Вкладки, змейка, экран занятия, календарь.

**Этап 11. Установка реальных программ.** Второй курс обязан встать **без изменений в ядре** — это приёмочный тест на модульность.

**Финансовая книжка (§15) идёт отдельной дорожкой Ф0–Ф8,** а не этапом в этом списке. Причина — независимость: она не пользуется ни движком курсов, ни моделями, ни расписанием портала, и единственная её связь с платформой — вкладка в той же оболочке. Единая нумерация создала бы ложную последовательность там, где её нет. Состояние дорожки — `docs/BUILD-PROGRESS.md`.

## 2. Движок курсов

### 2.1 Модель данных

```
Course → Level → Unit → Node → Activity
```

`Node.kind`: `lesson` | `review` | `checkpoint` | `media` | `level_check`.

**Уровень** — слой между курсом и разделом (ADR-028). Порядок уровней задаёт манифест, раздел объявляет, какому уровню принадлежит. Следующий уровень **закрыт целиком**, пока не завершён предыдущий, и в интерфейсе объясняет условие открытия числом — §8.2. Названий уровней ядро не знает: «B1», «B2» — данные курса, как и остальное содержание.

Единица планирования — **сессия**: один слот занятия. Длительность сессии, дни недели и состав блоков задаёт манифест курса; ядро значений не знает.

Манифест — структура, не содержание:

```yaml
id: <course-id>
title: <название>
levels:                                # порядок уровней; названия — данные курса
  - { id: <level-id>, title: <название> }
schedule:
  days: [mon, tue, wed, thu, fri]     # рабочие дни курса
  minutes_per_session: <N>
  start_date: <YYYY-MM-DD>
  extra:                               # активности сверх сессии, свой счётчик
    weekday_watch: { minutes: <N>, counts_toward_session: false }
    sat: { kind: media, counts_toward_session: false }
session_template:                      # состав сессии, сумма = minutes_per_session
  - { activity: <тип>, minutes: <N> }
tutor:
  rubric: <имя рубрики>                # рубрика принадлежит курсу, не ядру
  explanation_language: <политика>
level_check:
  every: quarter                       # периодичность контрольного среза
  day: first_saturday
reminder:
  anchor: after_last_class
  offset_minutes: <N>
  fallback_time: "<HH:MM>"
  latest_start: "<HH:MM>"
```

Узел:

```yaml
- id: <node-id>
  kind: lesson
  unit: <unit-id>
  sessions: <N>                # сколько слотов занимает
  tags: [<...>]
  requires: [<node-id>]
  activities:
    - { type: <тип>, ... }
  done_when: { min_minutes: <N>, activities_passed: all }
```

### 2.2 Типы активностей

Ядро знает набор типов и умеет их исполнять; какие из них использует конкретный курс — дело манифеста.

| Тип | Что делает | Проверка |
|---|---|---|
| `theory` | показывает материал: внешняя ссылка либо объяснение от модели | — |
| `flashcards` | колода интервальных повторений на сегодня | детерминированная |
| `quiz` | закрытые задания | детерминированная |
| `reading` | текст + вопросы | смешанная |
| `listening` | аудио/видео + вопросы | смешанная |
| `writing` | свободный текст | модель по рубрике курса |
| `level_check` | контрольный срез | модель + детерминированная |

Новый тип активности — расширение ядра, а не курса. Курс может комбинировать существующие, но не изобретать свои.

### 2.3 Состояния и очередь

`locked` → `available` → `in_progress` → `done` | `partial`

**Только один узел `available`.** Прямое следствие требования «тему нельзя пролистнуть»: в UI узлы ниже заблокированы, перескочить нельзя.

**Прогресс — очередь, а не календарь.** Узел не привязан к дате; дата вычисляется из позиции в очереди и истории занятий. Планировщик каждое утро берёт голову очереди: `available`, `in_progress` или `partial`.

### 2.4 Rollover

- Узел не завершён к концу дня → остаётся головой очереди. Ничего не пролистывается.
- **Накопленные минуты сохраняются всегда**, независимо от длины перерыва. Сброса при долгом пропуске нет (решено owner). Риск принят: после долгого перерыва накопленные минуты могут не отражать удержанное знание.
- **Отставание** = рабочих дней курса с даты старта − завершённых сессий, минус дни с флагом. Показывается числом, не прячется.
- **Догон** по умолчанию выключен. Опция: дополнительная сессия в нерабочий день курса при отставании выше порога.

### 2.5 Календарь исключений `day_flags`

Owner вносит периоды вручную: диапазон дат + причина. Автоматического источника нет.

- Дни внутри периода **не входят в расчёт отставания** — иначе месяц каникул превращается в месяц фиктивного долга.
- В такие дни не выдаются темы и не ставятся напоминания.
- Период, внесённый **задним числом**, пересчитывает отставание, а не остаётся историческим шрамом.
- Причина `late_classes` проставляется автоматически — см. §4.

### 2.6 Учёт времени

`study_sessions`: `id, course_id, node_id, activity_id, started_at, ended_at, minutes_counted, status`.

Таймер `start / pause / resume / stop`; на паузе минуты не идут. Автопауза: приложение в фоне дольше 2 минут либо отсутствие взаимодействия 5 минут. При обрыве связи клиент буферизует тики и досылает; сервер принимает только монотонно растущие значения — защита и от двойного зачёта, и от накрутки.

**Прогресс курса считается по сессиям**, не по узлам: `сессий_завершено / сессий_всего`, где знаменатель — сумма `sessions` по узлам. Иначе узел на 3 сессии весит столько же, сколько на 1. Прогресс уровня считается так же, по сумме его разделов.

Счётчики в UI: минуты за сегодня из нормы сессии, прогресс курса, отдельно **время активностей вне сессии** (то, что в манифесте помечено `counts_toward_session: false`), и график контрольных срезов.

### 2.7 Контрольные срезы

Периодическая независимая проверка уровня — прогресс по узлам измеряет усердие, а не результат. Периодичность и день задаёт манифест.

- Срез **привязан к календарю**, а не к позиции в очереди: уехавший вместе с отставанием срез перестаёт быть периодическим и ломает сопоставимость измерений.
- Ставится на нерабочий день курса, чтобы не прерывать очередь и не увеличивать отставание. При такой постановке исключение из §2.3 не требуется.
- **Не входит ни в счётчик занятий, ни в счётчик внеурочного времени**: это измерение, а не занятие; попадание в любой счётчик искажает обе метрики.
- Дата сдвигается вперёд, если попадает на период `day_flags`.
- Пропущенный срез предлагается в следующий подходящий день, пока не выполнен.
- Результаты — в `level_checks`: дата, оценка по каждому навыку, сводная оценка. Навыки, которые приложение оценить не может, вносятся вручную; при незаполненном поле сводная оценка **не вычисляется**, иначе она систематически завышается.

## 3. Интервальные повторения

Библиотека `fsrs` (py-fsrs). Свой алгоритм не писать.

`vocab_cards`: `id, course_id, term, translation, context, source, fsrs_state (JSON), due_at`.

Три источника карточек:
1. Материал узла — при прохождении темы.
2. Отмеченное пользователем при чтении и просмотре.
3. **Собственные ошибки** из проверенных работ.

Третий источник — ключевой обучающий контур: ошибся → получил карточку → повторил. Не побочный эффект, а причина, по которой подсистема существует.

Лимиты дневной колоды (сколько новых, потолок всего) задаются курсом. Карточка двусторонняя. Контекст обязателен — единица без контекста бесполезна.

## 4. Расчёт времени напоминаний

**В календарный релиз не входит — дорожка курсов, ADR-027 п.11.** Всё, чем считается время (`offset_minutes`, `fallback_time`, `latest_start`), приходит из манифеста курса, а курсов установлено ноль. Планировщик, который этот джоб когда-нибудь запустит, сделан на Э5 (§11.2); сам джоб — нет, и `make plan-today` до тех пор честно выходит с ошибкой.

Джоб, окно 14 дней, ежедневно и при каждом изменении расписания. На каждый рабочий день курса:

1. Взять занятия дня из локальной копии расписания.
2. Есть занятия → `start = конец последнего + offset_minutes`, округлить вверх до 5 минут.
3. Занятий нет → `fallback_time`.
4. **Расчётное начало позже `latest_start` → занятие в этот день не ставится вовсе.** День автоматически помечается `day_flags` причиной `late_classes` и **не входит в отставание**: это следствие расписания университета, а не пропуск по вине owner. Очередь не потребляется, тема выдаётся на следующий рабочий день.
5. Конфликт с существующим событием → сдвиг на длительность сессии, максимум 3 раза, затем `fallback_time` с пометкой конфликта. Упёрлись в `latest_start` → правило п.4.
6. Несколько курсов → сессии подряд без перекрытия, порядок из конфига; последняя не должна вылезти за `latest_start`.
7. Reconcile по `external_key = study:<course_id>:<date>`. Расписание изменилось → **переместить** событие, не создать новое.

Обязательно в тестах: занятий нет; одно занятие; последнее кончается перед самым `latest_start`; последнее кончается после него — напоминания нет, день помечен, отставание не выросло; расписание изменилось после срабатывания напоминания; период `day_flags` внесён задним числом; смена таймзоны.

## 5. Слой моделей

**Конкретные модели назначает owner.** Платформа обязана работать с любым назначением и уметь его сменить без правок кода.

### 5.1 Маршрутизация

`llm.routing` — конфиг вида «задача → провайдер + модель». Точки вызова, которые платформа обязана поддерживать:

| Задача | Профиль требований |
|---|---|
| Закрытые задания | **вызова нет** — детерминированная сверка. Не платить за сравнение строк |
| Генерация карточек, извлечение сущностей | механическая работа по фиксированной схеме, объём большой, требования к качеству низкие |
| Генерация упражнений, подбор материалов | нужно суждение; **не срочно** — кандидат на батч-режим |
| Оценка открытых ответов | нужно суждение, интерактивно |
| Проверка письменных работ по рубрике | качество вывода определяет ценность продукта; интерактивно |
| Контрольный срез | глубокий разбор, редко |
| Разбор фото и текста в событие | vision, короткие ответы |
| Расшифровка надиктованного в событие | распознавание речи, короткие ответы; модель с нативным аудио делает это тем же вызовом, что и разбор текста |
| Ответы на вопросы пользователя | интерактивно, возможна эскалация на более сильную модель по запросу |
| Категоризация операции в книжке | механическая работа по фиксированной схеме, объём большой, **не срочно** — кандидат на батч; §15.4 |
| Предложение набора категорий месяца | суждение по истории, редко — раз в месяц; §15.4 |
| Резюме о расходах | суждение, короткий текст, после импорта выписок; §15.9 |

Разные задачи имеют **разные профили**, поэтому одна модель на всё — либо переплата, либо низкое качество там, где оно важно. Профили фиксированы, назначение моделей — нет.

### 5.2 Требования к реализации

- **Смена модели — правка конфига, не деплой.**
- **Каждый вызов в `audit_log`:** провайдер, модель, задача, токены, стоимость.
- **`max_tokens` на каждом типе вызова.** Выход дороже входа у всех провайдеров кратно; неограниченный ответ — самая дорогая покупка.
- **Месячный потолок расходов** с деградацией на дешёвую модель **и уведомлением** — не тихий отказ и не тихий перерасход.
- **Фолбэк:** провайдер недоступен → альтернатива из `llm.routing`, а не ошибка пользователю.
- **Структурированный вывод** через JSON Schema, с валидацией и ретраем при невалидном ответе. Доля ответов, прошедших схему с первого раза, — метрика пригодности модели.
- **Промпты в `prompts/*.md` с версией**, не в строковых литералах. Смена промпта → повторный прогон эталонного набора.
- **Кэш и батч.** Механики скидок у провайдеров различаются принципиально: где-то платно хранение кэша по времени, где-то нет; где-то есть батч-режим, где-то нет. Отсюда: **адаптеры тонкие, но провайдер-специфичные.** Общая абстракция поверх кэша течёт, и течёт молча — счёт вырастает без ошибок в логах. Попадание в кэш проверяется тестом.

### 5.3 Обязательный локальный замер

Публичных бенчмарков на «оценить работу по рубрике» не существует, а общие лидерборды измеряют другое. Поэтому выбор модели для проверки работ owner делает **замером**, а платформа обязана его поддерживать: режим прогона набора эталонных работ через несколько назначенных моделей с отчётом.

Метрики: совпадение с эталонной оценкой; **стабильность повторных прогонов одной и той же работы**; доля ответов, прошедших схему без ретрая. Стабильность важнее средней точности: оценщик, дающий разные результаты на одну работу, делает график срезов бессмысленным.

## 6. Проверка работ

Рубрика **принадлежит курсу**, а не ядру: `tutor.rubric` — поле манифеста, `domain/tutor/` загружает её по имени. Разные курсы проверяются по-разному.

Контракт разбора, единый для любой рубрики:

```json
{
  "verdict": "passed | failed | partial",
  "scores": { "<критерий>": "<оценка>" },
  "overall": "<сводная>",
  "errors": [
    { "span": "…", "type": "…", "correction": "…",
      "explanation": "…", "severity": "high|medium|low", "tag": "…" }
  ],
  "blockers": ["что держит на текущем уровне"],
  "strengths": ["…"],
  "next_focus": ["<node-id>"],
  "new_cards": [{ "term": "…", "context": "…" }]
}
```

Правила, не зависящие от предмета:

- **Строгость выше вежливости.** Спорное не засчитывается как верное, оценка не завышается.
- Объяснение конкретное: что не так, как правильно, почему. «Постарайся лучше» — брак.
- Каждая ошибка `severity: high` порождает карточку или упражнение.
- Повторение одного `tag` несколько раз за период → в очередь вставляется узел `review`.
- `blockers` — отдельное поле не для красоты: ответ на вопрос «что именно мешает вырасти». Без него разбор превращается в список запятых.
- Способ агрегации сводной оценки задаёт рубрика курса, не ядро.

## 7. Подбор материалов

Утренний джоб, до начала учебного дня:

1. Голова очереди → тема дня.
2. Найти материал по тегам узла: приоритет внешним источникам.
3. **Валидация ссылки:** доступность, тип, длительность в допустимом диапазоне, наличие требуемых курсом атрибутов.
4. Отдельно — материал для активностей вне сессии, если курс их объявляет.
5. Проверка по `content_history`: повторно не рекомендуем.
6. Генерация упражнений по теме.
7. Внешнего материала нет → объяснение от модели, **в UI помечено как объяснение ассистента**, а не выдаётся за внешний источник.

`content_items`: `url, kind, title, duration, tags[], attrs (JSON), source, http_status, checked_at`. Кэш переиспользуется между днями и курсами. Политику подбора (какие источники, какие атрибуты обязательны, что чередовать) задаёт манифест курса.

**Только легальные источники.** Ссылки на пиратские ресурсы не выдаём ни при каких настройках курса.

## 8. UI

### 8.1 Навигация

**Вкладки генерируются, а не прописаны в коде.** Первая всегда календарь, далее по одной на каждый установленный курс в порядке из конфига. Хардкод списка вкладок — баг: он ломает требование добавлять и удалять курсы.

**Телефон:** плавающая капсула внизу поверх контента. Иконка над подписью; активная вкладка — скруглённая подложка внутри капсулы и акцентный цвет. Справа отдельная круглая кнопка контекстного действия: на календаре «добавить событие», внутри курса «начать занятие».

**Компьютер:** та же капсула **вертикально, в левом верхнем углу**; подложка активной вкладки съезжает по вертикали. Контент справа.

Общее: переключение вкладки не теряет состояние (вернулся — тот же узел, таймер продолжается); подложка анимируется перемещением; **потолок капсулы — 5 вкладок**, дальше нужен другой паттерн; обе раскладки читают один контракт, различается ориентация.

### 8.2 Змейка

Backend отдаёт плоский массив, вёрстка на клиенте по фиксированной формуле, одинаковой на всех платформах:

```
offset_x(i) = A * sin(2π * i / P)      A ≈ 25% ширины дорожки, P = 6
```

Дорожка — колонка ограниченной ширины по центру области, а не вся область. На всю ширину экрана та же амплитуда разносит соседние узлы так, что очередь перестаёт читаться как очередь — замерено на макете этапа 4 дизайна.

```json
{
  "id": "<node-id>", "index": 12, "level_id": "<level-id>", "unit_id": "<unit-id>",
  "kind": "lesson", "title": "…", "state": "available", "sessions": 1,
  "minutes_accumulated": 15, "activities": ["…"], "icon": "…"
}
```

**Состояние узла кодируется цветом** — ADR-029: пройденный салатовый, голова очереди фиолетовая, заблокированный серый. Больше цвета на экране нет: он закреплён за состоянием, и цветная плашка раздела или среза читалась бы как ещё один узел очереди.

**Заблокированный узел — без деталей:** ни состава активностей, ни минут. Число сессий при этом показано: оно отвечает не «что внутри», а «когда до этого дойдёт дело».

**В захвате 3–4 узла**, при открытии дорожка прокручена к активному узлу; прокрутка до любого места змейки доступна. Скроллится дорожка, а не экран: капсула и шапка курса остаются на месте.

**Разделы отделяются заголовком и линией, уровни — заголовком крупнее и прогрессом в сессиях.** Закрытый уровень объясняет условие открытия числом, а не просто гаснет.

**Соединительная линия идёт только по пройденному пути,** заканчивается на активном узле и имеет цвет пройденного узла. Линия — кривая с вертикальными касательными на концах: изломов на узлах нет.

Иконки активностей показывают состав. Узел `level_check` — плашка во всю ширину дорожки, с датой: срез привязан к календарю (§2.7), а не к позиции в очереди, и единственный из узлов дату имеет.

### 8.3 Экран занятия

Пошаговый: активность за активностью, полоса по блокам вверху, таймер. Внутри активности — только она.

После проверки — разбор: оценки по критериям, ошибки с исправлениями, `blockers` отдельным блоком, что уйдёт в карточки, кнопка «спросить репетитора».

### 8.4 Календарь

День и неделя; занятия из университета и сессии курсов визуально различимы; конфликты помечены. Кнопка контекстного действия открывает захват: текст, фото, голос. Отдельный экран — внесение периодов `day_flags`.

## 9. Модульность

**Минимум два курса одновременно** — это архитектурное требование, а не сценарий использования. Ядро не должно знать ни одного названия предмета.

**Установка:** папка `courses/<id>/` с манифестом и программой → `make course-install <id>`, валидация по JSON Schema, заливка в БД.
**Удаление:** `make course-remove <id>` → soft-delete, удаление событий календаря по префиксу `study:<id>:`, вкладка исчезает, история сохраняется.

Валидация обязательна: циклы в `requires`, ссылки на несуществующие узлы, дубли `id`, неизвестные типы активностей, сумма минут шаблона ≠ `minutes_per_session` → отказ с внятной ошибкой.

**Курс без программы допустим.** Есть манифест, программы нет. Обязано работать:
- валидация **пропускает курс с нулём узлов** — это не ошибка;
- вкладка открывается и показывает пустое состояние, а не пустой экран и не падение;
- джобы подбора и напоминаний такой курс пропускают;
- прогресс не делит на ноль.

Через это состояние проходит любой новый курс, поэтому случай тестируемый, а не временный.

**Один пользователь, без мультиарендности.** `user_id` в таблицах не заводим. Настройки owner — одна строка в `settings`, чтобы точка расширения была одна, если решение изменится.

Таблицы ядра, ни одна из которых не знает про конкретный предмет:
`courses`, `course_units`, `course_nodes`, `node_activities`, `node_state`, `study_sessions`, `vocab_cards`, `mistakes`, `submissions`, `level_checks`, `tutor_messages`, `content_items`, `content_history`, `extra_activity_log`, `itmo_lessons`, `calendar_events`, `day_flags`, `settings`, `audit_log`, `integration_tokens`, `job_runs`, `capture_drafts`, `capture_blobs`.

`job_runs` хранит факт «джоб отработал сегодня» — без него catch-up (§11.2) не работает, потому что расписание APScheduler пересоздаётся при каждом старте.

`itmo_lessons` — зеркало расписания портала: то, что my.itmo.ru отдал в последний успешный забор, с временем этого забора. Отдельно от `calendar_events` намеренно: первое — желаемое состояние из источника, второе — журнал того, что записано в Google. В одной таблице «пара исчезла из расписания» и «запись в календарь не удалась» были бы одним состоянием строки, а reconcile (§11.2) обязан их различать. Пометка давности на экране календаря (§10) берётся из `fetched_at` этого зеркала.

`capture_drafts` и `capture_blobs` живут от загрузки до подтверждения или отмены черновика и удаляются вместе с ним, в одной транзакции с созданием события. Сырьё вынесено в отдельную таблицу, чтобы выборка списка черновиков не читала `bytea`. Черновик, к которому не вернулись, удаляется джобом по сроку из конфига.

**Схема заводится по частям.** Первый релиз — календарь без курсов (ADR-019 с поправкой ADR-020), поэтому схема v1 (этап Э2) содержит девять таблиц: `settings`, `integration_tokens`, `itmo_lessons`, `calendar_events`, `day_flags`, `audit_log`, `job_runs`, `capture_drafts`, `capture_blobs`. Курсовые таблицы появляются вместе с движком курсов: их поля выводятся из манифеста курса, и спроектированные до него они были бы догадкой, которую всё равно пришлось бы переделывать.

## 10. Поведение при отказах

Инвариант «деградация вместо падения» запрещает **два** способа обработки отказа и требует третий.

Запрещено: **упасть** (пустой экран, 500, вечный спиннер) и **соврать** — подставить правдоподобное вместо недоступного. Второе опаснее: модель выдумывает охотно и убедительно — сгенерирует ссылку на несуществующее видео, вымышленное расписание, оценку наугад.

Требуется: **показать то, что есть, и явно подписать давность.** Критерий — пользователь в любой момент видит, свежие перед ним данные или нет.

| Отказ | Что делаем | Чего не делаем |
|---|---|---|
| Портал не отвечает, токен истёк | последнее сохранённое расписание + пометка давности | пустой календарь; догадки о занятиях |
| Материал не найден, квота кончилась | занятие с темой и упражнениями, честно «материал не найден» | сгенерированная ссылка: пользователь потеряет время, прежде чем поймёт, что её нет |
| Ссылка была в кэше, видео удалено | пометить статус, исключить, взять следующий вариант | отдать мёртвую ссылку |
| Модель недоступна | фолбэк из `llm.routing`; молчат все — «проверка недоступна, работа сохранена» | оценка наугад; потеря работы |
| Достигнут потолок расходов | деградация на дешёвую модель **с уведомлением** | тихий отказ; тихий перерасход |
| Ошибка записи в календарь | джоб падает громко, состояние помечено рассинхронизированным, следующий прогон делает reconcile | считать, что записалось |
| Формат ответа портала изменился | джоб падает громко | писать разобранный мусор в календарь |

**Фоновые джобы падают громко, интерфейс деградирует тихо.** Джоб некому смотреть в момент запуска, поэтому его отказ должен быть заметен позже; на экран смотрит человек прямо сейчас, ему нужен работающий экран с честной пометкой, а не трассировка стека.

**«Громко» зависит от того, кто джоб запустил.** У прогона из командной строки это ненулевой код возврата. У того же джоба, запущенного планировщиком внутри живого процесса (§11.2), кода возврата нет вовсе — завершаться нечему, — и громкость складывается из трёх следов: строка `failed` в `job_runs`, запись в `audit_log` и ERROR в логе процесса. Все три обязательны: первые два молчат при отказе самой базы, а третий пропадает, если логирование в процессе никто не настроил.

Каждая деградация пишется в `audit_log` — иначе «почему у меня расписание трёхдневной давности» становится неотвечаемым вопросом.

### 10.1 Забор расписания my.itmo.ru

Реализовано на этапе Э3, развилки — ADR-022. Здесь только наблюдаемое поведение.

**Вход.** Authorization Code + PKCE с эмуляцией формы Keycloak — password grant у ITMO ID нет. Порядок попыток: сохранённый access-токен → refresh-токен → пароль. Пароль лежит в `integration_tokens` шифротекстом, ключ (`ISU_CRED_KEY`) только в env.

**Окно.** Неделя назад и месяц вперёд от текущего дня, границы в конфиге. Назад — чтобы пара, перенесённая задним числом, исчезла из календаря, а не осталась в нём навсегда.

**Окно заменяется целиком, и только окно.** Пара, исчезнувшая из расписания портала, исчезает и из `itmo_lessons` — иначе reconcile (§11.2) никогда не удалит её из Google. Строки вне окна не трогаются: прошлогоднее занятие — история, по которой считается отставание.

**`fetched_at` обновляется у всех строк окна, включая неизменившиеся.** Он отвечает на вопрос «насколько свежи данные», а не «когда эта пара менялась»: пара, не менявшаяся месяц, всё равно подтверждена сегодняшним ответом портала.

**Отказ портала зеркало не трогает.** Ни строки не удаляется, `fetched_at` остаётся прежним — на нём держится пометка давности на экране календаря. Джоб при этом падает громко: ненулевой код возврата, запись в `audit_log`, отметка `failed` в `job_runs`.

**Отказ портала приходит внутри тела, а не кодом HTTP.** Рядом с `data` лежат `code` и `message`; на успехе `code = 0`. Ответ вида `{"code": 500, "message": "…", "data": []}` приходит с HTTP 200 и без проверки `code` неотличим от каникул — то есть стирает окно зеркала целиком. Каникулы и отказ сервиса различает только это поле. Отсутствие `code` считается успехом: поле неофициальное, как и вся схема, и его исчезновение не повод отказываться от расписания, которое портал всё-таки отдал.

**Три вида отказа различаются по реакции.** Недоступность портала — повтор с нарастающей паузой, потом деградация на сохранённое зеркало. Изменившийся формат ответа — отказ без повторов: тот же запрос вернёт тот же нечитаемый ответ. `401` на действующий по нашим часам токен — сброс токена и вход заново на следующей попытке.

**Формат занятия не достраивается.** У портала есть поле `format` со своими словами («Очный», «Очно - дистанционный»), и берётся именно оно. Ссылка на Zoom — запасной признак на случай, если поля не будет; нет ни того, ни другого — пусто. «Очно» на основании отсутствия ссылки не пишется.

**`make sync-itmo` по умолчанию dry-run:** показывает дифф к зеркалу и не пишет ничего, кроме токенов, добытых входом. Токены — плата за доступ, а не результат работы; выбрасывать их значило бы входить паролем на каждый ручной прогон. Запись зеркала — `make sync-itmo-apply`.

### 10.2 Запись в Google Calendar

Реализовано на этапе Э4, развилки — ADR-026. Здесь только наблюдаемое поведение.

**Доступ — service account** (ADR-019). Он создаёт три календаря JARVIS и расшаривает их owner ролью `owner`; в Google Calendar owner они видны как обычные. Создание — отдельная команда `make gcal-setup-apply`, а не побочный эффект ежедневного джоба. Идентификаторы календарей живут в `settings`, а не в env: это результат работы, и он обязан вернуться вместе с базой, восстановленной из дампа.

**Синхронизация односторонняя.** Мы пишем, Google хранит. Правка события руками в Google в базу не возвращается и будет перезаписана следующим прогоном; удаление руками приводит к тому, что событие создаётся заново.

**Окно записи совпадает с окном забора** — неделя назад и месяц вперёд. Одно окно на обе операции, из одного места в коде: две границы, живущие по отдельности, расходятся молча, и пара с края окна начинает то появляться, то исчезать.

**Решение по каждому событию принимается по трём источникам:** зеркало `itmo_lessons` (что должно быть), журнал `calendar_events` (что мы писали) и выдача Google (что там лежит сейчас). Событие не трогается, только если оно есть в Google **и** его `content_hash` совпадает с журналом. Отсюда следуют два обычных случая, которые обязаны переживаться без задвоения: база восстановлена из дампа (журнал пуст, календарь полон) и событие удалено в Google руками (журнал говорит `synced`, события нет).

**Ключ живёт в самом событии.** `external_key` = `source_key` пары, он же лежит в `extendedProperties.private.jarvis_key`. Без него события в чужой системе не с чем сопоставить, и первый прогон после restore создал бы вторую копию семестра. События без нашего ключа джоб не трогает вовсе.

**Событие переписывается целиком** (`update`, не `patch`): поле, исчезнувшее в источнике — пропала аудитория, — обязано исчезнуть и в календаре.

**Единица цельности — одно событие, а не прогон.** Запись в Google и строка журнала о ней коммитятся вместе, сразу; откат всего окна невозможен, потому что записанное в чужую систему не откатывается, а журнал, «забывший» про уже созданные события, приводит к их задвоению на следующем прогоне.

**Отказ по одному событию не останавливает остальные:** строка помечается `sync_state = failed` с причиной, прогон продолжается, следующий прогон её дописывает. Джоб при этом возвращает ненулевой код и пишет `failed` в `job_runs` — фоновому джобу некому смотреть в глаза в момент запуска. **Отказ доступа** (`401`, `403`, недоступность, отозванный ключ) прекращает прогон целиком: следующие восемьдесят событий получат тот же ответ. **404 отказом не считается** — так выглядит удалённое руками событие.

**Пустое зеркало означает пустой календарь,** и второй защиты здесь нет намеренно: отличать каникулы от отказа портала — работа забора (§10.1, поле `code`). Оговорка на этом уровне сделала бы неудаляемой пару, которая действительно исчезла из расписания.

**`make sync-gcal` по умолчанию dry-run:** показывает, что будет создано, обновлено и удалено, и не пишет ни в Google, ни в базу — включая `audit_log` и `job_runs`. Исключений, как с токенами на Э3, здесь нет. Запись — `make sync-gcal-apply`.

## 11. Восстановление после сбоя

Сервер — домашний Raspberry Pi. Рассчитывать на стопроцентный аптайм нельзя: электричество, сеть, перезагрузка.

### 11.1 Инфраструктура

Настройка хоста, но от неё зависят гарантии приложения.

- **Автоподъём стека:** `docker compose` с `restart: unless-stopped` на каждом контейнере. Проверять после каждого изменения compose-файла.
- **Буфер питания:** UPS или пауэрбанк с passthrough. Гасит секундные моргания, снимает главную причину порчи носителя.
- **Состав стека:** API, Postgres и статический фронтенд живут на одном Pi, одним `docker-compose.yml` (ADR-020). Отдельного хостинга фронтенда нет.
- **Носитель:** USB-SSD надёжнее SD-карты. Смертны оба, поэтому офсайт-копия обязательна независимо от типа носителя.
- **Бэкап:** ночной `pg_dump -Fc` на SSD (7 копий) и выгрузка в **Backblaze B2**, глубина 7 ежедневных / 4 недельных / 6 месячных. Ключ доступа — только на запись, без удаления; ретеншн правилами на стороне B2, чтобы сбой или компрометация Pi не стёрли историю копий. Ping в healthchecks.io шлётся **после** успешной выгрузки, а не после запуска джоба. Раз в месяц — restore-тест: развернуть последний дамп в пустую базу и сверить состав таблиц. Дампы не шифруются, риск принят и очерчен в ADR-020.
- **Доступ извне:** Pi за домашним роутером с динамическим адресом, порты наружу не открываем. Телефон вне дома и сам фронтенд должны дотягиваться до API → **Cloudflare Tunnel**: стабильное HTTPS-имя без проброса портов. OAuth-редирект здесь больше ни при чём: доступ к Google Calendar идёт через service account (ADR-019), туннель нужен ради доступа, а не ради сертификата для редиректа.

### 11.2 Приложение

Реализовано на этапе Э5, развилки — ADR-027. Здесь только наблюдаемое поведение.

**Что запускается.** Одна ежедневная цепочка `daily_calendar`: забор расписания (§10.1), затем запись в Google (§10.2). Шаги идут строго в этом порядке — реконсил по зеркалу, которое забор не обновил, уехал бы по вчерашним данным.

**Когда.** Шесть раз в день по зоне owner, каждые три часа с 06:30 до 21:30; времена в конфиге (`SCHEDULER_DAILY_TIMES`). Не один утренний прогон: расписание портала меняется задним числом, и узнать об этом можно только опросом.

**Рубильник.** `SCHEDULER_ENABLED`, по умолчанию включён. Выключен там, где автоматический прогон вреден: на машине разработки. Выключенный планировщик означает, что джобы запускаются только целями `make`.

**Догоняющий запуск.** При старте процесс проверяет `job_runs` и догоняет пропущенное **в пределах текущего дня**. Часовое отключение утром → расписание доедет до календаря позже сегодня, а не пропадёт. Условий три, и все обязательны: первый слот дня уже прошёл; успешного прогона за сегодня нет; последняя попытка за сегодня остыла (`SCHEDULER_CATCHUP_COOLDOWN_MINUTES`).

Последнее условие — не про параллельные прогоны, их быть не может: процесс один, воркер один. Оно про цикл перезапуска контейнера, который иначе означал бы вход в ИСУ на каждый рестарт.

**Граница наверстывания.** Вчерашний прогон не воскрешаем — вчерашнее напоминание бессмысленно и мусорит в календаре. Пропуск отражается в отставании курса, а не задним числом в расписании.

**Идемпотентность ужесточается.** Catch-up означает штатный второй запуск джоба за день. Reconcile по `external_key` обязан это выдержать без задвоения. Это тот сценарий, ради которого reconcile, а не «добавить ещё раз».

**Отказ шага не отменяет следующий.** Портал не ответил — зеркало осталось прежним (§10.1), и реконсил Google по нему всё равно полезен: он чинит событие, удалённое в календаре руками. Цепочка при этом считается неуспешной.

**След в `job_runs` — три строки за день:** одна на цепочку и по одной на шаг. Строка цепочки существует ради отказов, не принадлежащих ни одному шагу: неизвестная зона в настройках, обрыв базы между шагами, отказ построителя транспорта. Без неё такой отказ неотличим от «процесс вообще не стартовал».

**Транзакции.** Обрыв посреди записи не должен оставить полуприменённое состояние: логически цельная запись — одна транзакция. Отметка о начале прогона коммитится до первого шага: процесс, убитый посреди работы, обязан оставить след, а не исчезнуть бесследно.

**Триггера два: планировщик и catch-up при старте.** Runner один и тот же. Внешнего тика нет — контейнер на Pi не засыпает, и `POST /internal/jobs/tick` из плана бесплатного этапа не реализуется вовсе (ADR-020). Ручной прогон делается целями `make daily` и `make sync-itmo` на самом хосте, отдельного эндпоинта с секретом для этого не заводим — лишняя дверь наружу.

**Расписание пересоздаётся при каждом старте процесса** и живёт только в памяти: единственная память о прогонах — таблица `job_runs`. Практическое следствие: смена `settings.timezone` применяется после перезапуска контейнера, а не сама собой.

**Планировщик живёт в процессе API в одном экземпляре.** Второй воркер uvicorn означал бы второй планировщик и два параллельных реконсила в один календарь, поэтому `--workers` в образе нет.

**Heartbeat** во внешний healthcheck: нет сигнала за сутки → письмо owner. Иначе о тихо лежащем сервере узнаёшь, только не увидев напоминания. Реализуется на Э9 вместе с остальной живучестью.

## 15. Финансовая книжка

Личный учёт расходов и доходов. К учёбе отношения не имеет и в движок курсов не входит: это третья часть продукта наравне с календарём и курсами. Раздел стоит последним, а не по смыслу рядом с §2, чтобы не перенумеровывать существующие ссылки на §9–§11.

**Что делает:** принимает CSV-выписки нескольких банков, ведёт список операций, раскладывает их по категориям owner — детерминированными правилами, а непокрытое моделью, — показывает сальдо месяца, «Отложено» и «Осталось» накопленным итогом и после каждого импорта даёт короткое резюме о тратах.

### 15.1 Источники данных

**Канал один — CSV-выписка, выгружаемая owner вручную примерно раз в неделю** (ADR-024). **Банков при этом несколько** (ADR-030): за один заход приезжает не один файл, а по одному с каждого банка. Автоматического канала нет и не планируется: официального API для физлиц у банков нет, а на iOS стороннее приложение не может читать чужие push-уведомления.

Прямое следствие, которое обязано быть видно на экране: **книжка актуальна на момент последней загрузки, а не на момент покупки.** Требование «обновляется само после покупки» этим каналом не выполняется — вместо него §10 требует явной пометки давности: «операции по 5 сентября, загружено 3 дня назад». Давность считается **по самому старому из банков**: один загруженный вчера файл не делает свежими остальные.

**Парсер — реестр адаптеров, по одному на банк** (ADR-030). Ядро импорта банка не знает: адаптер отдаёт нормализованные строки, дальше сверка и хранение работают одинаково для всех.

**Банк определяется по заголовку файла,** а не по имени файла и не выбором owner. Заголовок и так сверяется на каждом импорте, а имя файла переименовывается. **Не узнал ни один адаптер — файл отклонён целиком** с перечислением пришедших колонок; частичный импорт запрещён, как и при изменившемся формате.

**Формат каждого банка фиксируется по настоящей выгрузке, а не по предположению.** Ниже — формат первого адаптера, Т-Банка, зафиксированный по выгрузке за август 2026 (62 операции, получена от owner 2026-09-05). Формат остальных банков — входные данные от owner: пока файла нет, адаптера нет, и выдуманных колонок в схеме тоже нет.

**Т-Банк.** Кодировка **UTF-8 без BOM** — распространённое ожидание `windows-1251` здесь неверно и было бы дорогой ошибкой: файл не упал бы, а дал бы кракозябры в названиях мерчантов. Разделитель `;`, **все** поля в двойных кавычках, переводы строк CRLF, дата `dd.MM.yyyy HH:mm:ss` во времени owner, десятичная запятая, расход со знаком минус.

Семнадцать колонок в этом порядке:

| # | Колонка | Что в ней | Как используется |
|---|---|---|---|
| 1 | Имя счёта | `Black`, `Накопительный счёт` | `account`, плюс роль счёта (§15.5) |
| 2 | Номер карты | `*3417` либо пусто — пусто у 25 операций из 62 | `card_last4`, необязательное |
| 3 | Дата операции | `31.08.2026 13:36:02` | `occurred_at`, зона owner → UTC |
| 4 | Сумма операции | `-330,00` | `amount` |
| 5 | Валюта операции | `RUB` | `currency` |
| 6 | Сумма в валюте счёта | при рублёвом счёте равна колонке 4 | `amount_rub` |
| 7 | Валюта счёта | `RUB` | — |
| 8 | Статус | `Ок` | `status` |
| 9 | Категория по-умолчанию | категория банка | подсказка для разбора |
| 10 | Ваша категория | категория, выставленная owner в приложении банка | подсказка сильнее колонки 9 |
| 11 | MCC | `5814`; пусто у переводов и процентов — 18 из 62 | подсказка слабее колонок 9 и 10 |
| 12 | Описание | мерчант либо имя человека при переводе | `merchant` |
| 13 | Сообщение | комментарий к переводу | `note` |
| 14 | Округление | в выгрузке нули | не используется |
| 15 | Сумма операции с округлением | в выгрузке равна колонке 4 | не используется |
| 16 | Бонусы (включая кэшбэк) | в выгрузке нули | не используется в v1 |
| 17 | Учёт в аналитике | `Да` | подсказка для `excluded` |

**Даты платежа в выгрузке нет** — только дата операции. Поэтому момент проведения из файла не берётся и в модели не хранится: колонки, которой нет в источнике, в схеме быть не должно.

**Известно одно значение статуса — `Ок`.** Как банк пишет ожидающую и отклонённую операцию, из этого файла не видно, а выдумывать написание запрещено. Парсер принимает известное значение и **падает на незнакомом**, называя его: тогда owner присылает выгрузку с таким случаем, и значение добавляется по факту. Это дешевле, чем угадать и молча пропустить неудавшийся платёж как состоявшийся расход.

**Схема выгрузки неофициальная,** ровно как у my.itmo.ru: банк вправе изменить состав колонок без предупреждения. Поэтому парсер сверяет заголовок с ожидаемым и при расхождении **отклоняет файл целиком с указанием колонки**. Частичный импорт запрещён: молча пропущенная колонка суммы даёт правдоподобную, но неверную книжку — худший из отказов по §10.

**Ручной ввод операции обязателен с первого дня.** Наличные, перевод с рук на руки, покупка не с карты, которой нет ни в одной выписке — всё, чего в файлах не будет. Без ручного ввода сальдо расходится с реальностью тихо, и обнаруживается это через месяцы.

### 15.2 Модель данных

Шесть таблиц, все с префиксом `fin_` — иначе `transactions` и `categories` в общей схеме читаются как что-то платформенное, а не как одна подсистема:

- **`fin_imports`** — факт загрузки файла: **банк**, имя, SHA-256 содержимого, период выгрузки, время импорта, число добавленных, обновлённых и пропущенных строк. Хэш даёт идемпотентность: тот же файл второй раз меняет ноль строк.
- **`fin_transactions`** — операции. Ключевое: **`bank`**, `occurred_at` (tz-aware, в UTC), `account`, `amount` и `currency`, `amount_rub`, `merchant`, `bank_category`, `own_category`, `mcc`, `card_last4`, `message`, `analytics_hint`, `status`, `kind`, `category_id`, **`offsets_transaction_id`**, `note`, `excluded`, `fingerprint`, `occurrence_no`, `import_id`, `source_row` (jsonb — исходная строка CSV целиком), `entered_manually`. Даты проведения нет, потому что её нет в источнике (§15.1).
- **`fin_accounts`** — свои счета: банк, имя счёта, роль (`checking`, `savings`, `unknown`). Нужна для статьи «Отложено» и для признака перевода между своими счетами (§15.5).
- **`fin_categories`** — категории owner, **версией на месяц**: стабильный ключ, месяц, родитель, отображаемое имя, происхождение (`owner` или `ai`) и статус (`active`, `proposed`, `rejected`). Данные, не код: ядро не знает ни одного названия категории, как не знает названий предметов (инвариант 2).
- **`fin_category_rules`** — правила разбора: по мерчанту, по банковской категории, по MCC и **по отправителю перевода** (§15.5). Последний тип определяет не категорию, а `kind`: родные → `income`, прочие → `refund`. Правило ссылается на **ключ** категории, а не на строку месяца, — иначе с наступлением нового месяца все правила осиротели бы.
- **`fin_summaries`** — резюме после импорта (§15.9): период, текст, снимок чисел, с которыми сравнивали, провайдер, модель, токены и стоимость.

**Деньги — `numeric`, никогда `float`.** Двоичная дробь не представляет 0.1 точно, и на горизонте года копейки расходятся в рубли. В Python — `Decimal`, в схеме — `numeric(12,2)`. Это инвариант того же уровня, что tz-aware время.

**`status`** — состояние операции в банке. Известное из выгрузки Т-Банка значение одно, `Ок` → `posted`; `pending` и `reverted` заведены, потому что нужны логике сверки (§15.3), но их написание в файле пока неизвестно и подставляется не догадкой, а по первой выгрузке, где они встретятся.
**`kind`** — роль в сальдо: `expense`, `income`, `transfer` (между своими счетами owner), `refund` (возврат либо доля, скинутая за общую покупку). Разделение обязательно: перевод на свой накопительный счёт — не расход, возврат товара — не доход.

**`kind` не выводится из категории банка.** В выгрузке категория «Переводы» покрывает 17 операций: 14 входящих и 3 исходящих, все — переводы людям, ни одна не движение между счетами owner. Правило «категория Переводы значит transfer» дало бы неверное сальдо на четверти операций месяца. Признак настоящего `transfer` — **пара строк**: списание с одного счёта owner и зачисление на другой той же суммой примерно в то же время, причём оба счёта размечены в `fin_accounts`. С несколькими банками пара приезжает двумя файлами, и без явного списка своих счетов «перевод себе» неотличим от перевода человеку.

**Сырьё хранится в самой операции** (`source_row`), а не в отдельной таблице. Отличие от `capture_blobs`: там `bytea` фотографии, из-за которого выборка списка читала бы мегабайты; здесь строка CSV весит сотни байт, и отдельная таблица дала бы связь один-к-одному без выигрыша. Хранится ради разбора расхождений: «почему эта операция попала в такую категорию» без исходной строки неотвечаемо.

### 15.3 Импорт и сверка

**Две фазы: `--dry-run` показывает дифф, `--apply` записывает.** Правило `CLAUDE.md` про dry-run написано для записей наружу, здесь запись внутрь своей базы — но фаза сохраняется по другой причине: она и есть подтверждение owner. Правило «без подтверждения не писать» соблюдается на уровне файла, а не каждой операции; поштучное подтверждение сотни строк выписки бессмысленно.

**За один заход импортируется несколько файлов** — по одному с каждого банка. Каждый учитывается своей строкой `fin_imports`, дифф показывается по каждому отдельно, и отказ на одном файле не отменяет остальные: банк, сменивший формат, не должен блокировать учёт по другим.

Дифф показывает: сколько новых, сколько уже есть, сколько обновится (изменилась сумма или статус), сколько ушло в разбор.

**Дедупликация — по кратности, а не по факту.** Выгрузки за перекрывающиеся периоды — норма (owner выгружает месяц, чтобы не потерять дни на стыке), поэтому одна и та же операция придёт много раз. В CSV нет идентификатора операции, поэтому ключ собирается из полей: `fingerprint` = хэш от **банка**, даты, суммы, валюты, описания и последних цифр карты.

**Банк в ключе обязателен** (ADR-030): без него две покупки на одну сумму в один день из двух разных банков попали бы в одну группу кратности, и правило «добавить разницу» добавило бы ноль строк.

**Проверено на настоящей выгрузке:** полных совпадений ключа за месяц нет ни одного, потому что дата операции содержит время до секунды. Но совпадений по дню, сумме и описанию — два: две оплаты `OOO Leon` по 575 ₽ 23 августа (15:13:33 и 15:13:53) и два билета `Яндекс Расписания` по 65 ₽ 2 августа. То есть **секунды и есть единственное, что их различает**, и выбрасывать время из ключа нельзя ни при каком упрощении.

Ловушка, ради которой правило записано: **две одинаковые покупки в один день — законны.** Два кофе по 200 ₽ в одном месте дают один `fingerprint` и две реальные операции. Поэтому сравнивается **число строк с этим `fingerprint` в файле и число уже лежащих в базе**, и добавляется разница; порядковый номер внутри группы хранится в `occurrence_no`. Дедупликация «есть такая — пропустить» теряет деньги owner и запрещена.

**Ожидающая операция обновляется, а не дублируется.** Строка со статусом `pending` в следующей выгрузке приходит как `posted`, и сумма могла измениться — валютная покупка, чаевые, отель. Поэтому `pending` матчится с `posted` по дате, карте и описанию **даже при несовпадении суммы** и обновляется на месте. Совпадение по `fingerprint` тут не сработает — сумма входит в хэш.

**Исчезнувшая операция помечается, а не удаляется.** Была в прошлом импорте, отсутствует в новом за тот же период того же банка — банк её отменил. Ставится `reverted`. Удаление запрещено: история правок сальдо важнее аккуратности таблицы.

**Неоднозначный случай уходит в разбор, а не решается угадыванием.** Кандидат в дубли, не совпавший ни по одному правилу, попадает в очередь «Требует внимания» и **в сальдо не входит**, пока owner не решит. Туда же попадает счёт с неизвестной ролью — новое имя счёта заводится в `fin_accounts` с ролью `unknown` (§15.5).

**Импорт заканчивается резюме** (§15.9): успешный `--apply` считает его по только что загруженным данным.

### 15.4 Категории

**Категории owner, банковские — подсказка** (решение owner от 2026-09-05). Порядок применения, от слабого к сильному:

1. MCC-код из выписки → категория,
2. категория банка по умолчанию → категория,
3. «Ваша категория» из выгрузки — то, что owner уже разметил в приложении банка,
4. правило по мерчанту (`fin_category_rules`),
5. **модель** — только для того, что не покрылось ступенями 1–4,
6. ручная правка owner в книжке.

Третья ступень в присланной выгрузке пуста во всех 62 строках: банковскими категориями owner не пользуется. Ступень всё равно нужна — она бесплатна и начнёт работать в тот день, когда он разметит хоть что-то в приложении.

Ручная правка сильнее всех и переживает переимпорт: повторная загрузка файла не должна затирать разложенное руками. **Запоминать ли правку как новое правило автоматически [?]** — решение owner; по умолчанию не запоминаем, чтобы одна разовая правка не начала действовать на все будущие операции этого мерчанта.

**Список основных категорий — входные данные от owner [?].** Ядро не содержит ни одного названия. До получения списка книжка работает с единственной категорией «без категории» — это рабочее состояние, а не блокер, ровно как пустой курс в §9.

#### Модель в разборе

**Модель участвует** (ADR-030, отменяет прежнее «модель не участвует»), но **только на пятой ступени**: ступени 1–4 детерминированы и бесплатны, и звать модель на то, что уже разобрано сравнением строк, — переплата того же рода, что вызов модели на закрытом задании (§5.1).

Модель делает две вещи:

- **раскладывает операцию** по основным категориям и подкатегориям месяца («фастфуд» → «Макдональдс»);
- **предлагает набор основных категорий на новый месяц** по истории прошлых месяцев.

#### Цикл месяца

- Категория — **строка с привязкой к месяцу**; операция указывает на версию своего месяца, и разбор прошлых месяцев не меняется никогда.
- **Глубина ровно два уровня:** основная категория → подкатегория. Третий уровень запрещён базой, а не соглашением.
- **Начало месяца:** набор основных категорий **наследуется** от прошлого месяца, модель отдельно кладёт предложения — что добавить и что убрать. Owner правит список и утверждает; до утверждения работает унаследованный набор, книжка не ждёт.
- **Внутри месяца модель добавляет категории и подкатегории сама,** без подтверждения (решение owner). Помесячный цикл и ограничивает цену такой вольности: месяц.
- **Сравнение между месяцами — по стабильному ключу** категории, не по имени и не по идентификатору строки. Без ключа «в среднем» (§15.9) не считается вообще.

Модель недоступна, ответ не прошёл схему или исчерпан месячный потолок — операция остаётся **без категории** и видна как неразобранная (§15.6). Выдуманная категория запрещена.

### 15.5 Сальдо, гашение расхода и накопление

**Накопления в v1 — это месяц: «Отложено» и «Осталось»** (решение owner, ADR-030). «Отложено» — сумма переводов на счета с ролью `savings`; «Осталось» — пришло минус ушло, плюс накопленный итог с начала ведения. Целей накопления, копилок и остатков по счетам нет — из этого прямо следует, что каналу **не нужно приносить баланс**, достаточно потока операций.

Две статьи, а не одна, потому что они отвечают на разные вопросы: месяц с хорошим сальдо, но без единого перевода на накопительный счёт — не накопление, а неизрасходованные деньги на карте.

**Роль счёта — данные owner, а не догадка по имени.** Новое имя счёта при импорте заводится в `fin_accounts` с ролью `unknown` и попадает в разбор. Пока счета не размечены, «Отложено» показывает **«счета не размечены»**, а не ноль: ноль здесь был бы правдоподобной выдумкой (§10).

- Месяц календарный, границы считаются в зоне owner, хранение в UTC (инвариант 7).
- В сальдо не входят: `transfer`, `reverted`, помеченные `excluded`, неразобранные кандидаты в дубли.
- **Неполный месяц помечается явно.** Данные загружены по 5-е — на экране «по 5 сентября», а не сальдо, выглядящее итоговым.
- Пустой месяц даёт нули и не делит на ноль — случай тестируемый, как пустой курс.

#### Входящий перевод: доход, возврат или доля за общую покупку

**Входящий перевод от человека — не обязательно доход.** В августе таких 14 на 9 911 ₽ при общем приходе 11 080 ₽, то есть почти весь «доход» месяца. Часть из них — деньги от родных, настоящий доход. Часть — доля за то, что owner оплатил на всех: в тот же день 23 августа приходят четыре перевода по 230 ₽ от разных людей и уходят две оплаты `OOO Leon` по 575 ₽. Если считать доходом всё, сальдо завышается вдвойне: и приход раздут, и расход не погашен.

Автоматически эти случаи неразличимы: в выгрузке они одна и та же строка с именем отправителя.

**Решено (owner, 2026-09-05): различаем правилом по отправителю.** Имя из колонки «Описание» — ключ правила в `fin_category_rules`. Отправители, отмеченные как родные, дают `income`; все прочие входящие переводы по умолчанию `refund`. Список родных — входные данные от owner, до его получения правил нет и все входящие переводы попадают в разбор, а не разносятся молча.

Почему по умолчанию именно `refund`, а не `income`: ошибка в эту сторону занижает доступные деньги, ошибка в обратную — завышает и приход, и остаток. Заниженное сальдо заметно и раздражает, завышенное выглядит правдоподобно и не проверяется.

#### Гашение конкретного расхода

**Поступление можно привязать к конкретной операции-расходу** (решение owner, ADR-030): оплатил стол в ресторане, потом скидывают доли — доли привязываются к этому расходу, и строка показывает **эффективную сумму**, свою минус погашенное. Много поступлений на один расход.

- **Гашение уменьшает месяц расхода, а не месяц поступления.** Это отменяет прежнее правило «`refund` уменьшает расход того месяца, в котором произошёл возврат» — но только для **привязанных** гашений. Непривязанный `refund` по правилу отправителя по-прежнему гасит месяц поступления: исходной покупки он не знает.
- **Окно привязки — текущий месяц и предыдущий.** В сентябре привязать можно к расходу сентября или августа; июль и раньше неизменны. Окно считается в зоне owner **от момента привязки**, а не от даты операции, и **снятие привязки ограничено тем же окном** — иначе старый месяц поехал бы через отмену.
- **Окно проверяется сервисом, а не CHECK:** оно зависит от «сейчас». Поэтому оно обязано быть покрыто тестом.
- **Излишек — доход.** Скинули больше, чем стоил стол: гашение закрывает расход до нуля, остаток показывается доходом — «погашено 5 750 ₽, доход 250 ₽». Отрицательного расхода не бывает, в разбор ничего не уходит. Излишек относится к **месяцу поступления**: у гасящей части есть исходная покупка, у излишка её нет.

**Следствие, которое обязано быть видно:** закрытый месяц перестаёт быть окончательным. Пересчитаться могут ровно два месяца — текущий и предыдущий, — и обзор месяца показывает, что цифра пересчитана позже. Всё старше окна окончательно.

### 15.6 Поведение при отказах

Дополняет таблицу §10 тем же принципом: не упасть и не соврать.

| Отказ | Что делаем | Чего не делаем |
|---|---|---|
| Выписку не загружали дольше срока из конфига | плашка «операции по `<дата>`, загружено N дней назад» + напоминание (§15.7) | показывать старое как актуальное |
| Один банк загружен, другой нет | давность считается по самому старому банку, в плашке назван он | считать книжку свежей по самой свежей выписке |
| Файл не разбирается, изменился формат | импорт этого файла отклонён целиком, с указанием колонки; база не тронута, остальные файлы захода обрабатываются | импортировать частично |
| Заголовок не узнал ни один адаптер | файл отклонён, пришедшие колонки перечислены | угадывать банк по имени файла |
| Кандидат в дубли неоднозначен | в очередь разбора, вне сальдо | тихо смержить или тихо задвоить |
| Операция есть в базе, но пропала из новой выгрузки | `reverted`, видно в ленте | удалить строку |
| Сумма в файле не парсится | вся строка в отказ, импорт останавливается | подставить ноль |
| Счёт с неизвестной ролью | в разбор; «Отложено» пишет «счета не размечены» | считать неразмеченный счёт расчётным и показывать ноль |
| Модель недоступна, ответ не прошёл схему, потолок расходов исчерпан | операция остаётся без категории и видна как неразобранная; резюме не показывается | выдумать категорию или резюме |

Импорт запускается руками, поэтому «падает громко» здесь означает внятную ошибку в терминале и ненулевой код возврата, а не письмо owner. Воскресный джоб напоминания — фоновый, и падает он громко по общему правилу инварианта 9.

### 15.7 Интерфейс и напоминание

Отдельная вкладка `Finance`, постоянная, вне генерируемого из курсов списка (ADR-025). Экраны — этапы 10–14 в `design/PROGRESS.md`: обзор месяца, импорт и дифф, лента операций, карточка операции, категории и правила. Карточка операции несёт привязку гашений (§15.5), экран категорий — очередь предложений модели на новый месяц (§15.4).

**Напоминание о выписках — воскресным джобом** (ADR-030): событие в календаре `JARVIS · События` со стабильным `external_key` (инвариант 5) плюс плашка давности на вкладке. Только плашки недостаточно — её видит лишь тот, кто сам открыл сайт; push не заводится, напоминания доставляет календарь (ADR-002).

### 15.8 Не делаем в v1

Бюджеты и лимиты по категориям, цели накопления и прогресс к ним, прогнозы трат, инвестиции, полноценная мультивалютность (валютная покупка записывается суммой списания в рублях), любой автоматический канал получения операций, интеграция с банком по API.

**Резюме о тратах (§15.9) в v1 входит** — прежняя формулировка относила к «не делаем» всю аналитику трат, и ADR-030 сузил её до прогнозов, бюджетов и целей.

### 15.9 Резюме о расходах

**Короткий текст после каждого успешного импорта** (ADR-030): «на этой неделе значительно больше на фастфуд, чем в среднем». Считается моделью по только что загруженным данным, за период с прошлой загрузки.

- **После импорта, а не по расписанию.** В воскресенье выписка ещё не загружена — это и есть повод для напоминания; резюме в тот момент описывало бы прошлую неделю, выглядя как отчёт о текущей.
- **Сравнение — по стабильному ключу категории** (§15.4), иначе «в среднем» не с чем сопоставлять: состав подкатегорий каждый месяц новый.
- **Мало истории — так и сказать.** Первые недели сравнивать не с чем, и текст обязан это назвать, а не выдумать среднее по одному месяцу.
- **Снимок чисел хранится вместе с текстом** (`fin_summaries.basis`). Гашение задним числом меняет цифры двух месяцев (§15.5), и без снимка прошлое резюме начнёт противоречить текущему сальдо необъяснимо.
- **Стоимость вызова — в `audit_log`** с провайдером, моделью и токенами (инвариант 8).
