# ADR-034 · Фронт: одна дверь снаружи, палитра и контракт — без копий

Запись журнала решений. Указатель — [DECISIONS.md](../DECISIONS.md).

---

**2026-09-13 · принято · развилки закрыты owner до начала работы · уточняет ADR-020, опирается на ADR-031 п. 3**

Каркас `apps/web` ставит три вопроса, каждый из которых решается один раз и потом живёт до конца проекта: кто отдаёт страницы наружу, откуда фронт берёт палитру и откуда — знание об API.

**Снаружи виден один сервис — `web`: Caddy со статикой, он же прокси `/api`.** Туннель ведёт на него, а не на API. Причина не в удобстве: CORS в API не настроен намеренно (ADR-031 п. 3), и это правильно ровно до тех пор, пока браузер ходит к API по относительному пути на том же источнике. Маршрут туннеля прямо на `api:8000` выставил бы наружу голый API без единой страницы и потребовал бы CORS с первого же экрана. В разработке ту же роль играет `next dev` — путь `/api` одинаков в обоих режимах, различается лишь, кто его проксирует.

*Почему Caddy, а не nginx:* конфиг раздачи со `try_files` и одним `reverse_proxy` умещается в десяток строк, где ошибиться негде; в `location`/`proxy_pass` nginx ошибиться есть где, а проверяется эта дверь только снаружи и только вручную. Выигрыш nginx — несколько мегабайт образа — на фоне Node-сборочного слоя не значит ничего.

**Палитра импортируется из `design/tokens.css` напрямую, копии внутри `apps/web` нет.** Копия расходится с оригиналом молча, и первым это видит owner на экране; дизайн при этом остаётся отдельной дорожкой, где макет открывается двойным кликом без npm. Цена решения — одна строка в `next.config.ts`: корнем сборки объявлен корень репозитория, иначе сборщик не выпускает импорт за пределы каталога приложения. Альтернатива — копия и тест-сверка — отвергнута: сверка ловит расхождение, но только после того, как оно случилось, и требует помнить о цели `make web-tokens`.

**Компоненты оболочки берутся из `tokens.css`, а не переписываются утилитами Tailwind.** Tailwind остаётся в сборке (стек, CLAUDE.md) и годится для раскладки, но `app`, `rail`, `tab`, `rail-action`, `content` утверждены на этапе 1 дизайна и живут в токенах. Второй системы для тех же элементов не заводим: две правды о кнопке — это две кнопки, расходящиеся на первой же правке.

**Клиент — сгенерированные типы плюс тонкая обёртка над `fetch`, а не сгенерированный рантайм-клиент.** `src/api/schema.d.ts` получается из `packages/contracts/openapi.json` ручным шагом `make web-client`, ровно как сам контракт получается ручным `make contract`: изменение обязано быть видно в дифе. Расхождение файла с контрактом роняет `tests/contract.test.ts`. Рантайм-генератор дал бы то же самое плюс зависимость, которая живёт в каждом ответе, — а обёртки нужно тридцать строк, потому что разбирать остаётся одно: тело отказа из контракта.

**Отказ разбирается по телу, а не по номеру статуса.** Признак «повторять» приходит от сервера (`retryable`), потому что решение это серверное; чужое тело — 502 от прокси, страница входа Cloudflare — не роняет разбор, а превращается в отказ с кодом `unknown` (инвариант 9). 401 и 403 клиент помечает отдельно: они лечатся не повтором запроса, а перезагрузкой страницы, потому что вход проводит Access на навигации, а не на `fetch` (ADR-033).

*Альтернативы, отвергнутые разом:* SSR-контейнер на плате — закрыт ADR-020 (рендерить нечего, Node стоит сотни мегабайт RAM); отдельный хост для фронта — закрыт там же; копия контракта внутри `apps/web` — та же ошибка, что копия палитры, только дороже.

*Почему в журнале:* это три решения, которые нельзя переиграть дёшево. Дверь снаружи определяет, нужен ли CORS; источник палитры — разъедется ли дизайн с продуктом; источник типов — будет ли фронт узнавать об изменении API из теста или из браузера owner.
