# ADR-033 · Аутентификация owner — Cloudflare Access, проверяемый нами второй раз

Запись журнала решений. Указатель — [DECISIONS.md](../DECISIONS.md).

---

**2026-09-13 · принято · закрывает отложенное решение ADR-031 п. 3, выполняет условие «туннель не раньше аутентификации»**

Э7 начинается с аутентификации, потому что включённый туннель поверх сервиса без неё — это публичный доступ к расписанию и к правке периодов ценой в один флаг. Ставить свой вход — форму, пароль, сессии, восстановление — ради одного пользователя мы не стали.

**Дверь запирает Cloudflare Access, а API проверяет результат ещё раз.** Запрос с улицы доходит до Pi, только пройдя политику Access; `cloudflared` подписывает его и кладёт токен в заголовок `Cf-Access-Jwt-Assertion`. `api/auth.py` — вторая дверь: проверяет подпись по публичным ключам команды (JWKS), адресата (`aud`), издателя и почту, сверяя её с `CF_ACCESS_ALLOWED_EMAIL`.

**Почему второй двери мало не бывает.** Политика Access правится мышкой в браузере, вне репозитория и вне ревью; промах в ней не должен означать доступ к расписанию owner. И заголовок с почтой, который Access тоже ставит, сам по себе не доказательство: поверить ему на слово — значит пустить любого, кто дотянется до порта API, просто набрав нужную строчку. Доказательство — подпись, а не содержимое.

**Три проверки, каждая из которых открывает дверь молча, если её забыть.** Алгоритм задан жёстко списком `RS256`: иначе токен с `alg: none` или подписанный HS256, где секретом подставлен наш же публичный ключ, проходит. Адресат сверяется явно: в одной команде Cloudflare живёт сколько угодно приложений, и токен, выписанный любому другому, — валидный токен с валидной подписью. Почта сверяется с единственной разрешённой; сервисные токены (`common_name` вместо почты) не пускаются вовсе — в проекте с одним пользователем им неоткуда взяться.

**Ненастроенная аутентификация — закрытая дверь.** Пустые `CF_ACCESS_*` при `ENV=prod` дают отказ на каждом `/api/*`, а не тихий пропуск. Правило выбрано по тому, как ошибаются на самом деле: строчку в `.env` забывают, а флаг «выключить защиту» ставят один раз и не убирают. Исключение одно и узкое — `ENV=dev`, машина разработки, где туннеля нет по построению; при старте в лог уходит строка о том, в каком режиме поднялся процесс.

**Зависимость вешается в одном месте — на подключении роутеров в `main.py`,** а не по роутеру. Роутер следующего этапа пишется по образцу соседнего, и потерянная строчка защиты не видна в дифе. Класс ошибки закрыт исполняемо: `tests/test_auth.py` обходит все пути `/api/*` из контракта и требует 401 от каждого — незащищённый роутер краснеет в тот же прогон, в котором появился.

**Ключи кэшируются на процесс.** Это не ускорение: без кэша каждый опрос сетки означал бы поход в Cloudflare на пути ответа. С кэшем недоступность Cloudflare перестаёт быть мгновенным отказом — ключи в памяти продолжают проверять подпись (инвариант 9, деградация вместо падения).

**Новая зависимость: `pyjwt[crypto]`** (подтверждена owner). Разбор JWT руками — это ровно три ошибки выше, и ни одна из них не видна на счастливом пути.

*Альтернативы:* свой вход с паролем и сессиями — отвергнут: собственное хранилище паролей и восстановление доступа ради одного пользователя, при том что дверь всё равно нужна снаружи туннеля; доверие заголовку `Cf-Access-Authenticated-User-Email` без проверки подписи — отвергнут по причине выше; mTLS с клиентским сертификатом на телефоне — отвергнут как неудобный ровно там, где приложением пользуются (перевыпуск и установка профиля на каждом устройстве); basic auth на прокси — отвергнут: пароль в заголовке каждого запроса и общий на все устройства, без журнала входов.

*Почему в журнале:* ADR-031 п. 3 отложил решение явным образом и поставил условие. Это ответ на отложенный вопрос, он же — единственная защита сервиса, который на следующем шаге выходит наружу.
