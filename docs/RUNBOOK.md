## Что где лежит

| Что | Где |
|---|---|
Плата | Raspberry Pi 4 Model B, 2 ГБ, домашняя сеть, `jarvis.local`
Пользователь | `jarvis`, вход **только по ключу**
Ключ доступа | `~/.ssh/jarvis_pi` на машине owner; снаружи — `ssh jarvis-pi` через туннель (ADR-045)
Репозиторий на плате | `/home/jarvis/jarvis`
Секреты | `/home/jarvis/jarvis/.env`, права `600`, в git не попадает
Данные базы | том Docker `jarvis_db-data`
Локальные копии | том Docker `jarvis_db-backups`
Носитель данных | USB-SSD, раздел `jarvis-data` в `/mnt/ssd`; туда вынесен весь `/var/lib/docker` (ADR-032)
Носитель системы | microSD: `/boot/firmware` и корень

Вход из дома:

```bash
ssh -i ~/.ssh/jarvis_pi jarvis@jarvis.local
```

Вход снаружи — через туннель, той же почтой owner (ADR-045; настройка —
«Внешние сервисы» → Cloudflare, шаг 9):

```bash
ssh jarvis-pi
```

Если имя не отвечает — плата доступна по адресу из DHCP роутера. Найти её
можно по MAC-префиксу Raspberry Pi (`dc:a6:32`).

**Если локальная сеть не отвечает вовсе, а интернет работает** — смотреть на
VPN: клиент с включённым kill-switch блокирует домашние адреса. Признак —
`ping` до собственного роутера отвечает `General failure`.

## Повседневные команды

Выполняются на плате, из `/home/jarvis/jarvis`.

```bash
make up              # поднять стек (база, API и фронт; туннель - только с COMPOSE_PROFILES=tunnel)
make down            # остановить
make logs            # смотреть логи
make migrate-pi      # накатить миграции внутри контейнера api
make backup          # снять дамп и показать, что выгрузил бы (dry-run)
make backup-apply    # снять дамп, выгрузить в B2, отправить ping
make restore-check   # развернуть свежий дамп в отдельную базу и разобрать, что вышло
make restore-check-apply # то же плюс ping сторожу - так это делает таймер
make sync-itmo-pi    # забрать расписание портала в зеркало (dry-run)
make sync-gcal-pi    # показать, что уедет в Google Calendar (dry-run)
make daily-pi        # обе операции разом, как это делает планировщик (dry-run)
make tunnel-check-pi # дверь заперта? проверка перед включением туннеля и после
```

Наружу по умолчанию не пишет ничего: реальная выгрузка — только `--apply`.

Проверка живости:

```bash
curl -s http://127.0.0.1:8000/health   # API напрямую
curl -s http://127.0.0.1:8080/health   # он же через фронтовый прокси
```

## Первый запуск на чистой плате

Если плату приходится ставить заново — например, после смерти карты.

**1. Система.** Raspberry Pi OS Lite **64-bit** (не 32-битная: под неё не
выпускают образов Postgres, а образ API собран под `linux/arm64`). Пишется
Raspberry Pi Imager с ноутбука; в окне настроек задаются имя хоста `jarvis`,
пользователь `jarvis`, Wi-Fi, часовой пояс и **SSH только по ключу** —
публичный ключ вставляется в поле на вкладке Services.

Imager 2.x применяет эти настройки через cloud-init: на разделе `bootfs`
появляются `user-data`, `meta-data`, `network-config`. Файл `custom.toml`
той же версией **не читается** — проверять применение настроек надо по
cloud-init файлам.

**2. Беспарольный `sudo`** (cloud-init его не выдаёт):

```bash
echo "jarvis ALL=(ALL) NOPASSWD: ALL" | sudo tee /etc/sudoers.d/010_jarvis-nopasswd
sudo chmod 0440 /etc/sudoers.d/010_jarvis-nopasswd
```

**3. Memory cgroup** — Docker без него не ограничивает память контейнеров.
Параметр отключает прошивка платы, в файле его не видно, поэтому дописывается
в конец **единственной строки** `cmdline.txt` (перевод строки внутри ломает
загрузку):

```bash
sudo cp /boot/firmware/cmdline.txt /boot/firmware/cmdline.txt.bak
CUR=$(tr -d '\n' < /boot/firmware/cmdline.txt)
printf '%s cgroup_enable=memory cgroup_memory=1\n' "$CUR" | sudo tee /boot/firmware/cmdline.txt
sudo reboot
```

Проверка: `cat /sys/fs/cgroup/cgroup.controllers` содержит `memory`.

**4. Docker** из официального репозитория (в Debian свой пакет заметно старее):

```bash
sudo apt-get update && sudo apt-get -y upgrade
sudo apt-get -y install git curl ca-certificates gnupg
sudo install -m 0755 -d /etc/apt/keyrings
curl -fsSL https://download.docker.com/linux/debian/gpg | sudo gpg --dearmor --yes -o /etc/apt/keyrings/docker.gpg
sudo chmod a+r /etc/apt/keyrings/docker.gpg
echo "deb [arch=arm64 signed-by=/etc/apt/keyrings/docker.gpg] https://download.docker.com/linux/debian $(. /etc/os-release && echo $VERSION_CODENAME) stable" \
  | sudo tee /etc/apt/sources.list.d/docker.list
sudo apt-get update
sudo apt-get -y install docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
sudo usermod -aG docker jarvis
sudo reboot
```

**5. Репозиторий и `.env`:**

```bash
git clone https://github.com/Viniron/PetProject.git ~/jarvis
cd ~/jarvis
cp .env.example .env
chmod 600 .env
```

Дальше в `.env` вписываются реальные значения — см. следующий раздел.
Пароль базы генерируется на месте:

```bash
openssl rand -base64 32 | tr -dc 'A-Za-z0-9' | head -c 28
```

**6. Подъём и проба восстановления:**

```bash
make up
docker exec -i jarvis-db-1 psql -U jarvis -d jarvis < infra/restore-probe.sql
```

## Внешние сервисы

Секреты вписываются в `.env` **на плате** и никуда больше не копируются.
Открыть файл: `nano ~/jarvis/.env`, сохранить `Ctrl+O`, выйти `Ctrl+X`.

### Google Calendar → `GOOGLE_SA_JSON`, `GOOGLE_CALENDAR_OWNER_EMAIL`

Service account в Google Cloud и почта owner, которой отдаются календари.
Пошагово — в разделе «Google Calendar» ниже: там же создание календарей
и первая запись расписания.

### Cloudflare → `CF_ACCESS_*`, `CF_TUNNEL_TOKEN`

Одна настройка на две вещи: **дверь** (Access — кого пускать) и **труба**
(Tunnel — как запрос с улицы попадает на плату за домашним роутером).

**Порядок шагов ниже обязателен: сначала дверь, потом труба.** Включённый
туннель поверх сервиса без аутентификации — это публичное расписание и
публичная правка периодов, ценой в одну строчку `.env` (ADR-031 п. 3,
ADR-033). Проверка `make tunnel-check-pi` стоит на этом пути не для красоты:
она отказывается признать настройку готовой, пока дверь не заперта.

**Что понадобится:** аккаунт Cloudflare, **свой домен** и примерно полчаса.
Домен платный — это единственная постоянная трата проекта. Бесплатного
постоянного имени у туннеля не бывает: адреса `trycloudflare` меняются при
каждом перезапуске, а Access без собственной зоны не работает вовсе. Сам
туннель и Zero Trust — бесплатны.

**Зона какая угодно, лишь бы её NS можно было делегировать на Cloudflare.**
`.ru` этому условию удовлетворяет, и дальше всё работает одинаково: Access,
туннель, сертификат. Разница только в том, где домен покупается и чем
платить.

**Где покупать и что покупать — два независимых вопроса.** Cloudflare
обслуживает зону, а не продаёт её: домен, купленный где угодно,
подключается одинаково.

| | `.com` в панели Cloudflare | `.com` у российского регистратора | `.ru` |
|---|---|---|---|
| Чем платить | зарубежная карта | рублями | рублями |
| Порядок цен | $10–12 в год | около тысячи рублей в год, смотреть прайс | несколько сотен рублей, продление дороже первого года |
| Что нужно | ничего сверх аккаунта | ничего сверх аккаунта регистратора | паспортные данные: `.ru` регистрируется на конкретное лицо |
| Зона заводится | сама | вручную: **Add a site**, затем сменить NS у регистратора | так же вручную |
| Зону могут отозвать | нет | нет: зона международная, регистратор только посредник | да, по решению регистратора или КЦ |

Cloudflare Registrar `.ru` не продаёт — он не аккредитован Координационным
центром, — но **обслуживать** зону `.ru` ему ничто не мешает.

**Средний столбец — разумный выбор по умолчанию.** Платится рублями, как
`.ru`, но домен остаётся в международной зоне, где решение национального
регулятора его не касается. Плата за это — разница в цене с `.ru` и то,
что продление у посредника дороже, чем у Cloudflare по себестоимости.
Перенести домен в Cloudflare Registrar позже можно отдельной операцией,
и на работающий JARVIS она не влияет.

Дальше `example.com` — это ваш домен, `jarvis.example.com` — имя, по которому
будет открываться JARVIS. С `.ru` читается так же: `jarvis.example.ru`.

**В текущей установке имя — сам домен, без поддомена:** `viniron.ru`
(переехали с `jarvis.viniron.ru` 2026-09-14). Шаги ниже от этого не меняются,
разница одна: поле **Subdomain** везде остаётся пустым — и в приложениях
Access, и в публичном имени туннеля. Цена выбора: апекс занят JARVIS
за дверью, публичную страницу-визитку на этом домене уже не повесить.

#### 1. Аккаунт и домен

1. `dash.cloudflare.com` → Sign up, почта owner. Включить двухфакторную
   аутентификацию сразу: этот аккаунт — ключ от дома.
2. Домен. Либо купить прямо здесь (**Domain Registration → Register
   Domains**) — тогда зона заводится сама, — либо, если домен куплен
   у другого регистратора (`.ru` — только так, `.com` — по желанию),
   **Add a site** → ввести домен →
   план **Free**. Cloudflare покажет два своих NS-сервера: их нужно вписать
   в панели регистратора вместо его собственных, **заменив, а не дополнив**.
3. Дождаться, пока домен в панели станет **Active**. Смена NS занимает
   от четверти часа до суток; до этого момента дальше идти бессмысленно.
   Почтовые и прочие записи, если домен уже где-то использовался, Cloudflare
   переносит при подключении не всегда — их стоит сверить глазами до смены
   NS, а не после.

**Домен owner куплен в reg.ru (2026-09-14) — значит второй путь: `Add a
site`.** В панели регистратора: «Домены» → карточка домена → управление
DNS-серверами. Подписи кнопок у регистратора меняются, операция называется
«сменить DNS-серверы»: вписать оба сервера Cloudflare вместо `ns1.reg.ru`
и `ns2.reg.ru`. Три вещи, которые здесь легко пропустить:

- **Собственный DNS reg.ru после этого не используется.** Записи в зоне
  на стороне регистратора остаются лежать и ни на что не влияют — всё
  правится в Cloudflare. Редактировать старую зону «на всякий случай»
  бессмысленно и путает при разборе.
- **DNSSEC, если он включён у регистратора, выключается до смены NS.**
  Подпись останется от старых серверов, резолверы отвергнут новую
  делегацию, и домен просто перестанет открываться — отказ выглядит как
  «интернет сломался», а не как ошибка настройки.
- **Делегация проверяется снаружи, а не по цвету строки в панели:**

```bash
nslookup -type=ns example.ru 8.8.8.8   # ждём два *.ns.cloudflare.com
```

#### 2. Команда Zero Trust

1. В панели слева → **Zero Trust**. Первый вход просит придумать **team
   name** — это часть адреса `<team>.cloudflareaccess.com`, менять её потом
   больно, так что лучше короткое и своё (например `jarvis`).
2. План — **Free**. Карту на этом шаге могут попросить привязать даже
   к бесплатному плану; списаний по нему нет. Учтите: платежи Cloudflare
   принимает не всякой картой, и карты российских банков через неё
   не проходят. Домен `.ru`, купленный за рубли, эту проблему решает только
   наполовину: если привязка карты всё же потребуется, понадобится
   зарубежная — других путей у Zero Trust нет.
3. Записать домен команды: **Settings → Custom Pages** (или General), строка
   вида `jarvis.cloudflareaccess.com`. Это будущее значение
   `CF_ACCESS_TEAM_DOMAIN`. Копировать можно вместе с `https://` — схему
   срежет код.

Вход по умолчанию — **One-time PIN**: Cloudflare присылает код на почту.
Этого достаточно; подключать Google как провайдера входа не обязательно.

#### 3. Приложение Access — сама дверь

**Access → Applications → Add an application → Self-hosted.**

| Поле | Значение |
|---|---|
| Application name | `JARVIS` |
| Session Duration | на своё усмотрение; сутки-месяц — разумно |
| Public hostname | subdomain `jarvis`, domain `example.com`, path — **пусто** |

Путь пустой намеренно: дверь накрывает имя целиком, вместе со страницей.
Приложение, повешенное на один `/api`, оставило бы страницу открытой всем,
а вход случался бы неизвестно когда.

Дальше — **политика**: Add a policy → Action **Allow** → Include →
**Emails** → почта owner. Одна почта, без «всех из домена».

После создания открыть карточку приложения → **Overview** → скопировать
**Application Audience (AUD) Tag** — 64 шестнадцатеричных знака. Это
`CF_ACCESS_AUD`.

#### 4. Второе приложение — `/health` мимо двери

**Access → Applications → Add an application → Self-hosted**, тем же
порядком, но:

| Поле | Значение |
|---|---|
| Application name | `JARVIS health` |
| Public hostname | subdomain `jarvis`, domain `example.com`, path `health` |
| Политика | Action **Bypass** → Include → **Everyone** |

Зачем — ADR-036: это единственная ручка, по которой снаружи видно, что плата
жива, а монитор доступности пройти вход по почте не умеет. Ручка не трогает
базу и отдаёт только «жив», версию и время.

**Путь обязан быть длиннее корневого.** Приложения Access различаются путём,
а не порядком создания: bypass, повешенный на корень, откроет весь JARVIS.

#### 5. Три переменные в `.env` — до всякого туннеля

```bash
nano ~/jarvis/.env
```

```
CF_ACCESS_TEAM_DOMAIN=jarvis.cloudflareaccess.com
CF_ACCESS_AUD=<64 знака из карточки приложения>
CF_ACCESS_ALLOWED_EMAIL=<почта owner>
```

Ни одна из трёх не секрет: домен команды и почта видны в браузере, а AUD —
идентификатор приложения, сам по себе ничего не открывающий. В репозиторий
они всё равно не попадают — `.env` закрыт `.gitignore`.

Дальше:

```bash
make up              # перечитать .env
make tunnel-check-pi
```

Проверка обязана пройти **до** включения туннеля и целиком:

```
[OK  ] ENV=prod
[OK  ] CF_ACCESS_TEAM_DOMAIN заполнена
[OK  ] CF_ACCESS_AUD заполнена
[OK  ] CF_ACCESS_ALLOWED_EMAIL заполнена
[OK  ] ключи команды Cloudflare отдаются
[OK  ] api: /health отвечает
[OK  ] api: /api/calendar заперт
[OK  ] api: мусорный токен не пускается
[OK  ] web: /health отвечает
[OK  ] web: /api/calendar заперт
[SKIP] ssh-маршрут заперт Access - CF_ACCESS_SSH_HOSTNAME пусто: проверять нечего
```

Хоть один `FAIL` — туннель не включать, чинить по подсказке в строке.
`SKIP` туннель не запрещает: до шага 9 второго маршрута ещё нет. Но и
пройденным пунктом он не считается — маршрут, заведённый в панели и
не вписанный в `.env`, остаётся без присмотра.

#### 6. Туннель

1. **Zero Trust → Networks → Tunnels → Create a tunnel → Cloudflared**,
   имя `jarvis`.
2. Скопировать токен из показанной команды — длинная строка после `--token`.
   **Это секрет**, в отличие от трёх переменных выше: он и есть ключ от
   трубы в дом.
3. **Public Hostname**: subdomain `jarvis`, domain `example.com`, service
   `http://web:8080`. Именно `web`, а не `api`: Caddy раздаёт интерфейс и он
   же проксирует `/api`, а прямой маршрут на API выставил бы наружу голый
   API без единой страницы.
4. В `.env` на плате:

```
CF_TUNNEL_TOKEN=<токен>
COMPOSE_PROFILES=tunnel
```

`COMPOSE_PROFILES` включается **той же правкой**, что и токен: сервис
туннеля живёт в профиле, и без этой строки не поднимается. Обязательной
переменной токен сделать нельзя — compose подставляет переменные до учёта
профилей, и тогда падали бы команды, туннеля не касающиеся.

```bash
make up
docker compose logs cloudflared   # ждём "Registered tunnel connection"
make tunnel-check-pi              # ещё раз: теперь дверь открыта наружу
```

#### 7. Проверка снаружи — с телефона по мобильной сети

Домашний Wi-Fi для этой проверки не годится: из дома всё работает и без
туннеля.

1. `https://jarvis.example.com` → страница входа Cloudflare → почта owner →
   код из письма → открывается календарь.
2. `https://jarvis.example.com/health` → отвечает **без** входа (ADR-036).
3. Открыть в режиме инкогнито и попробовать войти **чужой** почтой —
   Access отказывает. Если пустил, политика впускает лишних; чинить её,
   а не код.

### Когда что-то пошло не так

**Сам owner получает 401 на всё, страница пустая.** Дверь заперта для всех —
значит `CF_ACCESS_*` не те. Сверить AUD с карточкой приложения и домен
команды с `Settings`: одна опечатка в любом из них выглядит одинаково.
`make tunnel-check-pi` называет конкретную строку.

**Вход проходит, но экран говорит «Сессия кончилась».** Токен доезжает, но
не наш: чаще всего AUD от соседнего приложения (например от того, что
создано для `/health`). AUD у каждого приложения свой.

**Страница просит вход по кругу.** Session Duration слишком короткий или
браузер режет cookie третьих сторон в инкогнито. Проверять в обычном окне.

**`docker compose logs cloudflared` пуст, туннель не поднялся.** Либо
`COMPOSE_PROFILES=tunnel` не дописан (сервис просто не создан — смотреть
`docker compose ps`), либо токен обрезан при копировании.

**`/health` требует входа.** Второе приложение создано без пути или с путём
на корне. Путь обязан быть `health`, иначе bypass накрывает всё приложение —
и это уже не «не работает монитор», а открытый наружу JARVIS.

**Имя открывается, но отдаёт 502.** Туннель дошёл до платы, а `web` не
поднят: `docker compose ps`, затем `make logs`.

#### 8. Выход туннеля через AmneziaWG

Поставлено 2026-09-14, решение и доказательная часть — [ADR-037](adr/ADR-037-tunnel-egress-via-amneziawg.md).

**Симптом, ради которого это сделано.** Снаружи `1033` или `530`, в логах
`cloudflared` соединения регистрируются и через одну-три минуты теряются
(`Lost connection with the edge`), а входящих запросов в логе нет вообще.
При этом канал платы в порядке: потерь нет, файлы качаются, чужие TLS-сессии
живут. Рвутся именно сессии туннеля.

**Что стоит на плате.** Модуль ядра `amneziawg` (собран из исходников,
зарегистрирован в DKMS) · утилиты `awg`, `awg-quick` · конфиг
`/etc/amnezia/amneziawg/awg0.conf`, владелец `root`, права `600` · автозапуск
`awg-quick@awg0`. В конфиге две наши строки поверх выданного провайдером:

```
Table = off
PostUp = ip route replace 198.41.192.0/20 dev %i
```

`Table = off` запрещает VPN забирать весь трафик, `PostUp` уводит в него
**одну** подсеть — краевые узлы Cloudflare Tunnel. ИТМО, Google и бэкап идут
прежним маршрутом; отказ VPN гасит доступ снаружи, но не джобы.

**Проверить, что схема цела** — три команды:

```bash
sudo awg show awg0 latest-handshakes        # число близко к текущему времени
ip route get 198.41.192.67                  # ждём "dev awg0"
curl -s --interface awg0 https://cloudflare.com/cdn-cgi/trace | grep loc=   # loc=DE
```

**Когда что-то пошло не так.**

*Рукопожатие старое или интерфейса нет.* VPN лёг: `sudo systemctl restart
awg-quick@awg0`, затем `sudo systemctl status awg-quick@awg0`. Сам туннель
после этого лучше перезапустить: `docker compose restart cloudflared` —
коннектор не всегда замечает смену маршрута.

*Маршрут `dev awg0` пропал, а интерфейс жив.* Строку `PostUp` затёрли при
замене конфига. Вернуть руками — `sudo ip route replace 198.41.192.0/20 dev
awg0` — и дописать в конфиг, иначе после перезагрузки повторится.

*После обновления ядра.* `dkms status` обязан показывать `amneziawg`
собранным под новое ядро. Если нет — `sudo dkms install -m amneziawg -v 1.0.0`.
Молчаливый отказ здесь выглядит как «сайт не открывается», а не как ошибка.

*Меняете конфиг на новый от провайдера.* Он придёт без наших двух строк —
дописать их заново, иначе VPN заберёт весь трафик платы, и сбор расписания
поедет из Германии.

#### 9. Второй маршрут: SSH на плату

Зачем: до него чинить плату можно только из дома, а сценарий «не отвечает,
owner в другом городе» заканчивается выдернутым питанием. Решение и почему
именно так — [ADR-045](adr/ADR-045-ssh-route-over-tunnel.md).

**Делается после того, как первый маршрут работает.** Порядок тот же, что
на шаге 3: сначала дверь, потом маршрут.

**1. Проверить, что вход по паролю на плате выключен** — это условие, а не
пожелание: маршрут наружу превращает подбор пароля из домашней задачи
в интернетную.

```bash
sudo sshd -T | grep -E "^(passwordauthentication|permitrootlogin|kbdinteractiveauthentication)"
```

Ждём `passwordauthentication no`, `permitrootlogin no`,
`kbdinteractiveauthentication no`. Если хоть одна `yes` — дописать в
`/etc/ssh/sshd_config.d/10-jarvis.conf` и перезапустить `sudo systemctl
restart ssh`, **не выходя из текущей сессии**: сломанный конфиг оставит
плату без входа.

```
PasswordAuthentication no
KbdInteractiveAuthentication no
PermitRootLogin no
```

**2. Приложение Access — вторая дверь, отдельная от первой.**

**Access → Applications → Add an application → Self-hosted.**

| Поле | Значение |
|---|---|
| Application name | `JARVIS SSH` |
| Public hostname | subdomain `ssh`, domain `viniron.ru`, path — **пусто** |
| Session Duration | короче, чем у `JARVIS`: сутки хватает |

Политика — та же: Add a policy → Allow → Include → Emails → почта owner.
Одна почта, без «всех из домена».

Приложение именно **второе**. Сессия первого живёт в браузере телефона
сутками, и та же сессия не должна означать открытый вход на плату.

**3. Маршрут в туннеле.** Zero Trust → Networks → Tunnels → `jarvis` →
Configure → Public Hostname → Add:

| Поле | Значение |
|---|---|
| Subdomain | `ssh` |
| Domain | `viniron.ru` |
| Type | `SSH` |
| URL | `host.docker.internal:22` |

`localhost:22` здесь **неверно** и выглядит правильно: это сам контейнер
`cloudflared`, где 22-го порта нет. Имя `host.docker.internal` заведено
строкой `extra_hosts` в `infra/docker-compose.pi.yml`; если контейнер
поднят давно — `docker compose up -d cloudflared`, иначе имя не появится.

**4. Строка в `.env` на плате** — чтобы маршрут попал под присмотр:

```
CF_ACCESS_SSH_HOSTNAME=ssh.viniron.ru
```

Не секрет: имя и так видно в адресной строке. Читает её только проверка.

```bash
docker compose up -d api        # подхватить переменную
make tunnel-check-pi
```

Ждём строку `[OK  ] ssh-маршрут заперт Access`. Пока строка пустая, в отчёте
стоит `[SKIP]` с причиной — это не «всё хорошо», а «маршрут без присмотра».

**5. Клиент на машине owner.** Нужен `cloudflared` — на Windows он ставится
`winget install --id Cloudflare.cloudflared`. Затем в `~/.ssh/config`:

```
Host jarvis-pi
  HostName ssh.viniron.ru
  User jarvis
  IdentityFile ~/.ssh/jarvis_pi
  ProxyCommand cloudflared access ssh --hostname %h
```

Вход:

```bash
ssh jarvis-pi
```

Первый раз откроется браузер с входом Cloudflare — почта owner, код из
письма. Дальше токен живёт в `~/.cloudflared/` до конца Session Duration.
Ключ платы при этом никуда не уезжает: Cloudflare переносит шифрованный
поток, а пускает внутрь по-прежнему `authorized_keys`.

**6. Проверка снаружи — не из дома.** С мобильной сети, из-под телефона
или с ноутбука в чужой сети:

```bash
ssh jarvis-pi "uptime && docker ps --format '{{.Names}}: {{.Status}}'"
```

И отдельно — что дверь на месте: `curl -sI https://ssh.viniron.ru` обязан
ответить редиректом на `viniron.cloudflareaccess.com` (или прямым `401`).
Ответ `502` означает открытый маршрут — приложение Access либо не создано,
либо висит на другом имени; чинить немедленно, это вход на плату.

**Когда что-то пошло не так.**

*`ssh jarvis-pi` висит и молчит.* `cloudflared` не найден в PATH — `ProxyCommand`
запускается тем же shell, что и `ssh`. Проверить: `cloudflared --version`.

*Просит пароль.* Либо не тот `IdentityFile`, либо ключ не в `authorized_keys`
на плате. Пароля не будет: вход по нему выключен шагом 1.

*`connection refused` уже после входа Access.* Маршрут ведёт не туда —
в панели стоит `localhost:22` вместо `host.docker.internal:22`.

*`make tunnel-check-pi` говорит `catch-all туннеля (http_status:404)`.*
Имя в `.env` есть, маршрута в панели нет: шаг 3 не доделан.

#### 10. Третий маршрут: выход к моделям

Зачем: провайдеры моделей геоблокируют российский адрес запроса. Без этого
шага разбор события и категоризация операций отказывают с пометкой `ВЫХОД`
в `make llm-probe-pi-apply` — рабочее состояние этапа Э12б, а не поломка.
Решение и цена — [ADR-050](adr/ADR-050-llm-egress.md).

**Делается тем же механизмом, что шаг 8:** подсеть назначения в `PostUp`
конфига `awg0`, `Table = off` на месте, маршрут по умолчанию не трогается.

**Но сначала прочитать про Google, иначе сюрприз будет дорогим.**
`generativelanguage.googleapis.com` и `www.googleapis.com` резолвятся
в **один и тот же** набор адресов (проверено 21.09.2026: `172.217.112–119.4`).
Подсетью Gemini от записи в Google Calendar не отделить: уводя одно, уводите
и второе — то есть отказ VPN начнёт гасить ещё и запись событий, чего
ADR-037 избегал специально.

Выбор из трёх (ADR-050), и он за owner:

| | Что делаем | Чем платим |
|---|---|---|
| 1 | обе подсети в VPN | Календарь ходит через Германию, его живучесть привязана к VPN |
| 2 | только `160.79.104.0/23` (Anthropic) | разбор события идёт резервом, вчетверо дороже; основная модель отказывает |
| 3 | прокси на плате вместо подсетей | ещё одна служба, чьё падение похоже на отказ провайдера |

Вариант 2 — самый дешёвый способ проверить, что всё остальное работает:

```
PostUp = ip route replace 160.79.104.0/23 dev %i
```

**Проверить:**

```bash
ip route get 160.79.104.10                       # ждём "dev awg0"
make llm-probe-pi                                # план: ни одного вызова
make llm-probe-pi-apply                          # по вызову на модель, доли цента
```

**Как читать отчёт пробы.**

| Строка | Что значит |
|---|---|
| `OK` | ключ рабочий, модель доступна, схема прошла с первого раза |
| `ВЫХОД` | запрос ушёл мимо VPN — это маршрут платы, а не код и не ключ |
| `ОТКАЗ` | провайдер не ответил: ключ, имя модели или его недоступность |
| `НЕТ КЛЮЧА` | ключа нет в `.env` — провайдер просто не подключён |

Строка `батч: <провайдер> доступен` отвечает на вопрос ADR-046: батч есть
не на всяком уровне доступа, и ответ панели надёжнее документации.

**Когда что-то пошло не так.**

*Все строки `ВЫХОД`.* Маршрута нет или он затёрт: `ip route get` не показывает
`dev awg0`. Лечится так же, как в шаге 8, — вернуть `PostUp` и дописать
в конфиг.

*Часть моделей `OK`, часть `ВЫХОД`.* Адреса фронтенда провайдера не покрылись
выписанной подсетью — они не закреплены и меняются (риск из ADR-050).
Пересмотреть список, а не списывать на «иногда не работает».

*`ОТКАЗ` с текстом про модель.* Имя модели в `LLM_ROUTING` не то, что ждёт
провайдер. Проверяется `make llm-routes-pi` — он печатает разобранное
назначение и отличает опечатку в JSON от «не назначено».

*Проба говорит «месячный потолок исчерпан».* Так и задумано: обойти потолок
ради диагностики значит перестать иметь потолок.

### Backblaze B2 → `B2_BUCKET`, `B2_KEY_ID`, `B2_APP_KEY`

1. B2 Cloud Storage → Create a Bucket, тип **Private**.
2. Application Keys → Add a New Application Key: доступ **только к этому
   бакету**, права `writeFiles`, `listFiles`, `listBuckets` —
   **`deleteFiles` не давать.** Смысл в ADR-020: сбойнувшая или
   скомпрометированная плата физически не должна уметь стереть историю копий.
   Удаляет только облако, правилами жизненного цикла.
3. `applicationKey` показывается один раз — сохранить сразу.
4. Lifecycle Rules на бакете: глубина 7 ежедневных / 4 недельных /
   6 месячных, по префиксам (`daily/` и далее).

**Дампы не шифруются** — решение owner, риск очерчен в ADR-020. Поэтому
`ISU_CRED_KEY` в бакете оказаться не должен никогда: он живёт только в `.env`.

### Сторож бэкапа → `HEARTBEAT_URL`

Подходит любой сервис «мёртвой руки», принимающий GET: **UptimeRobot**,
**Better Stack**, healthchecks.io. Требование одно: сторож живёт **вне дома**,
иначе он умрёт вместе с платой и промолчит именно тогда, когда нужен.

1. Создать монитор типа **Heartbeat** (не «HTTP» — тот сам стучится к вам,
   а нужен обратный: ждать стука от платы).
2. Период — **1 день**, допуск опоздания — **2 часа**.
3. Скопировать выданный URL.

Джоб отказывается делать `--apply` с пустым `HEARTBEAT_URL`: бэкап без
контроля — это бэкап, о поломке которого узнают в день восстановления.

---

### Сторожа живучести (Э9) → `JOBS_HEARTBEAT_URL`, `RESTORE_HEARTBEAT_URL`

Ещё два монитора «мёртвой руки» в том же сервисе. От сторожа бэкапа каждый
отличается тремя вещами: периодом, вопросом и ценой молчания (ADR-043).
Заводятся так же: Heartbeat, скопировать URL, вписать в `.env` на плате.

| Переменная | Тип монитора | Период | Что означает молчание |
|---|---|---|---|
| `JOBS_HEARTBEAT_URL` | Heartbeat | **1 день**, допуск 3 часа | сутки ни одного удачного прогона цепочки: расписание не доезжает до Google |
| `RESTORE_HEARTBEAT_URL` | Heartbeat | **1 месяц**, допуск 2 дня | копия не разворачивается или в ней нет данных |
| — (адреса нет) | **HTTP** на `https://viniron.ru/health` | минуты | плата выключена или туннель лёг |

Третья строка — не heartbeat, а обычный монитор доступности: он ходит сам,
и `/health` пропущен мимо Access ровно ради него (ADR-036). Заменить друг
друга сигналы не могут: `/health` отвечает, что сервис жив, и ничего не знает
о том, доезжает ли расписание; сторож бэкапа знает про копию и не знает,
восстанавливается ли она.

Пустой `JOBS_HEARTBEAT_URL` прогон цепочки **не запрещает** — в отличие от
бэкапа: расписание в календаре полезно и без наблюдателя. В логе при этом
на каждом прогоне строка «сторож цепочки не настроен», чтобы ненастроенный
сторож не выглядел молчащим.

---

### ИСУ → `ISU_LOGIN`, `ISU_PASSWORD`, `ISU_CRED_KEY`

Регистрировать ничего не надо — учётная запись уже есть. Нужны три строки
в `.env` **на плате**; в чат они не присылаются.

```bash
ISU_LOGIN=<логин ИСУ>
ISU_PASSWORD=<пароль ИСУ>
ISU_CRED_KEY=<вывод openssl rand -base64 32>
```

**Зачем третья строка.** Пароль ИСУ нужен приложению постоянно: без него не
выпустить новый refresh-токен, когда старый кончится. Значит, он лежит в базе.
База каждую ночь уезжает дампом в B2, и **дампы не шифруются** (ADR-020) —
открытым текстом пароль в дампе означал бы, что утечка бэкапа равна утечке
доступа к ИСУ. `ISU_CRED_KEY` — замок: пароль шифруется им перед записью,
в облако уезжает шифротекст, ключ остаётся в `.env`.

Отсюда единственное жёсткое правило: **ключ и дамп не должны оказаться
в одном месте.** В бакете B2 ключу делать нечего никогда.

Генерировать — на плате, той же командой, что и пароль базы:

```bash
openssl rand -base64 32
```

**Сохранить копию ключа в двух местах** (менеджер паролей и что-нибудь
офлайновое). Восстановить его неоткуда: в git его нет, в бэкапе его нет.
Потеря ключа не катастрофа — приложение попросит ввести пароль ИСУ заново;
катастрофа — потеря ключа вместе с забытым паролем.

Кавычки вокруг значений не ставить: `docker compose` их не снимает, и они
уедут внутрь пароля.

Проверка, что вписалось без опечаток (сами значения на экран не выводятся):

```bash
grep -c '^ISU_.*=' ~/jarvis/.env               # 3
grep '^ISU_' ~/jarvis/.env | grep -c CHANGE_ME  # 0
chmod 600 ~/jarvis/.env
```

Первый забор расписания и что он делает — раздел «Расписание из my.itmo.ru».

## Ночной бэкап по расписанию

Юниты лежат в репозитории и ставятся симлинками — правка в git сразу
доходит до systemd:

```bash
sudo ln -sf /home/jarvis/jarvis/infra/systemd/jarvis-backup.service /etc/systemd/system/
sudo ln -sf /home/jarvis/jarvis/infra/systemd/jarvis-backup.timer /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now jarvis-backup.timer
```

Проверки:

```bash
systemctl list-timers jarvis-backup.timer   # когда следующий запуск
sudo systemctl start jarvis-backup.service  # прогнать сейчас
journalctl -u jarvis-backup.service -n 50   # что было в последний раз
```

`Persistent=true` в таймере означает, что пропущенный из-за выключенной платы
запуск выполнится при следующем включении — тот же принцип, что инвариант 11.

### Ежемесячная проверка восстановления

Второй таймер, рядом с бэкапом и по тем же правилам. Ставится один раз:

```bash
sudo ln -sf /home/jarvis/jarvis/infra/systemd/jarvis-restore-check.service /etc/systemd/system/
sudo ln -sf /home/jarvis/jarvis/infra/systemd/jarvis-restore-check.timer /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now jarvis-restore-check.timer
```

Идёт первого числа в 04:30 — через час после ночного бэкапа, то есть
проверяется копия этой же ночи, она же уезжает в месячный префикс B2
и переживёт все остальные. Живую базу таймер не трогает: дамп
разворачивается в `jarvis_restore`.

```bash
systemctl list-timers jarvis-restore-check.timer
sudo systemctl start jarvis-restore-check.service   # прогнать сейчас
journalctl -u jarvis-restore-check.service -n 80    # отчёт последнего прогона
```

Отчёт — список пунктов `[OK]` / `[FAIL]`. Непройденный пункт означает, что
копии верить нельзя, и ping сторожу в этом случае **не уходит**: через
месяц с небольшим придёт письмо. Разбор — в разделе ниже.

## Восстановление из бэкапа

Главная процедура файла. Пока она не проделана руками хотя бы раз, бэкапа
считай что нет (ADR-020).

**Быстрая проверка последней локальной копии** — не требует B2:

```bash
make restore-check
```

Разворачивает свежайший дамп в базу `jarvis_restore`, печатает число строк
по каждой таблице и отчёт из четырёх пунктов. Живую базу не трогает, ping
не шлёт — наружу пишет только `make restore-check-apply`, и так эту же
проверку зовёт ежемесячный таймер.

Пункты и что означает провал каждого:

| Пункт | Провал означает |
|---|---|
| копия свежая | ночной бэкап встал: смотреть `journalctl -u jarvis-backup.service` |
| таблицы из дампа на месте | `pg_restore` прошёл не до конца — читать его вывод выше по логу |
| `alembic_version` знает версию | дамп снят не с базы приложения (не тот `POSTGRES_DB`) |
| данные восстановились | восстановилась схема без строк: копия негодна, брать предыдущую |

Ожидаемый состав берётся из оглавления самого дампа (`pg_restore --list`),
а не из списка в репозитории: список рядом с кодом, снявшим дамп, сверял бы
дамп сам с собой.

**Полное восстановление из облака** — то, что понадобится при смерти карты:

1. Скачать дамп из бакета через веб-интерфейс B2 (ключ на плате читать не
   умеет намеренно) и положить на плату, например в `/tmp/restore.dump`.
2. Скопировать файл в том с копиями и развернуть:

```bash
docker cp /tmp/restore.dump jarvis-db-1:/tmp/restore.dump
docker exec -i jarvis-db-1 psql -U jarvis -d postgres -c "DROP DATABASE IF EXISTS jarvis_restore"
docker exec -i jarvis-db-1 psql -U jarvis -d postgres -c "CREATE DATABASE jarvis_restore"
docker exec -i jarvis-db-1 pg_restore -U jarvis -d jarvis_restore --exit-on-error /tmp/restore.dump
docker exec -i jarvis-db-1 psql -U jarvis -d jarvis_restore -c '\dt'
```

3. Убедиться, что данные на месте: `\dt` показывает девять таблиц схемы v1
   (`settings`, `integration_tokens`, `itmo_lessons`, `calendar_events`,
   `day_flags`, `audit_log`, `job_runs`, `capture_drafts`, `capture_blobs`)
   плюс `alembic_version`.
4. Только после этого, если восстановление идёт вместо живой базы:
   остановить стек, переименовать базы, поднять снова.

Порядок именно такой: сначала развернуть рядом и посмотреть, потом
подменять. Восстановление поверх живой базы не оставляет пути назад.

## Схема базы и миграции

Схему создаёт только Alembic (инвариант хоста 3). Руками в базе структуру
не менять — иначе следующий `upgrade` встретит не то, что ожидает.

```bash
make migrate-pi      # накатить всё, чего ещё нет
```

**Чистая плата:** поднять стек, затем `make migrate-pi` — база получит схему
с нуля.

**После восстановления из дампа миграции применять не нужно:** `pg_dump -Fc`
несёт и структуру, и таблицу `alembic_version`. Прогнать `make migrate-pi`
всё же стоит — он либо не сделает ничего, либо докатит то, чего в старом дампе
не было, и это единственный способ заметить, что дамп старше кода.

**Обновление кода на плате.** Порядок обязателен именно такой:

```bash
cd ~/jarvis && git pull
make build          # без этого up -d оставит старый образ
make up
make migrate-pi     # если в обновлении есть миграции
```

`make build` пропускать нельзя: `up -d` поднимает уже собранный образ молча,
и новый код на плату просто не приезжает. Симптом пропуска - `alembic: not
found` или старое поведение API после «успешного» обновления.

**Если `git pull` отказывается** («Your local changes would be overwritten»),
значит в рабочей копии лежат файлы, доставленные мимо git. Разработка на плате
не ведётся, поэтому местные версии выбрасываются:

```bash
tar czf ~/jarvis-pre-pull-$(date +%F).tar.gz --exclude=.git -C ~ jarvis
git checkout -- .
git clean -fd apps infra docs
git pull
```

`git clean` без `-x` игнорируемые файлы не трогает, а пути ограничены тремя
каталогами - `.env` в корне остаётся на месте. Снимок в tar делается всё равно:
секунда времени против невосстановимой потери.

**Проверить, на какой версии база:**

```bash
docker compose --env-file .env -f infra/docker-compose.yml -f infra/docker-compose.pi.yml   run --rm api alembic -c /app/apps/api/alembic.ini current
```

## Расписание из my.itmo.ru

Джоб забирает расписание портала в зеркало `itmo_lessons`. В Google из
зеркала пишет отдельный джоб — раздел «Google Calendar» ниже.

**По умолчанию ничего не записывает.** `sync-itmo` показывает дифф и выходит;
единственное, что он сохраняет в этом режиме, — токены доступа, добытые
входом. Без этого каждый ручной прогон логинился бы паролем заново.

```bash
cd ~/jarvis
make sync-itmo-pi          # дифф, в базу не пишет
make sync-itmo-pi-apply    # запись зеркала
```

**Что читать в выводе.** Строки `+` — пары, которых в зеркале не было,
`~` — изменившиеся, `-` — исчезнувшие из расписания портала. Первый прогон
показывает одни `+`; второй подряд — ноль изменений, и это главная проверка:
джоб идемпотентен, двойной запуск не задваивает расписание.

**Проверить, что легло в базу:**

```bash
docker exec -i jarvis-db-1 psql -U jarvis -d jarvis -c \
  "select lesson_date, starts_at, subject, room, fetched_at from itmo_lessons order by starts_at limit 10;"
```

Время в базе — **UTC** (инвариант 7). Пара, стоящая в расписании на 10:00,
здесь будет 07:00 — это не сдвиг, а хранение.

### Когда что-то пошло не так

Джоб падает громко и называет причину. Три сообщения, которые стоит узнавать:

- **`ISU_CRED_KEY пуст`** — не заполнена третья строка в `.env`. Шифровать
  пароль нечем, и класть его открытым текстом джоб отказывается.
- **`ITMO ID не принял логин и пароль`** — Keycloak показал форму снова.
  Почти всегда это действительно неверный пароль; ни логин, ни пароль
  в текст ошибки не попадают, поэтому лог можно пересылать.
- **`на странице входа ITMO ID не найден loginAction`** — портал сменил
  разметку страницы входа. Чинится не в `.env`, а правкой регулярного
  выражения в `apps/api/jarvis_api/integrations/itmo/auth.py`; это самое
  хрупкое место интеграции, и оно названо своим именем нарочно.
- **`формат ответа my.itmo.ru изменился`** — портал переименовал или убрал
  поле. Джоб не пишет разобранный мусор в базу; правится
  `integrations/itmo/schema.py`.

След каждого прогона — в базе:

```bash
docker exec -i jarvis-db-1 psql -U jarvis -d jarvis -c \
  "select at, status, detail from audit_log where kind='itmo_fetch' order by at desc limit 5;"
docker exec -i jarvis-db-1 psql -U jarvis -d jarvis -c \
  "select * from job_runs where job='sync_itmo' order by run_date desc limit 5;"
```

**Смена пароля ИСУ.** Пароль хранится в базе, а не читается из `.env` каждый
раз, поэтому правки одной строки в `.env` мало. После смены пароля на портале:

```bash
docker exec -i jarvis-db-1 psql -U jarvis -d jarvis -c \
  "delete from integration_tokens where provider='itmo';"
```

Следующий прогон возьмёт новое значение из `.env` и положит его в базу заново.

## Google Calendar

Расписание из зеркала уезжает в календарь owner. Доступ — **service account**
(ADR-019): у него нет ни браузерного входа, ни срока жизни токена, ни
требования публичного HTTPS-имени. Календари он создаёт себе и отдаёт owner.

### Что завести в Google Cloud — один раз

1. [console.cloud.google.com](https://console.cloud.google.com) → создать
   проект (имя любое, например `jarvis`).
2. **APIs & Services → Library → Google Calendar API → Enable.** Без этого
   шага все запросы получают `403`, и выглядит это как проблема с ключом.
3. **IAM & Admin → Service Accounts → Create service account.** Имя любое,
   например `jarvis-calendar`. **Роли не нужны** — на шаге «Grant this
   service account access to project» ничего не выбирать: доступ к
   календарям даётся не ролями IAM, а тем, что аккаунт сам их создаёт.
4. Открыть созданный аккаунт → вкладка **Keys → Add key → Create new key →
   JSON**. Файл скачается сам; второй раз его не показывают.

### Ключ в `.env` на плате

JSON нужен **одной строкой**. Превратить скачанный файл:

```bash
python3 -c 'import json,sys; print(json.dumps(json.load(open(sys.argv[1]))))' key.json
```

Полученную строку вписать в `~/jarvis/.env` целиком, без кавычек вокруг:

```
GOOGLE_SA_JSON={"type":"service_account","project_id":"…"}
GOOGLE_CALENDAR_OWNER_EMAIL=почта-owner@gmail.com
```

Две вещи, о которых стоит знать заранее:

- **Кавычек вокруг значения ставить не нужно** — JSON начинается с `{`, и
  compose передаёт строку как есть. А вот символ `$` в значении compose
  попытался бы подставить как переменную; в ключах Google его не бывает
  (base64 плюс hex), но если однажды появится — его удваивают: `$$`.
- **Скачанный файл ключа после этого удалить.** В репозиторий он не должен
  попасть никогда (инвариант 6), и второй копии на диске быть не должно.

Дальше — перезапуск стека, чтобы переменные дошли до контейнера:

```bash
cd ~/jarvis && docker compose --env-file .env -f infra/docker-compose.yml -f infra/docker-compose.pi.yml up -d
```

### Создать календари

```bash
make gcal-setup-pi          # показать, что будет создано
make gcal-setup-pi-apply    # создать и отдать owner
```

Создаётся три: `JARVIS · ИТМО`, `JARVIS · Занятия`, `JARVIS · События`.
Наполняется на этом этапе только первый — два других ждут курсов и захвата.
Их id ложатся в `settings`, а не в `.env`: они приезжают из Google и обязаны
вернуться вместе с базой при восстановлении из дампа.

**Что должен увидеть owner:** три новых календаря в списке слева в Google
Calendar.

**Приглашение приходит не на все три — проверено на живом прогоне Э4.**
Google разослал письма на два календаря из трёх, третий в списке не появился,
хотя доступ у него был выдан правильно. Права проверяются не почтой, а
запросом `acl().list()`; если в них есть почта owner ролью `owner`, календарь
просто не подписан. Добавляется вручную, без письма: слева **Other calendars →
+ → Subscribe to calendar**, вставить id календаря из `settings`
(`select gcal_itmo_id from settings;`). То же делает ссылка вида
`https://calendar.google.com/calendar/u/0/r?cid=<id>`.

Повторный запуск ничего не создаёт: команда сверяется с самим Google, а не
со своей базой. Календарь, удалённый owner вручную, при следующем прогоне
будет заведён заново — id в базе от этого не спасает и не должен.

### Записать расписание

```bash
make sync-gcal-pi          # дифф, наружу не пишет ничего
make sync-gcal-pi-apply    # запись в календарь
```

**Что читать в выводе.** `+` — событие будет создано, `~` — обновлено,
`-` — удалено, `!` — не записано, с причиной. Первый прогон — одни `+`;
**второй подряд обязан дать нули по всем трём** — это и есть проверка
идемпотентности, ради которой существует реконсил (§11.2).

Проверить, что записано:

```bash
docker exec -i jarvis-db-1 psql -U jarvis -d jarvis -c \
  "select external_key, title, starts_at, sync_state, google_event_id from calendar_events order by starts_at limit 10;"
docker exec -i jarvis-db-1 psql -U jarvis -d jarvis -c \
  "select at, status, target, detail from audit_log where kind='calendar_write' order by at desc limit 5;"
docker exec -i jarvis-db-1 psql -U jarvis -d jarvis -c \
  "select * from job_runs where job='push_gcal' order by run_date desc limit 5;"
```

Время в `calendar_events`, как и везде в базе, — UTC. Пара, стоящая в
расписании на 10:00, лежит как 07:00 и показывается в календаре как 10:00:
зона задана самому календарю при создании.

### Записать события захвата

События, подтверждённые owner в захвате, уезжают в `JARVIS · События` —
обычно **сразу при подтверждении** (ADR-042). Джоб ниже забирает только то,
что не дошло с первой попытки: Google не ответил за пять секунд, ключ был
отозван, календарь удалён.

```bash
make sync-capture-pi          # что стоит в очереди, наружу не пишет ничего
make sync-capture-pi-apply    # записать
```

**Пустой вывод — нормальное состояние.** «создано 0, обновлено 0,
с ошибкой 0» означает, что всё подтверждённое уже в календаре, а не что
джоб не работал: прогон он отмечает в `job_runs` в любом случае.

Что стоит в очереди и почему:

```bash
docker exec -i jarvis-db-1 psql -U jarvis -d jarvis -c \
  "select external_key, title, starts_at, sync_state, last_error
     from calendar_events where source='capture' and sync_state<>'synced'
     order by starts_at;"
```

`pending` — ещё не отправляли или отправка не удалась молча, `failed` —
Google отклонил событие, причина в `last_error`. Оба состояния джоб
пробует заново; `synced` он не трогает вовсе.

### Убрать брошенные черновики

Черновик живёт от захвата до подтверждения или отмены. Тот, к которому не
вернулись, убирается по сроку `CAPTURE_DRAFT_TTL_HOURS` (72 часа по
умолчанию) — это же число задаёт, сколько присланное owner лежит в ночных
дампах.

```bash
make capture-cleanup-pi          # показать, что просрочено
make capture-cleanup-pi-apply    # удалить
```

Оба шага входят в ежедневную цепочку, поэтому руками они нужны редко:
проверить перед первым живым прогоном и разобрать затор.

```bash
docker exec -i jarvis-db-1 psql -U jarvis -d jarvis -c \
  "select id, modality, created_at, left(coalesce(source_text,''), 40)
     from capture_drafts order by created_at;"
```

### Когда что-то пошло не так

- **`GOOGLE_SA_JSON пуст`** — переменная не дошла до контейнера. Сначала
  проверить `.env`, потом — что стек перезапущен после правки.
- **`GOOGLE_SA_JSON не разбирается как JSON`** — строка склеена не целиком
  или в неё попал перенос строки.
- **`календарь JARVIS · ИТМО не создан`** — не выполнен `make gcal-setup-apply`,
  либо он выполнялся против другой базы.
- **`Google отказал: … 403`** — два обычных случая: не включён Calendar API
  (шаг 2 выше) или ключ отозван в консоли. Прогон при этом прекращается
  целиком, а не перебирает все восемьдесят пар.
- **`Google недоступен`** — сеть или таймаут. Зеркало и журнал не тронуты,
  следующий прогон догонит: `sync-gcal` идемпотентен по построению.
- **Отдельные события с `!`** — они помечены `sync_state = failed` в
  `calendar_events`, причина в `last_error`. Следующий прогон допишет их сам,
  вмешательства не требуется.

**Событие, исправленное руками в Google, вернётся к прежнему виду.** Синк
односторонний (ADR-001): источник истины — расписание портала. Удалённое
руками событие создастся заново — по той же причине.

**Начать календарь с чистого листа:** удалить календарь `JARVIS · ИТМО`
в интерфейсе Google, затем очистить журнал и завести календарь заново.

```bash
docker exec -i jarvis-db-1 psql -U jarvis -d jarvis -c \
  "delete from calendar_events where source='itmo';"
docker exec -i jarvis-db-1 psql -U jarvis -d jarvis -c \
  "update settings set gcal_itmo_id = null where id = 1;"
make gcal-setup-apply && make sync-gcal-pi-apply
```

## Расписание джобов

С Э5 расписание и календарь обновляются сами: планировщик живёт внутри
процесса API и гоняет цепочку «забор расписания → запись в Google» шесть раз
в день — каждые три часа с 06:30 до 21:30 по зоне owner. Плюс догоняющий
запуск при каждом старте контейнера, если за сегодня успешного прогона ещё
не было. Внешнего cron нет и не нужно (ADR-020).

Руками то же самое:

```bash
make daily-pi          # показать, что сделала бы цепочка (dry-run)
make daily-pi-apply    # выполнить
```

### Настройки

Все четыре живут в `.env` на плате, все со здравыми умолчаниями — пустая
строка означает «умолчание», а не ошибку.

| Переменная | Умолчание | Что делает |
|---|---|---|
| `SCHEDULER_ENABLED` | `true` | рубильник; `false` — API поднимается без планировщика |
| `SCHEDULER_DAILY_TIMES` | `06:30,…,21:30` | времена прогона по зоне owner |
| `SCHEDULER_CATCHUP_COOLDOWN_MINUTES` | `30` | пауза перед повторной попыткой догона |
| `SCHEDULER_MISFIRE_GRACE_SECONDS` | `1800` | сколько слот ждёт занятого воркера |
| `JOBS_HEARTBEAT_URL` | пусто | сторож цепочки: ping после прогона без отказавших шагов (Э9) |

После правки `.env` — `make up` (compose перезапустит контейнер сам).

Сигнал сторожу уходит **только** после прогона, в котором не отказал ни один
шаг: сутки молчания означают, что расписание не доезжает до Google, и об этом
придёт письмо (ADR-043). Обратное неверно — недоступный сторож оставляет
в логе строку `сторож цепочки не получил сигнал` и прогон не отменяет.

### Убедиться, что расписание стоит

При старте планировщик пишет в лог строку со слотами и зоной:

```bash
make logs | grep "расписание джобов"
# 2026-09-10 06:31:02 INFO jarvis.scheduler: расписание джобов:
# 06:30,09:30,12:30,15:30,18:30,21:30 (зона Europe/Moscow)
```

Что делали джобы за последние дни — в базе, а не в логе:

```bash
docker exec -i jarvis-db-1 psql -U jarvis -d jarvis -c \
  "select job, run_date, status, started_at, finished_at, error
     from job_runs order by run_date desc, job limit 12;"
```

Строк за день пять: `daily_calendar` — итог цепочки, `sync_itmo`, `push_gcal`,
`push_capture` и `capture_cleanup` — её шаги. Строка `running` с пустым `finished_at` означает, что процесс убили
посреди прогона; следующий старт её догонит.

### Когда что-то пошло не так

**Джобы не идут вовсе.** Сначала `make logs | grep планировщик`. «планировщик
выключен» — значит `SCHEDULER_ENABLED=false` в `.env`. Тишина вместо строки
с расписанием — процесс не дошёл до подъёма: смотреть ошибки выше по логу.

**Джобы идут не в то время.** Почти всегда это зона. Триггеры строятся один
раз при старте процесса, поэтому смена `settings.timezone` в базе применяется
**только после перезапуска**:

```bash
docker compose --env-file .env -f infra/docker-compose.yml \
  -f infra/docker-compose.pi.yml restart api
```

**API не встаёт после правки `.env`.** Проверить, что в переменных
`SCHEDULER_*` нет мусора: `SCHEDULER_DAILY_TIMES=утром` роняет процесс при
старте — намеренно, с внятным текстом в логе. Пустое значение при этом
законно и означает умолчание.

**Прогон падает каждый раз.** Причина в `job_runs.error` и в `audit_log`
(`kind = 'job_chain'` — итог цепочки, `itmo_fetch` и `calendar_write` — шаги).
Отказ одного шага не отменяет второй: портал мог не ответить, а реконсил
Google при этом всё равно полезен.

**Не запускать `make daily-pi-apply` руками, пока идёт слот.** Задвоения
не будет — на то и реконсил, — но строка `job_runs` за день перезапишется,
и разбираться потом будет не по чему.

## API календаря

С Э6 у платы есть предметные эндпоинты: сетка календаря и периоды
исключений. Наружу сервис не выставлен — он слушает `127.0.0.1`, туннель
выключен. **Туннель не включать раньше, чем появится аутентификация**
(она на Э7, ADR-031): сейчас любой, кто дотянется до порта, читает
расписание и правит периоды.

| Метод | Путь | Зачем |
|---|---|---|
| `GET` | `/api/calendar?view=week&date=2026-10-14` | сетка на неделю или день; без `date` — вокруг сегодня |
| `GET` | `/api/day-flags?from=&to=` | периоды исключений; без параметров — окно забора |
| `POST` | `/api/day-flags` | внести период |
| `DELETE` | `/api/day-flags/{flag_id}` | убрать период |

### Настройки

Живут в `.env` на плате, все со здравыми умолчаниями; пустая строка
означает «умолчание», а не ошибку.

| Переменная | Умолчание | Что делает |
|---|---|---|
| `CALENDAR_STALE_AFTER_HOURS` | `12` | через сколько часов без успешного забора экран показывает полосу давности |
| `DB_CONNECT_TIMEOUT_SECONDS` | `5` | таймаут соединения с базой: недоступная база даёт 503, а не спиннер |
| `DB_POOL_TIMEOUT_SECONDS` | `10` | сколько запрос ждёт свободное соединение, пока идёт цепочка джобов |

Прореживаете `SCHEDULER_DAILY_TIMES` — поднимайте и `CALENDAR_STALE_AFTER_HOURS`:
порог ниже ночного перерыва зажигает полосу каждое утро. После правки
`.env` — `make up`.

### Убедиться, что работает

```bash
curl -s http://127.0.0.1:8000/health
curl -s "http://127.0.0.1:8000/api/calendar?view=week" | head -c 400
```

Свежесть смотреть в блоке `freshness` ответа:

```bash
curl -s "http://127.0.0.1:8000/api/calendar?view=day"   | python3 -c "import sys,json; print(json.load(sys.stdin)['freshness'])"
# {'state': 'fresh', 'fetched_at': '2026-10-14T07:10:00+00:00',
#  'portal': 'ok', 'covered_from': '2026-10-07', 'covered_to': '2026-11-13'}
```

`state`: `fresh` — забор был недавно; `stale` — порог превышен, экран
покажет полосу; `never` — зеркало пусто, забора не было ни разу. `portal`
объясняет причину: `failing` — последний прогон забора упал.

Период исключений заводится и убирается так:

```bash
curl -s -X POST http://127.0.0.1:8000/api/day-flags   -H 'Content-Type: application/json'   -d '{"starts_on":"2026-10-20","ends_on":"2026-10-24","reason":"отъезд"}'
curl -s -X DELETE http://127.0.0.1:8000/api/day-flags/1 -o /dev/null -w '%{http_code}
'
```

### Когда что-то пошло не так

Тело отказа одно на все случаи: `code`, `message` по-русски, `retryable`.

**503 `database_not_configured`.** `DATABASE_URL` пуст в `.env` на плате.
Повтор не поможет, см. `.env.example`. `/health` при этом отвечает 200 —
он в базу не ходит намеренно.

**503 `database_unavailable`.** Контейнер `db` не поднят или пул занят:
`docker ps`, затем `make logs`. Проходит само — `retryable: true`.

**503 `owner_timezone_invalid`.** В `settings.timezone` лежит зона, которой
нет в базе зон. Текст отказа называет её; чинится одной строкой:

```bash
docker exec -i jarvis-db-1 psql -U jarvis -d jarvis -c   "update settings set timezone = 'Europe/Moscow';"
```

**Дни приходят с `mirror_covers: false`.** Это не поломка API: забор до этих
дней не доходил. Прогнать цепочку — `make daily-pi-apply`, затем проверить
`freshness.fetched_at`.

**409 на удаление периода.** Пометку `late_classes` ставит и снимает джоб
расчёта времени занятий (§4), руками она не трогается — снятая, вернулась
бы сама.

**`make test` краснеет на `test_contract`.** Контракт разошёлся с
приложением: `make contract` и закоммитить `packages/contracts/openapi.json`
вместе с правкой эндпоинтов. Если эндпоинты не менялись — поднялась версия
FastAPI, и это тоже правка контракта: от неё меняется клиент Э7.

## Интерфейс

С Э7 рядом с API живёт сервис `web`: готовая статика Next и Caddy, который
её раздаёт. Наружу он смотрит один на всю плату — туннель ведёт на него,
а не на API (`infra/Caddyfile`).

| Что | Где |
|---|---|
| Интерфейс | `http://127.0.0.1:8080/` на плате, публичное имя — через туннель |
| API через прокси | `/api/*` и `/health` того же адреса |
| Конфиг раздачи | `infra/Caddyfile`, едет в образ при сборке |
| Файлы страниц | внутри образа, `/srv`; на диске платы ничего не лежит |

**Фронт и API обязаны быть на одном источнике.** CORS в API не настроен
намеренно (ADR-031 п. 3): браузер ходит по относительному `/api`, и всё
сводит Caddy. Маршрут туннеля прямо на `api:8000` эту сборку ломает —
интерфейса по такому адресу нет вовсе.

**Статика собирается при сборке образа.** Правка интерфейса доезжает до
платы только после пересборки:

```bash
docker compose --env-file .env -f infra/docker-compose.yml                -f infra/docker-compose.pi.yml build web
make up
```

Node внутри образа нет: он живёт только в сборочном слое, в рантайме
остаётся Caddy с файлами (ADR-020). Сборка фронта — самый тяжёлый шаг из
всех, что плата делает: если ей не хватит памяти, образ собирается на
машине owner через `docker buildx --platform linux/arm64` и грузится
на плату.

### Когда что-то пошло не так

**Страница открывается, данных нет, в консоли браузера 404 на `/api/...`.**
Caddy не дошёл до API: `docker compose logs web` и `make logs` — жив ли
контейнер `api`. Сервис `web` ждёт его здоровым при старте, но пережить
падение API он обязан молча.

**Страница открывается, а API отвечает 401 на всё.** Это Cloudflare Access,
а не фронт: `CF_ACCESS_*` в `.env` (ADR-033). Пустые значения при `ENV=prod`
закрывают `/api/*` целиком — так и задумано.

**`make up` поднял стек, но `127.0.0.1:8080` молчит.** Смотреть
`docker compose ps`: контейнер `web` не станет здоровым, пока не станет
здоровым `api`, а тот ждёт базу.

## Плата переехала в другую сеть

Симптом: плата включена, но недоступна ни по `jarvis.local`, ни по прежнему
адресу, и сканирование новой сети её не находит. Причина почти всегда одна:
прописанные в ней сети не совпадают с доступными. Ничего не сломано — плата
просто не вышла в сеть.

**Сначала проверить, не вышла ли плата в сеть всё-таки.** Если сайт открывается
снаружи, плата жива и в интернете — значит потерялся только локальный адрес,
и ходить к ней можно через туннель: `ssh jarvis-pi` адреса не знает вовсе
(ADR-045). Способы ниже — для случая, когда в сеть она не вышла.

Способы, от простого к муторному. Выбирается по тому, что под рукой.

### 1. Кабель Ethernet — если есть провод и порт

Воткнуть в роутер: плата получит адрес по DHCP независимо от Wi-Fi. Дальше
зайти по SSH (адрес искать в панели роутера или сканированием подсети) и
добавить сеть штатно:

```bash
sudo nmcli device wifi connect "<SSID>" password "<пароль>"
sudo nmcli connection modify "<SSID>" connection.autoconnect-priority 10
```

### 2. Точка доступа на телефоне с именем прежней сети

Создать на телефоне точку с **тем же SSID и тем же паролем**, что знает
плата. Она подключится, приняв её за домашнюю; ноутбук подключить туда же —
и дальше как в первом способе. Провода не нужны.

### 3. Карта в ноутбук — когда нет ни кабеля, ни телефона

Профили сетей NetworkManager лежат в `/etc/NetworkManager/system-connections/`,
то есть в ext4-разделе, которого Windows не видит. Но у Raspberry Pi OS есть
штатный способ выполнить скрипт при загрузке, задаваемый **с загрузочного
раздела** — того самого, что Windows видит как `bootfs`. Тот же механизм
использует Imager для своего `firstrun.sh`.

Порядок:

1. Выдернуть питание платы (корректно выключить нечем — SSH недоступен),
   вынуть microSD, вставить в ноутбук. Предложение Windows отформатировать
   второй раздел — **отклонить**.
2. Создать на `bootfs` файл `jarvis-net.sh`. **Только ASCII и только
   переводы строк LF**: файл правится Блокнотом, а `/bin/sh` не выполнит
   скрипт с CRLF в строке `#!`.

```sh
#!/bin/sh
set -e
BOOT=/boot/firmware
NMDIR=/etc/NetworkManager/system-connections
SSID='<имя новой сети>'
PSK='<пароль>'

UUID=$(cat /proc/sys/kernel/random/uuid)
PROFILE="$NMDIR/$SSID.nmconnection"
cat > "$PROFILE" <<PROFILE_EOF
[connection]
id=$SSID
uuid=$UUID
type=wifi
autoconnect=true
autoconnect-priority=10

[wifi]
mode=infrastructure
ssid=$SSID

[wifi-security]
key-mgmt=wpa-psk
psk=$PSK

[ipv4]
method=auto

[ipv6]
addr-gen-mode=default
method=auto
PROFILE_EOF
chmod 600 "$PROFILE"
chown root:root "$PROFILE"

# Себя из cmdline.txt убрать обязательно: иначе скрипт пойдёт каждую
# загрузку, а на FAT32 останется лежать пароль от Wi-Fi.
sed -i 's/ systemd\.run=[^ ]*//g; s/ systemd\.run_success_action=[^ ]*//g; s/ systemd\.unit=[^ ]*//g' "$BOOT/cmdline.txt"
rm -f "$BOOT/jarvis-net.sh"
```

3. Дописать в конец **единственной строки** `cmdline.txt` (перевод строки
   внутри ломает загрузку):

```
systemd.run=/boot/firmware/jarvis-net.sh systemd.run_success_action=reboot systemd.unit=kernel-command-line.target
```

4. Извлечь карту, вернуть в плату, включить. Плата выполнит скрипт, уберёт
   его вместе с параметром из `cmdline.txt`, перезагрузится и подключится
   к новой сети.

### Чтобы это не повторялось

Держать в плате **несколько** профилей сразу — домашний, запасной и точку
доступа телефона. NetworkManager подключится к той, что доступна, а
`autoconnect-priority` задаёт предпочтение. Добавить сеть, находясь на плате:

```bash
# Проще всего — подключиться к сети, находясь в её зоне: профиль создастся сам.
sudo nmcli device wifi connect "<SSID>" password "<пароль>"

# Приоритет: чем больше число, тем охотнее плата выберет эту сеть.
sudo nmcli connection modify "<SSID>" connection.autoconnect-priority 10

# Посмотреть, какие сети уже прописаны.
nmcli connection show
```

Тогда переезд плата переживает сама: включили — нашла знакомую сеть — поднялась.

## Если что-то не работает

| Симптом | Куда смотреть |
|---|---|
`/health` не отвечает | `docker ps`, `make logs`; база `healthy`? API ждёт её по `depends_on` |
Контейнеры не поднялись после перезагрузки | `systemctl is-enabled docker`, политика `unless-stopped` в compose |
`make` падает на `POSTGRES_PASSWORD` | нет `.env` в корне репозитория: compose ищет его в каталоге compose-файла, поэтому цели передают `--env-file` |
Бэкап молчит, healthchecks шлёт письмо | `journalctl -u jarvis-backup.service`; ping уходит только после успешной выгрузки — значит не дошла она |
`pg_dump: server version mismatch` | образ бэкапа обязан быть той же мажорной версии, что база: оба на `postgres:17-alpine` |
Туннель не поднимается | токен в `.env`, `docker compose logs cloudflared` |
`ssh jarvis-pi` не пускает | `cloudflared --version` в PATH, ключ в `authorized_keys`; `curl -sI https://ssh.viniron.ru` обязан дать редирект на вход Access или 401, а 502 — это открытый маршрут |
Нет места на карте | `df -h`, `docker system prune`, глубина копий `BACKUP_KEEP_LOCAL` |
Стек не поднялся, `docker info` показывает корень не в `/mnt/ssd` | не смонтировался SSD: `findmnt /mnt/ssd`, `dmesg -T \| grep -i sda`. Это штатный отказ, а не поломка: `nofail` пускает плату загрузиться, `RequiresMountsFor` не даёт демону создать пустой каталог на карте |

**Носитель — расходник.** Данные и дампы лежат на USB-SSD, система — на
microSD (ADR-032). Смерть карты стоит перезаливки образа, смерть SSD —
восстановления из B2. Поэтому офсайт-копия остаётся единственной настоящей
защитой истории занятий: проверять её восстановление раз в месяц, а не раз
в никогда.

**Если SSD переехал или заменён.** Раздел ищется по UUID в `/etc/fstab`
(строка помечена комментарием про `nofail`). Новый диск: разметить одним
разделом, `mkfs.ext4 -L jarvis-data -m 1`, подставить свежий UUID в `fstab`,
`mount -a`, затем восстановление по разделу «Восстановление из бэкапа» —
данные на старом носителе при замене не переносятся руками, они приезжают
дампом. TRIM через текущий бокс не проходит, `fstrim` не включён намеренно.
