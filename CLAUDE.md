# CLAUDE.md

Кодовое имя: **JARVIS**. Персональный ассистент для одного пользователя (owner) — студента ИТМО с 01.09.2026.

Спецификация платформы — `docs/SPEC.md`. Решения и их причины — `docs/DECISIONS.md`. Если инструкция здесь противоречит просьбе в чате — **спроси, не решай сам**.

## Фаза: PHASE 0 — проектирование

- Задача больше одного файла → **сначала план в чат, ждать «ок»**.
- Не писать «на будущее». Минимум, который работает и покрыт тестом.

**Две вещи приходят от owner. Их нельзя ни изобретать, ни требовать как условие работы:**

- **Содержание курсов** — темы, программы, уровни, пропорции занятия, лимиты повторений. Owner пришлёт файлами курсов. Движок разрабатывается и тестируется на `courses/_fixture/`; курс может быть установлен пустым, и это рабочее состояние, а не блокер.
- **Назначение моделей** — какая модель на какую задачу. Owner укажет позже. Слой моделей разрабатывается на заглушках; точки вызова и профили их требований зафиксированы в `SPEC.md` §5.1, конкретные модели — нет.

Не хватает программы или назначения модели → сделать всё остальное и обозначить недостающее. Не останавливаться и не подставлять выдуманное.

## Дизайн UI — где смотреть этап

Идёт **поэтапное проектирование интерфейса**: один экран за этап, макет показывается owner, этап закрывается только после «ок».

**Текущий этап, утверждённые макеты и решения по ходу — `design/PROGRESS.md`. Прочитать его перед любой работой по интерфейсу**, в любом чате, не спрашивая owner «на чём мы остановились». Макеты — `design/mockups/` (чистый HTML, открывается двойным кликом), палитра — `design/tokens.css`.

Визуальный ориентир задан owner: **ChatGPT и OpenAI**. Порядок этапов и рамки — там же в `PROGRESS.md`.

## Реализация — где смотреть этап

Код ведётся так же поэтапно, как интерфейс. **Текущий этап, что нужно от owner и решения по ходу — `docs/BUILD-PROGRESS.md`. Прочитать его перед любой работой по коду**, в любом чате, не спрашивая owner «на чём мы остановились».

Отличие от дизайна: этап закрывается не только «ок» owner, но и зелёной проверкой по Definition of Done. «Ок» без прогона тестов этап не закрывает.

## Что это

Вкладки: **Календарь**, **Финансы** и по одной на каждый установленный курс. Курсов планируется два, установлено пока ноль — и это рабочее состояние: их число переменная, а не константа. Первый релиз — календарь без курсов (ADR-019).

- **Календарь** — тянет расписание из my.itmo.ru в Google Calendar, создаёт события из текста, фото и голоса, ведёт периоды исключений (`day_flags`).
- **Финансы** — личная книжка расходов и доходов. Данные приходят выпиской банка, которую owner загружает файлом; автоматического канала нет и не будет (ADR-024). К учёбе отношения не имеет, движком курсов не пользуется — `SPEC.md` §15.
- **Курсы** — платформа, исполняющая любую учебную программу: очередь тем, активности внутри занятия, интервальные повторения, таймер, проверка работ моделью, контрольные срезы, змейка прогресса.

Ассистент работает **сам**: утренний джоб берёт голову очереди, подбирает материалы, ставит напоминание в календарь. Чат — интерфейс поверх, а не механизм работы.

## Инварианты

Нарушать только после обсуждения. Требует фича нарушить — остановись и скажи.

1. **Backend — источник истины.** Клиенты тонкие. Прогресс, rollover, выбор темы, интервалы повторения — только на сервере.
2. **Курс = данные, не код.** Ядро не знает названий предметов. Любое `if course == "..."` — баг. Предметная специфика живёт в манифесте курса и рубрике.
3. **Вкладки генерируются из списка курсов.** Календарь первый, дальше по одной на установленный курс. Хардкод списка — баг. Курс может быть **пустым**: вкладка открывается с пустым состоянием, джобы его пропускают, прогресс не делится на ноль.
4. **Прогресс — очередь, а не календарь.** Узел не привязан к дате. Отсюда следует «непройденное переносится, а не пролистывается».
5. **Записи наружу — через `integrations/`,** со стабильным `external_key` и режимом `--dry-run`. Двойной запуск джоба не создаёт дублей.
6. **Ни одного секрета в репозитории.**
7. **Всё время timezone-aware,** в БД только UTC. Наивных `datetime` нет.
8. **Аудит:** каждая запись в календарь и каждый вызов модели — в `audit_log` с провайдером, токенами, стоимостью.
9. **Деградация вместо падения.** Внешний источник недоступен → показываем последние сохранённые данные с явной пометкой давности, а не пустой экран и **не правдоподобную выдумку**. Материал не найден — так и пишем: сгенерированная ссылка на несуществующий источник хуже отсутствия ссылки. Пользователь всегда видит, свежие данные или нет. При этом **фоновые джобы падают громко**, а интерфейс деградирует тихо. Таблица случаев — `SPEC.md` §10.
10. **Проверяющая модель не льстит.** Оценка строгая, по рубрике курса. Засчитать неверное «чтобы не расстраивать» — баг уровня потери данных.
11. **Джобы переживают перезагрузку.** Планировщик при старте догоняет пропущенный джоб **в пределах текущего дня** (catch-up). Не рассчитывать, что сервер всегда включён в нужную минуту. Старше текущего дня — в отставание курса, не в календарь задним числом. `SPEC.md` §11.

## Стек

**Выбор языка.** Берём тот, что лучше подходит задаче; **при наличии выбора приоритет Python, затем C++.** Практическое применение здесь: на сервере Python, а не Go или Rust. Для C++ в текущем составе продукта подходящей задачи нет. **Не изобретать место для C++** (нативные модули, расширения, WASM) — правило про приоритет при выборе, а не про обязательное присутствие.

Фронтенд — не выбор, а ограничение: браузер исполняет только JavaScript и WASM, поэтому TypeScript.

| Слой | Выбор |
|---|---|
| Backend | Python 3.12 + FastAPI + Pydantic v2 |
| БД | PostgreSQL + Alembic |
| Планировщик | APScheduler в процессе API |
| SRS | `fsrs` (py-fsrs) — свой алгоритм не писать |
| Фронт | TypeScript, Next.js + Tailwind, **PWA** |
| iOS | **отложено** — ADR-002, не начинать без переспроса |
| Модели | маршрутизация конфигом, назначение от owner, `SPEC.md` §5 |
| Хостинг | домашний Raspberry Pi с первого дня (ADR-020): API, Postgres и фронт одним compose + Cloudflare Tunnel |

Контракт: OpenAPI в `packages/contracts/` — источник истины, клиенты генерируются.

## Ключевое по интеграциям

**my.itmo.ru** — официального API нет. Эндпоинт: `GET /api/schedule/schedule/personal?date_start=&date_end=` с заголовком `Authorization`, токен от ITMO ID (Keycloak на `id.itmo.ru`). **Перед реализацией прочитать референс** `github.com/iburakov/my-itmo-ru-to-ical`. Схема неофициальная: при изменении формата джоб падает громко, а не пишет мусор в календарь.

**Креды ИСУ:** приоритет за refresh-токеном; пароль хранится на сервере **в шифрованном виде**, ключ в env, не в базе — утёкший дамп без ключа бесполезен. Честная граница: на одном хосте лежат и шифротекст, и ключ, значит защита от утечки бэкапа, а не от компрометации Pi.

**Календарь — только Google.** iCloud, CalDAV, EventKit не используются (ADR-001). Двусторонний синк не делаем никогда. Отдельные календари: `JARVIS · ИТМО`, `JARVIS · Занятия`, `JARVIS · События`.

**Захват событий:** вход → модель извлекает структуру → черновик → **подтверждение** → запись. Без подтверждения писать запрещено, кроме автонапоминаний о занятиях. Низкая уверенность или нет даты → спросить, не угадывать.

**Слой моделей.** Маршрутизация — конфиг «задача → провайдер + модель», смена без деплоя. Закрытые задания идут **без модели**, детерминированной сверкой. Обязательно: `max_tokens` на каждом типе вызова; месячный потолок с деградацией на дешёвую модель **и уведомлением**; фолбэк при отказе провайдера; структурированный вывод по JSON Schema с валидацией и ретраем. Стабильная часть промпта строго в начале запроса — иначе кэш молча перестаёт попадать и счёт растёт кратно, это тестируемый инвариант. Механики кэша и батча у провайдеров различаются принципиально: **не прятать их за одной абстракцией**, адаптеры тонкие но раздельные.

## Команды

Нужной нет — добавь в `Makefile` и обнови этот раздел тем же коммитом.

```bash
make venv           # создать apps/api/.venv и поставить dev-зависимости
make dev / test / lint
make format         # ruff --fix + black
make compose-check  # docker compose config, без запуска
make db-up          # dev- и тестовая базы в Docker на машине разработки
make db-down        # остановить их
make build          # пересобрать образ api после правки Dockerfile или зависимостей
make migrate        # alembic upgrade head по DATABASE_URL
make migrate-pi     # то же внутри контейнера api на Pi
make revision m="…" # autogenerate новой миграции
make sync-itmo      # забор расписания в зеркало, dry-run по умолчанию
make sync-itmo-apply  # то же с записью зеркала
make sync-itmo-pi     # то же внутри контейнера api на Pi, dry-run
make sync-itmo-pi-apply  # то же с записью зеркала на плате

```

`make help` перечисляет цели и этап, на котором каждая появляется. Заглушкой
остался `plan-today`: он выходит с ошибкой, а не молча успехом.

Всё, что пишет наружу, по умолчанию `--dry-run`. Реальная запись — только `--apply`.

## Конвенции

Python: ruff + black, `mypy --strict`, Pydantic для всего внешнего, никаких `except:` без типа, внешние вызовы с таймаутом и backoff. Деньги — только `Decimal` в коде и `numeric` в схеме; `float` для сумм запрещён, копейки на нём расходятся в рубли за год. TypeScript: strict, `any` запрещён. Магические числа — в конфиг. Промпты — в `prompts/*.md` с версией, не в строковых литералах.

Коммиты: Conventional Commits, одна задача — один коммит, ветка на фичу. Комментарии объясняют «почему»; в rollover, расчёте времени, дедупликации и SRS — обязательны.

## Тесты

Обязательно покрыто: **rollover** (пропуск нескольких дней, брошенное занятие, узел на несколько сессий) · **время напоминания** (нет занятий, поздний конец и `latest_start`, расписание изменилось задним числом) · **дедупликация календаря** (двойной запуск, изменение, удаление в источнике) · **парсинг my.itmo.ru** на фикстурах · **учёт минут** (пауза, фон, обрыв, защита от накрутки) · **SRS** (интервалы, карточка из ошибки, объём колоды) · **пустой курс** (валидация, вкладка, джобы, деление на ноль) · **`day_flags` задним числом** (пересчёт отставания) · **структурированный вывод модели** на эталонном наборе. · **импорт выписки** (перекрывающиеся выгрузки, две одинаковые покупки в один день, дозревание `pending` в `posted`, изменившийся заголовок файла).

Сеть в тестах всегда замокана. Ни один тест не ходит в реальный my.itmo.ru, Google или к моделям.

## Безопасность

Секреты: креды ИСУ, ключ service account Google, ключи провайдеров моделей. Только env, в `.env.example` заглушки. **Код репозитория публичный, секреты и данные — нет** (ADR-019): push protection и secret scanning в GitHub, pre-commit `gitleaks`, фикстуры my.itmo.ru анонимизированы — в сыром ответе портала есть ФИО, номер ИСУ и группа. Секрет, попавший в историю, **отзывается и перевыпускается**, переписыванием истории он не лечится. Приватен при этом **работающий сервис**: наружу не выставляется, файрвол, SSH по ключу. Сырьё захвата (фото, аудио, текст) живёт в БД от загрузки до подтверждения или отмены черновика и удаляется вместе с ним; брошенный черновик убирается джобом по сроку из конфига. Токены не логировать даже на DEBUG. Ночной `pg_dump` в Backblaze B2 ключом только на запись, ежемесячный restore-тест (ADR-020) — годы истории занятий не восстановить ничем.

## Definition of Done

Тесты зелёные · `make lint` чист · миграция при изменении схемы · затронутые джобы проверены в `--dry-run` · обновлён `SPEC.md` при изменении поведения · развилка записана в `DECISIONS.md` · этап отмечен в `docs/BUILD-PROGRESS.md`.

## Чего НЕ делать

- Не изобретать содержание курсов и не назначать модели — это входные данные от owner.
- Не встраивать особенности конкретного предмета в ядро.
- Не хардкодить список вкладок.
- Не начинать нативное iOS-приложение без переспроса.
- Не трогать Apple Calendar, CalDAV, EventKit — решено, что их нет.
- Не добавлять **оценку** произношения и речи (ADR-010). Расшифровка надиктованного в захвате событий под запрет не подпадает — это третий способ ввести тот же текст, решение этапа 3 дизайна и ADR-019.
- Не писать в календарь без `--apply` и без ревью dry-run диффа.
- Не создавать событие без `external_key`.
- Не писать свой алгоритм интервальных повторений.
- Не заводить автоматический канал получения операций из банка — ни мост уведомлений, ни неофициальное API. Канал один: файл, который приносит owner (ADR-024).
- Не схлопывать одинаковые операции при импорте «раз такая уже есть» — две покупки на одну сумму в один день законны, и это потеря денег owner, а не аккуратность.
- Не прятать семантику кэша разных провайдеров за одной абстракцией.
- Не заводить `user_id` в таблицах — пользователь один, настройки в `settings` одной строкой.
- Не ставить занятие позже `latest_start`: день помечается `late_classes` и не входит в отставание.
- Не добавлять зависимость, не спросив.
- Не строить абстракции под несуществующие требования.
- Не менять схему БД мимо Alembic.
- Не ссылаться на нелегальные источники.
- Не коммитить `.env`, токены, дампы.
- Не молчать, если требование технически противоречиво.
- Не делать `git commit` и `git push` — owner коммитит и пушит сам. Менять файлы можно, фиксировать изменения в git — нет.
